## North-star fit

**Reuses:** the existing structured-failure plumbing almost entirely — `refusal()`/`classifyFailure()` in `dashboard/webhook-server/failure.js:74-96,185-187` already attach `{code, stage, message, remediation, action}` to every merge failure, and the webhook's JSON response (`failureResponse`, `failure.js:205-211`) already spreads that payload to the client. The gap isn't missing data, it's that three *different* client-side layers each collapse/re-derive it into a flat string instead of passing the structured fields through: `describeApproveFailure` (`mr_review.js:442-453`) bakes `code`+`stage`+`message`+action-wording into one sentence that `prState.js:186-187` then shows verbatim as the whole "detail" with no disclosure; `stage_strip.js` keeps its own hand-duplicated `REMEDIATION_BY_CODE` (18 codes) instead of importing `failure.js`'s (which has zero imports, so it's safe for the Mobile-portable `stage_strip.js` to depend on); `mr_history.js`'s `REASONS` table falls back to printing the bare `code` when it doesn't recognize one (`plainReason = (code) => REASONS[code] || code`). The `<details><summary>▸ Technical details</summary>` disclosure pattern already exists twice (`ProposalsSection.jsx:175`, `SupportTab.jsx:217`) — reused as-is, no new UI primitive invented.

**Simplicity:** one canonical `CODE_INFO` table added to `failure.js` (already the natural home — it already builds `REMEDIATION_BY_CODE` from `RULES`), covering every one of the ~30 real codes I enumerated via `rg` across `webhook-server/*.js` (RULES' 11 + `UI_EVIDENCE_UNCHECKED`/`NO_UI_EVIDENCE`/`IMAGES_UNPINNED`/`IMAGES_STALE` + `DECISIONS_UNCHECKED`/`DECISIONS_PENDING`/`DECISIONS_UNSTRUCTURED` + `CI_FAILED`/`CI_PENDING` + `NO_MERGE_PROFILE`/`ENV_MISSING`/`WRONG_BASE`/`SENT_BACK`/`MEMORY_PRESSURE`/`GATE_INFRA`/`MAIN_RED`/`MERGE_REFUSED`/`VERSION_BUMP_FAILED`/`GATE_TESTS_FAILED` + `ALREADY_MERGING`/`OUT_OF_ORDER`/`REBASE_CONFLICT`/`UNKNOWN`). The other two files stop duplicating and import it.

**Tokens:** spent up front reading 4 evidence files + their call sites + 6 existing test files to find the exact 30-code list and the exact IPC-serialization boundary (Electron's `ipcRenderer.invoke` only carries `.message` across, not custom `Error` props like `.payload` — confirmed via `cleanIpcError`/`handleApprove`'s catch in `MrReview.jsx:309-312`), so the design threads structured data through the channel that actually survives (`mergeOps`'s pushed plain-object state, not the thrown `Error`), avoiding a rebuild once that's discovered mid-implementation. No tokens spent on a new UI mechanism.

**Leaves the user more capable:** the owner (and whoever reads a merge failure next) understands *what happened and what to do* without clicking into logs, and the one place that genuinely wants more ("why exactly") still has it one click away, not deleted.

**Machine:** no preference — this is a pure dashboard/webhook-server JS change, run and tested wherever the worktree is (this Mac).

## What's actually breaking the acceptance criteria today (traced, not guessed)

1. **No disclosure at all, live approve path.** `prState.js:186-187` shows `describeApproveFailure`'s baked string (e.g. `"RATE_LIMITED at merging: GitHub rate limit. -- already retried 3 times; try again shortly. GitHub rate limit. Retried automatically..."`) as the card's entire detail text — `MrReview.jsx:378` renders it with a plain `<p>`, no `<details>`. **Violates "no code string visible without opening Technical details" directly.**
2. **Unknown code falls back to the bare code.** `mr_history.js:23`: `export const plainReason = (code) => REASONS[code] || code`. The existing test (`mr_history.test.js:89`) even locks this in: `['WHATEVER', 'WHATEVER']`. **This is the exact scenario named in "How we'll try to break it."**
3. **Tooltip falls back to raw, code-prefixed `detail`.** `StageStrip.jsx:34`: `!segment.cause && segment.detail && ...` — for a failed stage whose code isn't in `stage_strip.js`'s local (incomplete) `REMEDIATION_BY_CODE`, this shows the original string, which starts with the code.
4. **Three duplicated tables**, confirmed: `failure.js` RULES-derived `REMEDIATION_BY_CODE` (11 codes, server-side), `stage_strip.js`'s own `REMEDIATION_BY_CODE` (18 codes, hand-copied + extended), `mr_history.js`'s `REASONS` (14 codes, short labels, different wording for the same codes).

`failureResponse`/`refusal()` already deliver `remediation` to the client in the live JSON body — `approve_flow.js`'s `refused(err)` (lines 71-89) just throws away `err.payload.message`/`.remediation` and keeps only the pre-baked `err.message` when calling `mergeOps.fail/queue/waitMemory`. That's the actual fix point, not the server.

## Tests first

From the ticket's "How we'll try to break it" plus misuse the section didn't spell out:

1. **The named case** — a failure code `CODE_INFO` doesn't recognize anywhere it's looked up (`stage_strip.remediationFor`'s call site inside `deriveStageStrip`, `mr_history.plainReason`, and the live-approve render path) shows a generic plain sentence, never the bare code. Replaces/updates `mr_history.test.js:86-91`'s `['WHATEVER','WHATEVER']` case.
2. **Exhaustive coverage** — one test enumerating every real code found by `rg "refusal\('|code: '[A-Z_]+'"` across `webhook-server/` (the ~30-code list above) asserts `CODE_INFO[code]` exists with non-empty `label`, `remediation`, and a boolean `needsYou`. This is the literal "a test fails if any refusal code has no plain text" criterion — extends `stage_strip.test.js:163-184`'s two partial lists into one exhaustive one, sourced from the codebase, not hand-typed.
3. **No code string outside `<details>`** — a render test on the live-approve card (`MrReview.jsx`) for an `'error'`-kind view asserts the rendered text (everything *except* inside a `<details>`) never contains the raw code token, for at least one RULES code (`RATE_LIMITED`) and one inline-refusal code (`DECISIONS_PENDING`); the code string *is* found inside the `<details>` block.
4. **Empty/malformed payload** — `describeApproveFailure`/the new structured-parts function given `body = null`, `body = {}`, `body = {code: ''}`, `body.remediation` missing/undefined: never throws, never renders `undefined`/`null` as visible text, falls back to the generic sentence.
5. **A code unknown to `CODE_INFO` but present in a live payload** (future code added server-side before the client table catches up) — same generic-fallback behavior, not a crash, not the bare code.
6. **Dependency failing: the push never arrives** — `MrReview.jsx`'s `handleApprove` catch path (IPC strips `err.payload`, confirmed via `cleanIpcError`) must still show a sane headline/detail from `cleanIpcError(err)` alone, with `code`/`remediation` simply absent (no Technical details section rendered) rather than showing `undefined`.
7. **Repeats** — two consecutive failures with *different* codes on the same PR card don't leak the first failure's code/remediation into the second's Technical details (state must be cleared on each new `handleApprove`/pushed op, mirroring existing `errorMessage` reset at `MrReview.jsx:262` idle branch and `:263` approving branch).
8. **Stale state** — `IMAGES_STALE`'s existing re-verify-on-click behavior (`prState.js:179-184`) keeps working unchanged after code/remediation are added to its view object (it already has special-cased Approve-stays-enabled logic that must not regress).
9. **A person's mistake: the two existing locked-string tests must still pass unchanged** — `merge_failover.test.js:542` (`describeApproveFailure`'s exact baked string) and `stage_strip.test.js:7-33` (`extractCode`/`remediationFor` exact return values, including `remediationFor('UNKNOWN_CODE') === null`) are not touched; the new behavior is additive (new fields/functions), not a rewrite of the old ones, so a reviewer doesn't have to re-verify dozens of unrelated existing assertions.
10. **Concurrency/wrong order** — a merge-op `fail()`/`queue()`/`waitMemory()` call given a plain string (today's calling convention, used by ~40 existing call sites across `merge_ops.test.js`, `merge_failover.test.js`, etc.) still works exactly as before (back-compat shim: string in ⇒ `{message: str, code: null, remediation: null}`), so none of those existing tests need to change.
11. **Screenshots** — MR Review card showing a merge error, at 900px and 1440px, before/after, pinned to the PR (acceptance criterion #3), since the card's visible layout changes (new remediation line + Technical details disclosure).
