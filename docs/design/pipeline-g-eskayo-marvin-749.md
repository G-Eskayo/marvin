## North-star fit

**Reuses before adding anything new:**
- `disk_trim.py::_trim_swiftpm()` (lib/disk_trim.py:142) already treats `~/Library/Caches/SwiftPM` as a disposable-tier cache under ADR 0065 ("npm/pip/SwiftPM caches" are named explicitly as disposable). Pointing every `-clonedSourcePackagesDirPath` at that same folder means the shared cache needs **no new cleanup code** — `disk_trim.trim()` and `disk_ledger.measure_categories()`'s `rebuildable_caches` walk already cover it.
- `cleanup_sweep.py::decide_simulator`/`CAPTURE_SIM_RE` (lib/cleanup_sweep.py:552-553, 600-615) already recognizes `marvin-<hash>` capture devices and already protects Xcode's stock device-type names (`_default_stock_names()`). The fix is a behavior change inside this existing function (immediate-delete-when-shutdown → delete-when-unused-14-days), not a new mechanism.
- `fcntl.flock` + stage-then-atomic-rename, the exact concurrency-safety idiom `model_cache.py::ensure()` (lib/model_cache.py:147-158) already uses for clarity-captions' own model setup steps, is the right shape to point to if any new shared-state write needs locking — but Apple's own `-clonedSourcePackagesDirPath` is *designed* for exactly this (concurrent CI runners sharing one checkout folder) and does its own internal locking, so no new lock wrapper is added on top of it; that would be machinery for a problem the flag already solves.
- `evidence_capture.py::_with_build_folder` (lib/evidence_capture.py:318-327) already makes each screenshot build's DerivedData disposable (created in a temp dir, `shutil.rmtree`'d in `finally`). Only the missing `-clonedSourcePackagesDirPath` argument is added to the two `xcodebuild` calls inside it — the ephemeral-DerivedData pattern itself is untouched.

**Why this is the simplest sufficient approach:** the ticket is unusually explicit about the mechanism (`-clonedSourcePackagesDirPath`, reuse named devices, delete after 14 days unused). I'm not introducing a new abstraction (e.g. a `model_cache.py`-style symlinked checkout cache) where a literal shared-path argument already does the job and matches what the ticket asked for; see the scoping note below on where I'm deliberately *not* chasing a fancier fix.

**Where it saves/spends tokens:** spends a review-time budget now (this plan, implementation, and three separate repos' PRs) to remove a recurring manual-cleanup cost (`du`/`find` scans over ssh, the 2026-10-28 hand-cleanup) that has already recurred twice (#687, #765) — compounding leverage, not a one-off.

**Phone-OS direction:** indirect — this keeps the Mac mini (the only machine that builds iOS apps) usable, which every app-repo ticket depends on.

**More capable or more passive:** more capable — it removes a manual "go find what's eating disk" chore, it doesn't take a judgment call away from Gil (ADR 0065's three-tier rule already draws that line; this just applies it correctly to two more surfaces).

**Important scoping finding, stated plainly:** this ticket's three "What to build" bullets land in **three different GitHub repos plus one untracked machine-local folder**, not just this worktree:
1. `G-Eskayo/marvin` (this repo): `lib/evidence_capture.py`, `lib/cleanup_sweep.py`, `lib/simulator_capture.py`, `lib/purpose_metrics.py`, and their tests.
2. `~/.agents/instance/config/projects/clarity-captions.json` and `marvin-mobile.json` — **private instance data, gitignored (`.gitignore:53-54,101`), not part of any PR** (same distinction already documented in `docs/design/pipeline-g-eskayo-marvin-752.md:8`). These are hand-edited directly on disk; the marvin PR's body states what changed there and why, since no diff will show it.
3. `G-Eskayo/marvin-voice` (separate repo, own PR): `scripts/install.sh` + a new test script.
4. `G-Eskayo/clarity-captions` (separate repo, own PR): `scripts/release-mac.sh`.

I could not find a linked PR for either of the two prior failed automated attempts (`gh pr list --search 749` returns nothing), so I have no specific "must-fix" review comments to carry forward — only "code review found must-fix issues" / "mixed," with no detail. My best-supported guess, not a fact: a prior attempt likely stayed inside this worktree and either missed the cross-repo/instance-config pieces entirely, or got the simulator-reuse semantics wrong, since `lib/simulator_capture.py::capture_scenarios` currently **assumes the named device already exists** (`xcrun simctl boot <name>` with no `simctl create` anywhere in the file) and has an entire test file of stub (`pass`-bodied) tests — i.e. this module is scaffolding, not working code, which is the most load-bearing gap for the "reuse named devices" criterion.

**Deliberately out of scope, flagged rather than silently assumed fixed:** `-clonedSourcePackagesDirPath` is an `xcodebuild`-only flag. The plain `swift test`/`swift build` verify steps (`caption-core`, `marvin-core`, marvin-voice's `swift-test`) have no verified equivalent flag I can point to with confidence, and FluidAudio is a dependency of marvin-voice's SwiftPM package itself (confirmed on disk: `~/Developer/marvin-voice/.build/checkouts/FluidAudio` exists *separately* from `.build/xcode/SourcePackages/checkouts/FluidAudio`), so some duplication may persist on that path after this fix. I'm not inventing an unverified mechanism to paper over that; I'll say so in the PR and leave it as a named follow-up if the before/after measurement still shows it.

## Tests to write first

From "How we'll try to break it" plus the acceptance criteria's implied cases:

1. **Two concurrent builds share the cache, no corruption** — real-collaborator integration test (Xcode-gated, `skipif` on no Xcode, same pattern as `lib/tests/test_simulator_capture.py:243-249`): two `xcodebuild`/`swift package resolve` processes against a tiny fixture SwiftPM package with one small dependency, both pointed at the same `-clonedSourcePackagesDirPath`, run concurrently; both must succeed and the resulting checkout must be valid. Not mocked — mocking would hide exactly the SwiftPM locking behavior being tested (north star: "Verified, not assumed").
2. **Shared cache folder deleted mid-run** — same integration tier: `shutil.rmtree` the shared folder immediately before invoking the build, assert the build still succeeds (SwiftPM/Xcode recreate it) rather than erroring on a dangling path.
3. **A booted simulator is never deleted even if its last-used timestamp is old** — unit test on `cleanup_sweep.decide_simulator`: a `marvin-<hash>` device, `state="Booted"`, `last_booted_at` 20 days ago → `"keep"`.
4. **Xcode's/the owner's own devices are never touched** — existing `test_xcodes_own_devices_are_never_touched_even_though_their_names_end_in_numbers` (lib/tests/test_cleanup_sweep.py:447) must keep passing unchanged; add a case for a hand-named device that happens to match no pattern.
5. **Cleanup run twice is a no-op the second time** — unit test: `sweep_simulators()` called twice with the same input list and a `delete_simulator` stub; second call deletes nothing because the first already removed the stale entries (extends `test_the_sweep_deletes_only_what_it_decided_to_remove`, lib/cleanup_sweep.py:472).
6. **Replaces the now-wrong existing test**: `test_a_leftover_capture_simulator_is_removed_once_it_is_shut_down` (lib/tests/test_cleanup_sweep.py:458-460) encodes the *old* "delete immediately when shut down" rule. It must change to: shut-down + used 20 days ago → `"remove"`; shut-down + used 2 days ago → `"keep"`; booted regardless of age → `"keep"` (already covered by #3). This is a deliberate, named verify-fails-when-code-changes-without-test-changing case.
7. **Bad/empty/huge/malformed `lastBootedAt`** — missing field, unparsable string, a future timestamp (clock skew) → defensively `"keep"` (ADR 0065: unclear tier = more protected tier), never crash.
8. **`simulator_capture.capture_scenarios` creates the device when none exists, reuses it when one does** — unit tests (mocking `_simctl_run`): first call with no matching device issues a `simctl create`; second call with the same worktree/ticket (same deterministic name) and the device already present issues no `create`, only `boot`.
9. **Stale device from a previous run is reused idempotently** (fills in the existing stub `test_capture_scenarios_stale_device_idempotent`, lib/tests/test_simulator_capture.py:118-120): device exists but is in a weird/shutdown state from a prior crashed run → boot succeeds without a hang or a duplicate create.
10. **Concurrent `capture_scenarios` calls for two different tickets don't collide** (fills in the existing stub, line 114-116): two worktree paths → two distinct device names, verified independently created/booted.
11. **A person's or Xcode's own device existing under the exact hash name** — pathological but cheap to guard: if `_simctl_run(["boot", name])` fails with "unable to find device," fall back to create-then-boot once, not an infinite retry.
12. **`install.sh` success removes `.build/xcode`; failure keeps it** — new bash test script in `marvin-voice` (no existing bash-test convention there; this is a new, minimal primitive, not found elsewhere to reuse) stubbing `xcodegen`/`xcodebuild`/`codesign`/`security` on `PATH`: one run where the stub `xcodebuild` exits 0 → `.build/xcode` gone after; one run where it exits 1 → `.build/xcode` still present, script exits non-zero.
13. **`install.sh` run twice in a row is harmless** — same stub harness, run twice back-to-back, second run succeeds and still cleans up (idempotent).
14. **Permissions / stale state**: `evidence_capture.py`'s two `xcodebuild` calls get `-clonedSourcePackagesDirPath` asserted present in the constructed argv (unit test, mocked `run`, covers `_capture_ios` lib/evidence_capture.py:349-351 and `_capture_macos` lines 413-415) — a bad/missing shared-cache path must not be silently dropped from the command.
15. **Purpose-metric probe**: `purpose_metrics._days_under_disk_floor` (new, modeled on `_missing_model_failures`/`_marvin_verify_timeouts`, lib/purpose_metrics.py:318-365) — malformed JSON lines in the log are skipped not crashed; entries outside the 7-day window are excluded; two entries on the same calendar day under the floor count as **one** day, not two; a log that doesn't exist yet returns `0.0`.
16. **Repeats/wrong order**: `decide_simulator` and `decide_worktree` are pure functions already exercised with out-of-order/duplicate input lists in existing tests (`test_the_sweep_deletes_only_what_it_decided_to_remove`) — extend with a duplicate-name input to confirm no double-delete attempt.
