## North-star fit

**Reuses, before adding anything new:**
- `dashboard/webhook-server/copy_route.js` + `dashboard/electron/main/peer_copy.js` (marvin#1223) already implement exactly the "read local stamped copy, ask the producer once when stale, use the newer of the two, fail soft when the producer is unreachable" mechanism this ticket calls "every reader uses the hub's feed." Adding `github-feed` to `COPY_NAMES`/`COPY_PATHS` and stamping it with `lib/stamped.py`/`stamped.js` gets the laptop (and the Mini's own dashboard) reading the feed almost for free — this is most of acceptance criterion 1.
- `~/.agents/bin/gh` (the gh gate) is the one chokepoint every caller already passes through — Python (`subprocess.run(["gh", ...])` in `purpose_metrics.py`, `rework_status.py`, `owner_decisions.py`, `ticket_queue.py`), JS, and chat sessions alike. Gil's own comment 1 already names this: "a read-through cache in the gh gate." Extending the gate itself, rather than threading feed-awareness into five separate scripts, is the simplest sufficient form (Colton check) and is the only way the "chat sessions' read-only gh calls" requirement can be met without a new call site everywhere.
- `job_catalog.py` already has the exact "producer on one Mac, fallback on the other, skip while the producer is healthy" idiom, three times over (`daily-digest`/`daily-digest-fallback`, `morning-brief`/`-fallback`, `research-colony`/`-fallback`). This is what "one producer per job, not one per machine" (comment 1) is asking for — reuse the idiom for `ticket-queue` and any duplicated health-check scanning, don't invent a new placement mechanism.
- ADR 0081 ("Macs look after each other") already defines trigger-based peer watching (Tailscale IPN bus peer change, boot "I'm back", stale-heartbeat-noticed-at-end-of-sync-run), a `classify()` → fix-ladder pattern, and "a lock per watched Mac stops two watchers acting at once." The hub watcher/reporting agent in this ticket is the same shape of problem (who's responsible for a role, handed over on failure, reported once) — reuse its trigger list and lock idea rather than building a new polling watcher.
- ADR 0069/0082's pattern (no credential ever stored on the box; it only relays through a Mac's existing login/credential) is the one already governing exactly this machine for exactly this reason. The box-hub-credential Decision was already answered by Gil (2026-11-10, comment 3): **no credential on the box; it relays through the laptop's gate.** This plan implements that, it does not reopen it.
- `copy_route.js`'s `allowedPeerAddress` (loopback/Tailscale-range check) is reused for the relay endpoint's transport-level gate, but — flagged below as a real gap — it only proves "some Tailscale peer," not "the registered box specifically." The relay needs the latter (it's credential-proxying, unlike `/copy`), so it must also check the caller's Tailscale hostname against the registry's box entry, the same lookup `pull_only_node`/`device_identity.js` already do to recognize "this is the box."
- `lib/stamped.py` (marvin#1223 envelope: `host`, `generated_at`, `alive_at`, `tolerance_s`) is reused for the hub-claim file and the per-caller budget file, instead of inventing a new freshness format.

**Simplest sufficient approach:** no new cross-machine consensus system, no new polling loop, no new credential anywhere. One gate (`bin/gh`) grows a feed-aware read-through cache; one existing peer-copy mechanism gains a fourth file; one existing fallback-job idiom gets two more entries; one existing ADR-0081-shaped watcher gets a new role to track (hub) instead of a new watcher process.

**Tokens/compute:** this spends design complexity once (hub election, relay) to cut ~40,600 GitHub calls/day fleet-wide by ≥80% — a north-star-1 win by a wide margin, and it is the kind of work north star 4 favors (it makes every future GitHub-reading tool cheaper, not just today's five callers).

**Machine:** the gate change lands in the shared `~/.agents` repo (every machine already runs it). The hub role defaults to the Mini (ADR 0032's existing primary-host pick), consistent with "the always-on machine."

**User impact:** purely infrastructural — Gil sees the same dashboard, same freshness, fewer rate-limit stalls. Nothing here changes what a person does; it removes an annoyance ("the API issue is becoming tiresome"), which is squarely north star 1/5's job, not a capability trade-off against north star 3.

**Gap this plan surfaces, not invented by it:** `device_identity.js`'s `primaryDeviceId()`/`isPrimaryHost()` picks the first `kind: "desktop"` registry entry — today that's a static pick, not an electable role. There is **no existing failover/election mechanism for this role at all.** The hub-claim file + priority-ordered claiming below is genuinely new code, not a relabeling of something that exists. That is the one piece of this ticket that can't be reduced to "reuse X."

## Why no Decisions section

The one open choice the ticket raised (`box-hub-credential`) was already answered by Gil on 2026-11-10 (comment 3): no credential on the box; it relays reads through the laptop's gate over Tailscale, authenticated by Tailscale identity, nothing secret sent to the box. Nothing else in the ticket or this design requires an owner pick between options — the remaining parameters (tolerance seconds, budget shares) are implementation defaults I'm setting from existing convention, noted inline below, not forks the owner needs to choose between.

**Defaults I'm picking, and why:** hub-staleness tolerance = 600 s, matching `github_feed.js`'s existing `STALE_MS` (10 min) rather than inventing a second number for the same kind of judgment. Per-caller budget shares are log-only (Vitals shows overshoot; nothing is blocked) — consistent with the gate's existing fail-open philosophy (an unreadable budget never stalls dispatch, `dispatch_concurrency.py`'s `_safe`) and with the fact that this ticket's hard floor (`BUDGET_FLOOR`, background calls wait below 20% hourly allowance) already exists and isn't being changed.

## Tests first

One per "How we'll try to break it" item, one per Attack/decision-driven scenario from the comments, plus misuse the section didn't name.

**From "How we'll try to break it":**
1. Mini stopped (simulated: hub-claim file past tolerance, no heartbeat) → the box claims hub within one tolerance window, reads route through the laptop relay, labelled "direct, Mini unreachable" is **not** shown (feed-backed reads still say "from the box, as of..."); only a true all-hubs-down path shows "direct, no hub."
2. A feed older than `STALE_MS`/`tolerance_s` is never served as current — `feedStatus`/gate cache must mark it stale and either refetch (if this machine can) or show the stale label; a test asserts the gate never returns cached data past tolerance without the stale flag.
3. A burst of 50 near-simultaneous change pings for the same repo coalesces to one read in flight (reuses `github_feed_writer.js`'s existing `inflight` coalescing — test that it still holds when the pinger is the new multi-reader-aware watch, not just the single Mini case).

**From the widened-scope and redundancy-chain comments (comment 1, 2, 3):**
4. Fleet-wide `gh-calls.jsonl` count across both Macs for a replayed day drops ≥80% from ~40,600 (a fixture of a day's recorded reads replayed through the new gate cache vs. the old pass-through).
5. The same day's load differs <10% between "owner on laptop" and "owner on Mini" replays (two fixtures, same call pattern, different originating machine) — proves the fix isn't laptop-specific.
6. Hub failover end-to-end: Mini down → box is hub inside one tolerance; box's relay also down (laptop unreachable) → laptop becomes hub directly; all three down → every machine falls back to budgeted direct calls, each transition logged exactly once (not re-logged on every subsequent check).
7. Two watchers racing to claim hub at once (simulated concurrent claim attempts under a network split) never produce two machines both believing they're hub — the claim file's lock/lease must make this exclusive.
8. Flapping: more than 3 hand-overs in an hour holds at the lower hub and alerts instead of bouncing (direct port of ADR 0081's existing flap rule to this new watched role).
9. Role moves back up the chain when the Mini returns, and that hand-back is itself reported once.
10. The box's environment and disk hold no GitHub token at any point, including mid-relay (grep the box's env/files in the test, not just "the code doesn't read one" — a planted token from an unrelated process must not get picked up either).
11. The relay refuses a write command (`gh pr merge`, `gh issue edit`, etc.) from the box even with a syntactically valid-looking read-shaped request (argument-smuggling attempt: a `pr list` call with an embedded `--` or body flag that resolves to a mutating API path) — reuses `decisions_check.py`/`pr_ticket_check.py`'s existing "gate inspects argv, not trusts the caller's label" posture.
12. A Tailscale peer that is **not** the registered box (wrong hostname/no registry entry) hits the relay endpoint and is refused — this is the gap flagged above; `allowedPeerAddress`'s IP-range check alone must not be treated as sufficient identity proof for a credential-proxying endpoint.
13. Laptop asleep when the box's relay request arrives: the box queues the pending read; the laptop's wake/login/network-up announcement (ADR 0081's existing triggers) resumes the queued read within seconds with zero polling in between (assert no timer fires between the queue and the wake event).
14. A lost wake announcement is caught by backoff (1→2→4→8→...→30 min cap); one successful contact resets the backoff to the first interval again.
15. `ticket_queue.py` makes zero `gh` calls for a repo whose `updatedAt`/ETag hasn't changed since the last pass (fake `gh` records call count; ticket-queue test already implied by the ticket, point it at the new gate-cache path, not a bespoke cache inside `ticket_queue.py` itself, since the gate is now the cache).
16. Dashboard views are never staler than today after the change: a change ping still reaches a viewer within ~20 s end-to-end (feed write → peer-copy fetch → render), on the laptop and the box both.

**Misuse not named in the ticket:**
17. Malformed/truncated `github-feed.json` (half-written, truncated mid-JSON) read by a peer mid-write — the atomic temp-file-rename already in `github_feed_writer.js`/`peer_copy.js` must still hold when a third reader (the gate itself) is added; test a reader sampling during a simulated partial write never sees garbage (it sees old-or-new, never half, matching the existing contract).
18. The gate's feed cache asked for fields the feed doesn't carry (e.g., `gh pr list --json reviews` when the feed only stores the `prListArgs` field set) — must fall through to a real call, never silently return a response missing requested fields.
19. Repeated identical hub-claim attempts from the same machine (a flapping local process, not a real handover) must not count as hand-overs for the flap rule (dedupe by current-hub-unchanged).
20. Wrong permissions: a non-owner identity (a stray CI credential, a forked PR's workflow) hitting the relay or the `/copy/github-feed` route is refused the same as any other untrusted caller — covered by existing `allowedPeerAddress`/registry-hostname checks, tested explicitly for this new route rather than assumed inherited.
21. Concurrency: two local processes on the box both wanting a relayed read at the same moment must not double-queue or double-wake the laptop (one outstanding relay request per box, coalesced, mirroring `github_feed_writer.js`'s existing per-repo `inflight` coalescing).
22. Stale state: a hub-claim file left over from a previous, now-dead process (crash, not clean handover) must expire by its own lease/tolerance rather than wedging the claim forever — test a claim with no heartbeat past tolerance is reclaimable by anyone, including the original claimant restarting.
23. A person's mistake: `config/gh_budget.json` edited by hand into an invalid shape — falls back to defaults field-by-field (the `dispatch_concurrency.load`/`validate` pattern), never a crash, never a silent full-budget bypass.

2. **Laptop (and Mini's own dashboard) read the feed through `peer_copy.js`'s existing read-through cache**, instead of `mr_repos.js`/`boards.js` calling `gh` directly, whenever the current machine is not producing the feed itself. Wire `createFeedSource`'s consumers to go through `createPeerCopies().read('github-feed', ...)` first; keep today's direct-`gh` path as the "producer host" branch (the hub still reads GitHub itself) and as the last-resort fallback when the peer is unreachable past tolerance (labelled, never silently, per `FeedError`'s existing convention).
3. **Build the hub-claim mechanism.** New `lib/github_hub.py` (+ JS twin only if a dashboard-side read needs it directly — check first whether the gate alone covers every JS/Python caller before duplicating): a stamped claim file (`~/.claude/github-hub.json`, `stamped.py`) naming the current hub, since-when, and a lease. Priority order Mini → box (relay via laptop) → laptop → direct, matching ADR 0069/0081's existing "deterministic order beats true consensus" style. Claim/renew/expire logic with a lock (reuse `fcntl.flock`-over-a-lockfile the way `bin/gh`'s own `_State`/`_background_slot` already do it, extended across machines via the same stamped-copy read every watcher already polls on trigger, not on a timer).

Accepts only a closed allowlist of read-shaped `gh` argv (mirrors `pull_only_refusal`'s existing argv-prefix style), runs it through the laptop's own gate (so it's still budgeted/logged as a relay-caller), refuses anything else including disguised writes.
