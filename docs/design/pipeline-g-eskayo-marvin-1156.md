## North-star fit

**Reuses, before adding anything new:** the exact `fcntl.flock`-guarded idiom already used twice in `lib/` for this same shape of problem — `lib/model_cache.py:ensure` (`with open(model_dir / ".lock", "a") as lock: fcntl.flock(lock, fcntl.LOCK_EX)` around a fetch-into-shared-cache step, lines 147–148) and `lib/test_slot.py:slot`/`_wait_no_merge` (mkdir-parents-then-open-append-then-flock, same release-on-close pattern). `chroma_onnx_lock.protect()` applies that identical idiom, but has to do it by monkeypatching a method on a third-party class rather than calling a MARVIN helper directly, because the race lives inside `chromadb`'s own `ONNXMiniLM_L6_V2._download_model_if_not_exists` — confirmed by reading the installed source at `~/.agents/venv/lib/python3.11/site-packages/chromadb/utils/embedding_functions/onnx_mini_lm_l6_v2.py`, not MARVIN code, so it can't be edited directly. Wrapping it once at import time mirrors how `conftest.py` already patches around other third-party/external surfaces it doesn't own (`_no_real_github`, `_no_real_claude`).

**Why this is the simplest sufficient approach:** one ~20-line module (`protect(cls)`), one `try/except ImportError` wiring line in the existing repo-root `conftest.py` (already the single place that does "repo-wide test isolation"), zero changes to the two victim test files. No new dependency — `fcntl` is already used by `test_slot.py` and `model_cache.py`.

**Where it saves/spends tokens:** near-zero ongoing runtime cost — the lock is only ever contended in the narrow first-download window; once the model is cached, `_download_model_if_not_exists`'s own `onnx_files_exist` check short-circuits and every later caller's lock hold is a no-op. It spends a small one-time cost now to stop a recurring, expensive failure mode: this ticket's own comment thread shows **five dead retries** (a timeout, then four "model service unavailable" bounces) before this attempt even started, each one a full planner/executor model session — all because a latent race, not a logic bug, keeps tripping CI.

**Root cause, concretely:** `DOWNLOAD_PATH = Path.home() / ".cache" / "chroma" / "onnx_models" / MODEL_NAME` is a class attribute. `make_test_home` (`lib/real_home_guard.py`) gives each pytest-xdist worker process its own `TEST_HOME`, but symlinks `.cache` straight through to the **one real** `~/.cache`. So every worker's `ONNXMiniLM_L6_V2` ends up pointed at the same shared `onnx.tar.gz`. `_download_model_if_not_exists` is an uncoordinated instance method: two workers can both decide the archive is missing, both call `self._download(...)` against the same path, and one worker's `open(fname, "wb")` (truncate-on-write) or its own `os.remove(fname)` on a SHA mismatch races the other's `_verify_sha256(fname, ...)` — exactly the `FileNotFoundError: .../onnx.tar.gz` seen in the three failures. This has been latent since the shared-`.cache` symlink was introduced (`real_home_guard.py`, well before this run) — it is not something the merge at `cc830481` (an unrelated "Site: In progress status" change) introduced, so **this is a fix-forward, not a revert**; there is no single breaking merge to revert.

**More capable, not more passive:** fixing the latent race (instead of skipping, deleting, or widening anything in the two victim test files) keeps the exact same safety net Gil already has, it just stops it from blocking every other PR intermittently.

## Tests I will write first (`lib/tests/test_chroma_onnx_lock.py`, red before `lib/chroma_onnx_lock.py` exists)

All against the **real** `chromadb.utils.embedding_functions.onnx_mini_lm_l6_v2.ONNXMiniLM_L6_V2` class (a fresh dynamic subclass per test so monkeypatches never leak across tests or into the shared process-wide class), `DOWNLOAD_PATH` pointed at `tmp_path`, with only the network leaf (`_download`'s `httpx.stream` call) replaced by a fast local write of real bytes whose SHA256 is computed and set as `_MODEL_SHA256` — everything else (`_download_model_if_not_exists`, `_verify_sha256`, the exists-check, the tarfile extraction) runs for real, matching `lib/tests/test_model_cache.py`'s own convention of a deterministic `sleep`-forced overlap between two `threading.Thread`s rather than probabilistic repetition:

3. **`test_protect_downloads_only_once_across_concurrent_callers`** — `_download` call-count instrumented; with `protect()` applied, concurrent callers trigger at most one real download, the rest short-circuit on `onnx_files_exist`.
4. **`test_protect_is_idempotent`** — calling `protect(cls)` twice wraps only once (marker attribute check); a third concurrent trial behaves identically to a single wrap. *(Misuse: repeated calls / wrong order — `protect()` could plausibly be invoked from more than one place.)*
5. **`test_protect_noops_when_download_path_attribute_is_missing`** — a stub class with no `DOWNLOAD_PATH` (future chromadb renaming it) passed to `protect()`; asserts no exception and the method is left untouched. *(Misuse: a dependency's shape changing underneath MARVIN.)*
6. **`test_protect_noops_when_download_method_is_missing`** — same defensive case for a class with `DOWNLOAD_PATH` but no `_download_model_if_not_exists`; no exception.
7. **`test_protect_propagates_the_original_exception`** — a forced genuine failure (bad SHA256, or an `OSError` writing the lock directory under a read-only `tmp_path`) still raises out of the wrapper — the lock never swallows a real failure. *(Misuse: "each dependency failing," "wrong permissions.")*
8. **`test_protect_releases_the_lock_after_an_exception_so_a_later_call_can_proceed`** — companion to 7: after one call raises, a fresh call in the same process succeeds and does not hang — proves the `finally`-released `flock`. *(Misuse: "stale state" — a crashed holder must not deadlock everyone else.)*
9. **`test_lock_file_is_created_next_to_download_path_not_inside_it`** — the lock file lives at `DOWNLOAD_PATH.parent/.{DOWNLOAD_PATH.name}.lock`, created with `mkdir(parents=True)`, and never appears inside `DOWNLOAD_PATH` itself — so it can never be swept into the tarfile extraction or counted among the six `onnx_files`. *(Misuse: "a person's mistakes" — an accidental file landing where the exists-check looks.)*
