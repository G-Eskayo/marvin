## North-star fit

**Reuses:** `lib/test_slot.py`'s existing cross-process file-lock pattern (`_open()` + `fcntl.flock(fh, fcntl.LOCK_EX)` / `LOCK_UN`, `lib/test_slot.py:70-91`) — the only other place in this repo serializes concurrent pytest-xdist workers via a flock on a file beside the resource being guarded. The new module applies the identical pattern to a different resource (the ONNX model cache) instead of inventing a new locking primitive. `lib/real_home_guard.py:64` (`make_test_home`) and `conftest.py:46-52` are read, not changed in shape — I'm adding one wiring call between two existing lines, matching how `conftest.py` already wires `real_home_guard`/`test_slot` at module scope.

**Simplest sufficient approach:** confirmed root cause by reading `chromadb==1.5.9`'s actual `ONNXMiniLM_L6_V2._download_model_if_not_exists`/`_download` (installed at `~/.agents/venv/lib/python3.12/site-packages/chromadb/utils/embedding_functions/onnx_mini_lm_l6_v2.py:98-123,281-322`) — it does no locking at all. Every pytest worker's test `HOME` symlinks `.cache` straight to the *real* `~/.cache` (`real_home_guard.make_test_home`, since `.cache` isn't a `.claude*` name it gets a plain symlink), so under `pytest-xdist` every worker race-downloads into the literal same `~/.cache/chroma/onnx_models/all-MiniLM-L6-v2/onnx.tar.gz`. One worker's `_download` fails its own post-write SHA-256 check (corrupted by a concurrent write to the same path), deletes the file in its cleanup branch, and reraises `ValueError`; a sibling worker that's mid-`_verify_sha256` on the same path gets `FileNotFoundError` — exactly the CI traceback. A single process-wide `flock` around the whole method is sufficient: it doesn't need to understand chromadb's internals, because once a second worker gets the lock, chromadb's own "are the extracted files already there?" check short-circuits before it ever touches the archive. No alternative (widening a retry, catching-and-ignoring `FileNotFoundError`, serializing CI to one worker) is simpler *and* keeps full test parallelism — the ticket itself rules out hiding the failure.

**Not a revert:** `cc830481`/`689df677` (the commit CI flagged) is the site "In progress" status PR — unrelated to Python or chromadb. `git log` on `conftest.py`/`test_slot.py`/CI config shows `da7507c0`/`8aa90861` ("CI runs the Python suite in parallel... Parallel pytest from the selector's own command line", #826) made CI run the suite under `pytest-xdist` for the first time; this race has likely always been latent in `real_home_guard`'s shared `.cache` symlink and only became reliably triggerable once CI itself went parallel. There is no single breaking merge to revert — fix-forward is correct and small.

**Tokens:** spends a small one-time read/design budget (confirmed against the real installed `chromadb` source rather than guessing); saves tokens going forward because every future full-suite CI run (and every local parallel run) stops burning a run + a ticket cycle on this flake.

**User capability:** fixes CI infrastructure invisible to Gil's daily work; it unblocks the merge gate (currently refusing every PR with `MAIN_RED`) without him having to notice or intervene — net more capable, not more passive, since nothing he'd otherwise do by hand is being taken over.

**Reattempt context:** this ticket was attempted once before in this same ticket slot; that attempt's code review found `test_1_reproduce_original_race_unprotected` never called `protect()` and so proved nothing about the fix. The test list below replaces that test with two explicit tests (#1 unprotected/#2 protected-same-scenario) so the "before" and "after" of the exact bug shape are both asserted, plus a cross-process test (#3) since `pytest-xdist` workers are separate OS processes, not threads — a `threading.Lock`-based "fix" would pass thread-only tests and still fail in real CI.

## Tests first (red before `lib/chroma_onnx_lock.py` exists)

All in new `lib/tests/test_chroma_onnx_lock.py`, against a stub class shaped like `ONNXMiniLM_L6_V2` (own `DOWNLOAD_PATH`, own `_download_model_if_not_exists`) so no test needs real network access, plus one integration test against the real chromadb class:

1. **`test_unprotected_overlap_reproduces_the_race`** — two threads call the *unwrapped* stub method; deterministic `threading.Event` handshake (no `sleep`-based timing) forces the second call to start while the first is still inside the body. Asserts it raises `FileNotFoundError`, reproducing the CI bug's shape without `protect()` involved.
2. **`test_protect_prevents_the_race_on_the_same_scenario`** — identical forced-overlap harness as #1, but `protect(StubClass)` is applied first. Asserts *neither* call raises, `calls == 2`, and — via an ordered shared log both calls append to — that the second call's body only starts after the first call's body finished. This is the test the prior attempt's review found missing: it must prove serialization, not just absence of an exception by luck.
3. **`test_protect_works_across_real_processes`** — spawns two real child processes (not threads, since `pytest-xdist` workers are OS processes) that both call the protected stub method against a shared `DOWNLOAD_PATH`; asserts neither raises. Guards specifically against a `threading.Lock`-based fix that would pass #1/#2 but fail in real parallel CI.
4. **`test_protect_is_idempotent`** — calling `protect(cls)` twice doesn't double-wrap (no nested-flock deadlock on a single call; the marker attribute is set exactly once).
5. **`test_protect_noops_when_method_missing`** — `protect()` on a class without `_download_model_if_not_exists` doesn't raise and leaves the class unmodified (per the ticket's stated contract).
6. **`test_protect_propagates_the_wrapped_exception`** — stub body raises a distinct exception (simulating a genuine download failure, e.g. a real corrupted-download `ValueError`); the wrapped call re-raises it unchanged, not swallowed.
7. **`test_lock_released_after_an_exception_so_the_next_call_is_not_blocked`** — after #6's failure, a second call (bounded `join(timeout=...)`) completes rather than hanging, proving the `finally`-unlock runs on the exception path too (a person's mistake: a crash mid-download must not wedge every future CI run).
8. **`test_protect_calls_through_every_time_not_just_once`** — two sequential (non-concurrent) protected calls both invoke the underlying method; `protect()` is a mutex, not a memoizing cache (chromadb's own exists-check stays the only thing deciding whether to actually download).
9. **`test_lock_file_created_when_parent_cache_dir_does_not_exist_yet`** — a from-scratch cache dir (no `.cache/chroma/...` at all, matching a brand-new machine or test) doesn't raise when the lock file's parent has to be created first (stale/missing state).
10. **`test_conftest_wires_protect_onto_the_real_onnx_class`** — `pytest.importorskip("chromadb")`; imports `ONNXMiniLM_L6_V2` and asserts it carries `protect()`'s marker attribute after the suite's own root `conftest.py` has run its module-level setup — the one integration check that the wiring (not just the module) actually took effect end to end.

Verify fails if any of these are later skipped, deleted, or weakened (e.g. a widened timeout masking a real deadlock) without an equivalent replacement.
