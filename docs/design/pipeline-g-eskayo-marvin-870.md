## North-star fit

**Reuses:** `lib/cleanup_sweep.py`'s `trim_pytest_temps()` (built for marvin#866, same symptom — 4.9 GB of stuck `pytest-of-<user>/pytest-N` dirs) stays exactly as-is as the daily backstop; I extend only its basetemp-name recognition (`PYTEST_BASETEMP_RE`, line 81) rather than writing a second trimmer. The root fix reuses pytest's own public `--basetemp` option instead of fighting its internal lock/retention machinery, and reuses the existing "wrap the subprocess.run call in try/finally" shape already present at every one of these call sites (`main_health._run_suite_in_slot`'s worktree-removal `finally`, `mutation_check._run_tests`'s `except TimeoutExpired`, etc.) — no new control-flow pattern, just one more thing cleaned up in each existing `finally`/`except`.

**Why this is the simplest sufficient fix:** I read pytest's own `_pytest/tmpdir.py` and `_pytest/pathlib.py` (installed at `~/.agents/venv`). Its "keep last 3" retention only runs at a session's *normal* finish (`atexit`/`ExitStack.close()` → `cleanup_numbered_dir`), and a directory is only a cleanup candidate if its `.lock` file is either absent or older than `LOCK_TIMEOUT` (**3 days**, hard-coded). Every pytest-running call site here (`lib/main_health.py:84`, `lib/affected_tests.py` via `.github/run-check.sh`'s `timeout_s`, `lib/mutation_check.py:160`, `lib/auto_merge_regression.py:76`, `lib/conflict_repair.py`, `lib/rule_checks.py:127`) wraps pytest in a `subprocess.run(..., timeout=N)`, which sends **SIGKILL** on expiry — the child never reaches `atexit`, so its `.lock` is never removed and that basetemp becomes *permanently* "in use" for 3 days, no matter how many clean runs happen after it. That's the literal "something defeats pytest's own last-3" the ticket asks me to find; a once-daily cron sweep (the #866 fix) only bounds the damage to "at most a day's worth," which is why a busy pipeline still filled the disk. I considered just calling `trim_pytest_temps()` more often instead of this — rejected: it's mtime-gated (1h) by design to protect live concurrent runs, so it can't give an *exact* "no leftovers" guarantee right after a kill, only a bounded one. The simpler, exact fix is to stop depending on pytest's internal retention for these known, controlled call sites at all: each gets its own disposable, pre-named `--basetemp` (a fresh path under the same `pytest-of-<user>` root pytest itself would use, never colliding across concurrent worktrees because each path is unique), removed unconditionally in the same `finally`/`except` that's already there. Zero reliance on lock staleness, zero reliance on cron cadence. I checked this doesn't collide with the worktree-dirty sweep (`cleanup_sweep.decide_worktree`, which refuses a plain `git worktree remove` if `git status --porcelain` is non-empty): the basetemp lives purely under `$TMPDIR`, never inside a git worktree, same reason `-p no:cacheprovider` is already passed everywhere to keep `.pytest_cache` out of worktrees.

**Tokens/compute:** no new subprocess, no new scan, no new background job — a few extra lines at existing call sites (`tempfile`/`uuid`-level cost) replace the current dependence on a 3-day-locked, heuristic retention path. The only recurring cost (the daily `trim_pytest_temps` walk+lsof) is unchanged; I only widen one regex it already evaluates.

**Capability:** this is pure infrastructure hygiene — it doesn't change what any human does, it stops a disk-fill from silently blocking *every* command on a Mac again (north star 2's reliability precondition: "nothing may break silently"). No tradeoff against north star 3.

## Root-cause summary (for the record)

1. A pytest run killed by any of these call sites' own `timeout=` (SIGKILL) never removes its basetemp's `.lock` file, so pytest's built-in "keep 3" cleanup skips it for 3 days — the actual mechanism that "defeats" retention.
2. The only existing backstop (`cleanup_sweep.trim_pytest_temps`, #866) runs once a day (`config/jobs/cleanup-sweep.json`), too slow for "ten runs in a row" to self-bound.
3. "xdist workers" and "the test HOME in conftest.py" (the ticket's other two suspects): xdist workers share one basetemp set by the controller (not a source of fragmentation), and `lib/tests/conftest.py`/`conftest.py` change `$HOME`, not `$USER`/`$LOGNAME`/`$TMPDIR` — `getpass.getuser()` and `tempfile.gettempdir()` don't read `$HOME`, so this one isn't the actual driver. I'm not building anything to "fix" either of these since they aren't the real cause; the plan below removes the dependency on pytest's basetemp-naming/user/lock logic entirely for the named call sites, which moots both suspects regardless.

## Tests (write first)

From "How we'll try to break it" plus the standard misuse list:

1. **Parallel runs from two worktrees at once** — two concurrent invocations of the same call site each get a distinct disposable basetemp (no shared path, no collision), and each cleans up only its own.
2. **A run killed by the gate's time limit** — simulate `subprocess.TimeoutExpired`/a hard-killed child at each wrapped call site; assert the disposable basetemp is gone immediately after the call returns (not after an hour, not after a day).
3. **xdist and serial runs mixed** — a real `-n auto` run and a real serial run through the same call site back-to-back; assert `tmp_path` fixtures resolve under the passed `--basetemp` in both, and nothing is left behind by either.
4. **Normal pass** and **normal fail** (non-zero exit, no kill) — basetemp removed in both; cleanup must not be conditional on pytest's exit code.
5. **"Ten runs in a row"** — the literal AC1: loop the new disposable-basetemp helper (and, once, a real small pytest subprocess through one call site) 10 times; assert at most the current run's own temp ever exists under the owner dir — i.e. 0 left behind after each, trivially ≤ 3.
6. **Stale state** — the owner dir (`pytest-of-<user>`) doesn't exist yet (fresh machine): helper creates it (`parents=True`) without error.
7. **Wrong permissions** — owner dir exists but isn't writable: helper raises loudly rather than silently falling back to pytest's own (broken) default basetemp behavior, so the fix can't be silently defeated the same way again.
8. **A person's mistake / bad input** — a pre-existing directory already sitting at the generated disposable path (name collision): tolerated, because pytest's own `getbasetemp()` already `rm_rf`s a given basetemp that exists before reusing it — test asserts this doesn't raise.
9. **Regex-widening regression** (extends `lib/tests/test_cleanup_sweep.py`'s existing basetemp tests, ~line 920-1050): a leftover disposable-named dir (simulating "the parent process itself was hard-killed before its own `finally` ran") is picked up by `trim_pytest_temps()` once old and unopened — same as the existing `pytest-<N>` cases already tested. Add a negative case: an unrelated directory name (e.g. `pytest-cache-v1`) must still be left alone, so the widened regex doesn't start matching things it shouldn't.
10. **No regression on existing argv-shape tests** — `lib/tests/test_affected_tests.py`'s `argv[-3:]`/`argv[-5:]` tail assertions on `affected_tests.plan()` must still pass unchanged; this dictates that the basetemp flag is added at `main()`'s subprocess.run call, never inside `plan()`. Same care needed for any equivalent exact-argv assertions in `test_conflict_repair.py`, `test_mutation_check.py`/mutation-check tests, `test_auto_merge_regression.py`, `test_rule_checks.py`, `test_build_type_measure.py` — check each before editing its module.
11. **Concurrency with the existing test-slot** (`lib/test_slot.py`) — a "heavy" run that holds the slot and a concurrent "light" run that's exempt must not fight over a basetemp path (satisfied structurally, since paths are always unique — test asserts this explicitly for one such pairing).

No owner decision needed here — the fix (exact disposable `--basetemp` per invocation, cron sweep kept as unchanged backstop) is the only approach I found that satisfies both acceptance criteria exactly, not just probabilistically, and I can justify it fully from the pytest internals above.
