## North-star fit

**Reuses before adding anything:** the entire data layer already exists and is further along than the ticket implies — `lib/ticket_stages.py` / `dashboard/webhook-server/ticket_stages.js` already write the full stage timeline (#216's project-keyed files), `dashboard/electron/main/activity.js` (`getTicketTimeline`, wired to IPC as `window.api.activity.timeline`) already serves it to the renderer, `ProjectBoard.jsx` already has a working vertical `PipelineHistory` component plus a `STAGE_LABEL`/`money`/`when` set of helpers, `mr_review.js`'s `listPipelinePrs` already computes every live PR blocker (`checks`, `conflicts`, `sentBack`, `rework`, `waitingOn`, `baseProblem`, `rebase`), `ActivityBoard.jsx` already has a reusable `formatElapsed`, and `board.js`/`boards.js` already compute a correctly-scoped, local-machine-only `isLive`/`liveNumbers` signal with the exact asymmetric usage pattern ("never infer running from a stale claim label") this ticket needs. **This ticket adds one new pure derivation module and one new presentational component on top of that, nothing else.** PR #368 (the previous 7 failed attempts on this same ticket, still open, never merged) duplicated some of this instead of reusing it, which is almost certainly why it kept failing verification/mutation checks — this plan deliberately does not repeat that.

**Simplest sufficient approach:** one pure function (`deriveStageStrip`) that turns `{events, liveOverlay?}` into an ordered list of display segments, used by both a React presentational component (dashboard now) and — unchanged — by a future native/mobile renderer later, per the ticket's own "same component... in MARVIN Mobile's Dashboard later." No new storage, no new IPC channel for ticket cards (the existing `activity:timeline` channel is reused), no new polling loop (existing trigger/refresh wiring is reused).

**Token cost:** spends a modest one-time budget writing ~2 new files + several small, surgical edits to existing ones (no rewrites); saves on every future "where did this PR/ticket get stuck" investigation, which today still requires SSH + log archaeology per Gil's own problem statement — directly hits the "retry storms were ~70% of output tokens" motivation in `docs/plans/pipeline-visibility-2026-10-07.md`.

**More capable, not more passive:** this is pure visibility, not automation — it does not act on Gil's behalf, it lets him see and decide faster (stalled vs running, who's blocking what) exactly where he said he currently can't. No north star argues against building it.

**Ticket's own stated fit:** the ticket doesn't state a north-star fit itself, so nothing to correct there. But its design-doc parent (`docs/plans/pipeline-visibility-2026-10-07.md`) does claim "one shared pipeline... stages generic... visuals derived from stage logs, never stored separately" — confirmed true and still the right frame against the current code.

## Tests to write first

The ticket has no "How we'll try to break it" section (and no Attacks list) — the triage bot flagged this ticket as missing a "What to build" section too, but a concrete "Solution" + ACs plus seven rounds of real owner feedback in the comments give enough to build from, so this isn't the "too vague" case; it means I derive the break-it list myself from first principles plus every concrete failure Gil already reported live.

1. **Empty/no history** — a ticket with zero stage-log events (new, pre-claim) renders a strip of all-"pending" segments, not a crash or empty render.
2. **Malformed/legacy data** — a stage file that is truncated JSON, or a pre-#216 bare-number legacy file — `readStages` already fails soft to `[]`; the derivation function must also tolerate an event missing `timestamp`/`machine`/`detail`/`cost_usd` (old schema) without throwing.
3. **Huge history** — a ticket sent back and rebuilt many times (exactly PR #368's real case: dozens of `merging failed` + re-queue events) collapses to one segment per stage showing only the *latest* status for that stage, not one pill per historical attempt.
4. **Every status per stage**: passed, failed (with message+remediation), running (animated, with elapsed time via the existing `formatElapsed`), stalled (no event for N minutes — see Decisions), skipped (greyed), and genuinely unknown/unrecognized stage name or status value from a future schema change (fails soft to a neutral "unknown" pill, never throws, never hides the rest of the strip).
5. **The exact #92 cases from Gil's 2026-10-09 comment**: (a) a PR sitting on `checks.state === 'pending'` shows which named checks are pending, not a generic spinner; (b) a PR with `mergeable === 'CONFLICTING'` after a sibling merged shows a distinct "needs rebase · waiting on a person" segment, not "failed" or "in progress"; (c) a PR that was a draft and got marked ready via Approve shows the draft→ready step once it has happened, and shows nothing extra when it never was a draft.
6. **The #161-class bug, reproduced on purpose**: a ticket whose latest event is `status: "started"` with a timestamp from hours ago, where `isLiveNow`/`liveNumbers` for *this* machine is false — must render **stalled**, never "running for Nh" inferred from the claim label alone. And the inverse: `isLiveNow` true but the last event is only seconds old — still "running", not stalled.
7. **Cross-machine false negative** — same stuck-looking ticket, but it's actually running on the *other* machine (so this machine's local `isLiveNow` is false and tells us nothing): must not be misreported as definitely-dead; the only trustworthy signal is "no event for N minutes," so this is really test 6's negative case restated — assert the derivation never uses `isLiveNow === false` as proof of anything, only `isLiveNow === true` as a positive override.
8. **Refusal-code parsing robustness** — detail strings in every real shape seen in the codebase (`"refused OUT_OF_ORDER: Merge #208 first"`, `"CI_FAILED: ..."`, `"MAIN_RED: 2 failing test(s)..."`, `"GATE_INFRA: ..."`, `"REBASE_CONFLICT after PR #42 merged: dashboard/x.js"`, and a bare message with **no** leading code at all, e.g. today's un-prefixed `versioning` failure) — code-extraction must degrade gracefully to "no remediation available, show the raw detail" rather than mis-parsing or throwing.
9. **Unknown/future refusal code** — a code not in the remediation map shows the raw detail text with no remediation line, not a blank/broken pill.
10. **Cross-project correctness (AC: "works for every onboarded project")** — two different repos both with ticket number 158 (the #216 regression this exact scenario is named for) must produce two independent, non-colliding strips; a project with no CI at all must not show a "checks" segment; a project profile that skips e.g. `mutation` must show it skipped, not failed.
11. **Wrong/missing permissions and a person's mistakes** — `window.api.activity.timeline` IPC rejection (file unreadable, home directory on another machine's path) is caught and renders "history unavailable" rather than crashing the card or the whole board; clicking a stage segment for a card whose detail drill-down 404s (ticket deleted) fails soft.
12. **Concurrency / repeats** — two stage-writers appending near-simultaneously (Python + Node both write the same file per the documented shared format) is already handled by the existing read-modify-write in `ticket_stages.js`/`.py`; the new test here is only that the *renderer* re-derives cleanly when the same ticket's events array grows between two polls (no stale/duplicated segments, keyed by stage name not array index).
13. **Component rendering** (the AC's explicit "Component tests with fixture stage logs"): fixtures for *passed*, *failed at gate*, *refused at order*, and *running* — matching the AC's own wording — rendered via `renderToStaticMarkup` per the existing `decisions_view.test.jsx` convention, asserting the visible label/message/remediation text, not implementation details.
14. **Verify-fails-without-a-test-change guard**: every new exported function (`deriveStageStrip`, the code-extraction regex, the remediation map, the draft→ready stage write, the `needs rebase` label mapping) has at least one test that fails if that function's behavior changes — i.e. no "trust me" code path ships untested.
