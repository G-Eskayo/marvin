## North-star fit

- **Reuses existing patterns, no new abstractions:** the queue itself (`createMergeQueue`/`createQueueStore`, marvin#231, decided 2026-10-30) already dedupes a *queued* approve by URL (`store.add`, "keeps its place") and already has an in-process latch for a *running* one (`createMergeLatch`/`alreadyMergingBody`, marvin#766, `merge_progress.js:328-343`). The gap is narrower than the ticket's own evidence lines suggest (those point at pre-#231 code that no longer exists at those lines): it's (a) the flat 409 on a genuinely-running duplicate instead of joining its result, (b) no `state`/OPEN check anywhere, and (c) a silent "queued" placeholder for a PR that's already left GitHub's open list. The fix reuses `pr_snapshot.js`'s existing field-sharing snapshot (add `'state'` to `SNAPSHOT_FIELDS`, zero extra `gh` calls in the common path), the existing `refusal()`/`MergeFailure` shape every sibling preflight check already uses (`assertTargetsBase`, `assertNotSentBack`, `readyIfDraft`), and the existing `attach` callback contract in `merge_queue.js`'s `drain()`.
- **Simplest sufficient approach:** no new queue, no new storage, no new endpoint. One new pure helper (`createMergeJoiners`, same shape as `createMergeLatch`, same file) plus one new preflight assertion (same shape as its three neighbours) plus one new optional `attach` callback.
- **Token/resource cost:** the early `assertOpen` check costs nothing extra (served from the snapshot already built for the other three preflight checks). The pre-merge recheck costs one live `gh pr view` call, only after the snapshot has gone stale anyway (a push already happened) — cheap insurance against burning a full multi-minute rebase+retest only to die with an unclassified `UNKNOWN` error at the end.
- **Phone-OS direction:** a cleaner, machine-independent "already merged"/"already closed" refusal (instead of a mystery escalation) is exactly the kind of thing MARVIN Mobile and other Macs need to render correctly without guessing.
- **More capable, not more passive:** the owner stops seeing confusing double-merge failures and ambiguous escalations for a no-op (approving twice, or approving a PR someone already resolved); nothing is hidden or auto-decided on their behalf.

## What's actually broken today (traced in code, not from the ticket's stale line numbers)

1. **A genuinely concurrent second approve** (two Macs, or "approve, deny, approve" landing while the gate is mid-run) hits `mergeQueue.isRunning(prUrl)` in `index.js:286-289` and gets an immediate `409 ALREADY_MERGING`. The *dashboard* that sent it shows this as an actual error card, even though the real merge is about to succeed — misleading, and literally what the ticket's acceptance criterion "both streams end on its result" is about.
2. **A stale approve of a PR already merged/closed** never reaches `mergePrUnqueued` at all: `merge_order.js`'s `mergeOrder()` only builds `entries` for PRs still in `gh pr list --state open`; a merged/closed URL is reported in `out.dropped` and has no `entries[url]`. `drain()` (`merge_queue.js:209`) then answers the waiting attach with `attach.queued(undefined)` → the dashboard is told `{mergeQueued: true, state: 'queued', ...}` — wrong, and it never gets corrected. This is the most common real-world trigger for "approve a merged PR" and the ticket's literal text ("check state === OPEN first in mergePrUnqueued") does not fix it, because that function is never called on this path.
3. **A deny racing a running gate** (e.g. "drop", which closes the PR on GitHub) doesn't touch the merge queue or abort the running `mergePrUnqueued`; the gate finishes rebase+retest and only then fails at `gh pr merge`, which no `failure.js` RULE matches → `UNKNOWN`/`escalate`, a confusing dead end for a complete non-event. This is the ticket's own "how we'll try to break it" case.

None of this duplicates GitHub-side work twice (the queue already prevents a true double `gh pr merge`); the bug is entirely in *how the second/stale caller is answered*.

## Decisions

### join-scope: should joining a running merge's result apply to every duplicate `/approve` of that URL, including the automated interrupted-merge retry (`approval_retry.js`), which today gets an instant `ALREADY_MERGING` refusal by design (owner decision on #766)?
- [ ] A — Recommended. Join uniformly (one code path, no new request field). The retry pass (`approval_retry.js:pass`) awaits `approve()` sequentially per entry; in the rare case the "interrupted" merge is actually still running, that retry call now blocks for the remainder of the gate (up to ~40 min) instead of bailing to "still interrupted" in milliseconds, delaying *other* waiting entries in the same pass until it resolves. The payoff: the retry gets the real result instead of a guess.
- [ ] B — Add a `retry: true` field to the `/approve` POST body (threaded through `approveMrStream`/`createApproveFlow`) and keep the instant `ALREADY_MERGING` refusal for retry calls only, joining for everything else. More code, preserves today's retry-pass timing exactly.

5. **The exact break-it case**: "approve, deny, approve within a second" — a stateful exec stub answers `OPEN` on the early check and `CLOSED` on the recheck placed immediately before the `gh pr merge` attempt → refused cleanly with `ALREADY_CLOSED` instead of an unclassified `UNKNOWN` escalation after a full rebase+retest.

7. `createMergeJoiners` (new, `merge_progress.js`, tested in `merge_progress.test.js`): two `join(url, replyA)` / `join(url, replyB)` then one `settle(url, 200, body)` → both replies get `result(200, body)` exactly once; a third, unrelated URL's joiners are untouched.
8. A joiner's `reply.result` throws (client disconnected while waiting) → `settle` still resolves the *other* joiners for that URL, and never throws itself (same "a reader going away never breaks the merge" contract already used for `tracker.emit`).
9. `settle(url, ...)` with no joiners registered is a no-op (common case — zero overhead).
10. **End-to-end, the primary acceptance criterion** ("two approves of one URL: one merge, both streams end on its result"): a small real `http.createServer` wired like `index.js` (reusing `approveResponder`/`wantsStream` as `approve_stream.test.js` already does) — two concurrent POSTs to `/approve` for the same URL while the gate is slow (a controllable fake `rebaseAndRetestFn`) result in exactly one `gh pr merge` call and *both* HTTP responses resolving with the identical final body.
11. A third and fourth concurrent approve of the same running URL all join and all receive the identical result (proves a `Set`/list, not a single slot).
12. A concurrent approve of a **different** PR while the first is running is not held — it queues/runs independently (joiners keyed correctly by URL; cross-repo and cross-PR isolation unaffected).
13. **The dropped-attach path** (`merge_queue.js`'s `drain()`): approving a PR that is already merged/closed (no race — `load()`'s `openPrs` simply doesn't contain it) resolves the attach with a terminal `ALREADY_MERGED`/`ALREADY_CLOSED` result, not the misleading `{mergeQueued: true, state: 'queued'}` placeholder, and leaves no lingering queue entry. Add to `merge_queue.test.js` alongside the existing "a restart after the PR merged elsewhere drops it" test (`:248`), this time with an `attach` present.
14. `attach.dropped` omitted (old-style test stub, e.g. existing callers in `merge_queue.test.js`) → falls back to the current `attach.queued(null)` behaviour unchanged — no existing test needs editing.
15. `by: 'memory-queue'` auto-retry hitting a URL that's already running on this process joins cleanly too (no double `forgetQueuedMerge`, no double `announceThisMac`) — misuse case: an automated trigger racing a human click.
16. Regression: `pr_url` missing/invalid is still refused at once, before any join/dropped logic runs (unchanged short-circuit in `index.js`).
