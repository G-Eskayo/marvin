## North-star fit

**Reuses:** almost everything this ticket needs already exists and only needs wiring, not new mechanisms —
- `merge_order.js:ownReason()` (lines 146–162) already produces the queue-line text for a conflict (`"conflicts with main after #970 · MARVIN is fixing it"`, decided 2026-10-30, CONTEXT.md:1577–1601, marvin#231). It just needs new wording and a files clause, not a new code path.
- `rebase_status.js` / `post_merge_rebase.js:checkOpenPrs()` already compute conflicting file lists (`{url, state, files}`) via `merge.js:conflictsWithBase()` (git merge-tree) after every merge. `merge_order.js:enrichForOrder()` already reads this store (`rebaseStatus`) but drops `rb.files` on the floor — that's the one real gap.
- `index.js`'s `onWaiting` callback (lines 446–452) **already** triggers `triggerTicketPipeline()` once per `headRefOid` when `entry.conflict` is true, which runs `ticket_pipeline.py:_requeue_conflicted_prs()` → `conflict_repair.attempt()`/`repair()` (the "cheap fix before any rebuild", #314) immediately on the event, not on a timer. The ticket's second bullet ("conflict after approval triggers a rebase… once per head commit, on the event") is **already built**; no new code needed there.
- `merge_order.js`'s `rank()` already orders queued PRs by `queuedAt` (approval time), untouched by a conflict episode, so "keeps its original place in line" after the hold clears is already structurally guaranteed — needs a confirming test, not new code.
- `HOLD_UNTIL.IMAGES_STALE` (`merge_order.js:113`, key `'head'`) already turns a fresh post-rebase run that needs new pinned evidence into a held reason instead of silently going back to "queued" — this is the existing generic hold path (`merge_queue.js` lines 230–244), so "needs the owner's re-approval" is also already covered by an existing mechanism, confirmed by a test rather than new production code. (Confirmed this repo's branch protection sets `required_pull_request_reviews: None`, `lib/branch_protection.py:45` — there is no GitHub review to go stale, so this can't be a GH review-dismissal case; it maps onto MARVIN's own evidence/decisions holds instead.)

**Simplest sufficient approach:** thread the one missing field (`conflictFiles`) through the one function that already builds the reason string, reword it, and add one PR-comment call beside an existing notify call. No new files, no new state machine, no new endpoint — `GET /merge-queue` and the dashboard card both already render whatever `merge_order.js` computes (`dashboard/electron/main/mr_review.js:9,314,317` calls the exact same pure `enrichForOrder`/`mergeOrder` the server does), so fixing the one shared pure function fixes both surfaces identically.

**Token/compute cost:** net new code is small (a few lines in `merge_order.js`, one new exported pure text-builder, one new `gh pr comment` call); no new processes, cron jobs, or scans are added — the opposite, it avoids adding a parallel "stale review" detector by reusing the existing hold mechanism.

**Where it saves:** avoids building a second conflict-files pipeline (git merge-tree is already run once per merge; we just stop discarding its output) and avoids inventing a GitHub-review-staleness detector that doesn't apply to this repo.

**User capability:** the owner stops being silently misled by "in the merge queue" when a PR is actually stuck; they get the reason and the files without having to dig through `~/.claude/logs/merge-queue.json` or ask MARVIN — more capable, not more passive, and this is a correctness/legibility fix MARVIN should own itself (no coaching trade-off here).

**Contradicts a recorded decision — correctly, per this ticket.** CONTEXT.md:1590 documents today's exact wording (`"conflicts with main after #970 · MARVIN is fixing it"`) as the decided queue-line format. This ticket is the instruction to supersede that wording with `"Held: conflicts with main…"` plus files, so I'll update that CONTEXT.md bullet (dated) rather than silently drift from it.

**Which machine:** no machine-specific work; it's pure JS logic in the shared webhook-server code, exercised by vitest, same as the surrounding suite.

No Decisions section: there is nothing here the owner needs to choose between — the wording is given by the ticket, truncation of a long file list follows the codebase's existing convention (`prState.js`'s `needsImages` block, 3 files + "and N more"), and the "stale review" bullet resolves to an existing mechanism rather than a new design choice.
