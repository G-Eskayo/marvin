## North-star fit

**Reuses:** `createInflightStore`/`inflightPath` (`dashboard/webhook-server/merge_progress.js:17-61`, already written for #568's restart record) for the new `GET /inflight` route; the existing `GET /merge-progress` route (`dashboard/webhook-server/index.js:229-233`) and `mergeOps.adopt()` (`dashboard/electron/main/merge_ops.js:64-79`, #231-follow-up) for "follow"; the cross-Mac stage relay that's already wired end-to-end (`merge_stage_relay.js` → `POST /merge-stage` → `receiveMergeMessage` at `index.js:1439`) to deliver the eventual real result without any new polling; the `mergeOps.notice()` mechanism and its existing render path in `prState.js:34-40` (used today for #762's "Mac mini is offline" failover banner) to show the "Lost contact…" text with no UI changes; `endpoint()`/`getJson()`/`the()` helpers already in `merge_failover.js:88-100` for "ask a machine something over HTTP" (same shape as `askReady`/`askForget`).

Most of what #808 describes (cross-machine relay, mount-time catch-up via `catchUpMerges`, the `adopt()` reducer that already handles "finished while disconnected") was already built for #231/#568/#762/#940/#766. Tracing the actual bug to its root: `approve_flow.js:48-53`'s `answered()` declares `'interrupted'` the instant `approveMrStream` resolves `{interrupted:true}`, with **no check** of whether the merge is still really running — that's the one real gap, and it's also exactly what lets a second Approve queue a duplicate (`mergeOps.start()` only refuses a second start while the op is still `'merging'`; flipping to `'interrupted'` unlocks it). The simplest sufficient fix is one `await` in that branch, backed by one thin new route. No new persistence, no new polling: the inactivity timer is a debounce/dead-man's-switch (same shape as `approve_stream.js`'s existing, unlisted `connectTimer`), not a recurring poll, so it should pass `polling_guard.test.js` without an allowlist entry — to be confirmed by running that test once the timer exists.

Token/compute cost: one new ~5-line route backed by data already written to disk; one `fetch` per dropped-stream event (rare) plus a once-per-10s in-process heartbeat only while a stream is open (bounded by the merge's own lifetime). Leaves the user more capable: no more false "Approve again" prompts, no more silent duplicate-merge risk, no more 45-minute false "Merging…" on a dead socket.

Machine: no change — same webhook (Mini, or whichever Mac answered) and same Electron main process that already own this code.

## Tests first

From "How we'll try to break it":
1. **Merge finishes while disconnected** — `GET /merge-progress` already returns the finished snapshot (`outcome: 'merged'|'failed'`) even after the merge ends (`createLiveMerges.get`, unlike `.running()`); a reconcile check must call `mergeOps.adopt()` with that snapshot and land on `'merged'`/`'error'`, never `'interrupted'`.
2. **`/inflight` itself unreachable** (refused, no route, times out) — reconcile falls back to the existing behavior: conclude `'interrupted'` exactly as today, never hangs, never throws out of `approve()`.

From the acceptance criteria, as direct behavioral tests:
3. **Kill the stream mid-merge** (socket destroyed after some progress, like the existing `approve_stream.test.js` "webhook restart" test) **while `/inflight` still shows it running** → the op stays `'merging'` with the notice text, not `'interrupted'`; a later relayed stage event (`receiveMergeMessage`/`adopt()`) carries it to `'merged'`.
4. **The same, but `/inflight` has nothing for that PR** (genuinely interrupted) → unchanged existing behavior: `'interrupted'`, "Approve again".
5. **Restart the app mid-merge**: a fresh `mergeOps` (empty map) + `GET /merge-queue` still reporting the PR running → `catchUpMerges`'s existing fetch of `GET /merge-progress` + `adopt()` reaches `'merging'` with the real stage data (regression test confirming this already-built path still works after the other changes; add an `/inflight` fallback call in the same function for when `/merge-progress` has nothing, e.g. evicted from the 50-entry cache).
6. **A dead half-open socket with no TCP close event at all** (no `res.on('end'|'close'|'error'|'aborted')` ever fires) — only the new inactivity timer, not the OS, must notice within the configured window (test with a tiny injected `streamInactivityMs`, same pattern as existing `connectTimeoutMs: 50` in `merge_failover.test.js`).
7. **A real keepalive line must never be mistaken for a progress or result event** (the ndjson parser already ignores unknown `type`s — add a test pinning that `{type:'keepalive'}` is a no-op for `onEvent`/resolution but does reset the inactivity clock).

Misuse the ticket's bullets didn't name:
8. **Malformed/huge `?url=`** on `GET /inflight` (not a github.com URL, a 10 KB query string, a URL with no entry) → `200` with `{inflight: null}`, never a crash (mirrors `/merge-progress`'s existing handling).
9. **Corrupt or missing `merge-inflight.json`** → route returns `{inflight: {}}` (or `null` for a `?url=` query), reusing `createInflightStore.read()`'s existing fallback-to-`{}` — one test confirming the route survives it, not re-testing `read()` itself (already covered in `merge_gate_progress.test.js`).
10. **Repeats/concurrency — the actual bug**: Approve, drop the stream while `/inflight` says it's still running, and click Approve again *during* the reconcile check → refused as `alreadyMerging` (via the unchanged `mergeOps.start()` guard), never queues a second gate run. This is the regression test that proves the fix, not just a side check.
11. **A listener/reconcile call that throws** → never loses the eventual result and never crashes `approve()` (same "a listener's mistake never stops the merge" guarantee the file already documents elsewhere).
12. **Stale state**: a reconcile snapshot for an *older* attempt id/seq than what's locally known must not regress the card (already `adopt()`'s job — add one test calling the new reconcile path with a stale snapshot to confirm it delegates correctly rather than bypassing `adopt()`'s own staleness guard).
13. **polling_guard.test.js** run as-is after adding the inactivity timer and the webhook heartbeat, to confirm neither needs (or, if it does, gets) an allowlist entry with a reason citing #808.

## Decisions

None — the two points that looked ambiguous (whether to add a literal `GET /inflight` when `GET /merge-progress` could technically answer the same question, and where to intercept the "interrupted" conclusion) have a single reasonable resolution each, reused from existing code shape, and are decided above rather than left open.
