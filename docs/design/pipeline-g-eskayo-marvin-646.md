## North-star fit

**Reuses before adding anything new:**
- `lib/instance.py` / `dashboard/electron/main/instance.js` (ADR 0071 step 1, already shipped) — `is_configured()`/`require_configured()` extend this exact module rather than creating a new "whose MARVIN is this" concept.
- `lib/tests/conftest.py`'s existing autouse-fixture pattern (already isolates ~15 other pieces of real state — `_isolate_failure_breaker_log`, `_isolate_ticket_stages_everywhere`, etc.) is the pattern I reuse for the configured-instance guard, instead of inventing a second mechanism.
- `dashboard/test/support/temp_home.js` + `assert_temp_home.js` (the JS twin of the same isolation idea, `vitest.config.js`'s `setupFiles`) — reused the same way for the dashboard suite.
- `lib/launchd/com.marvin.code-sync-push.plist` + `install_code_sync.sh`'s `sed "s#__HOME__#$HOME#g" | plutil -lint | bootstrap` sequence is the already-proven template; I extract it once and point every other install script at it instead of writing a second version.
- `lib/host_os.py:memory_dir()`'s `str(home).replace("/", "-")` is the existing, already-tested algorithm for the Claude-Code project-dir slug; `boot_data.js`'s hardcoded `-Users-gileskayo` gets the same derivation, not a new one.

**Why this is the simplest sufficient approach:** the ticket's real difficulty isn't finding the 84+11+N files (`git ls-files` + the ratchet regex already enumerates them); it's the guard-placement defect that sank both prior attempts. Root-causing that once (an autouse pytest fixture that pins a *configured* fake instance for the whole suite, keeping `REPO`'s computed value identical to today's literal `"G-Eskayo/marvin"` so none of the ~90 existing test files' assertions change) lets the guard go directly into every real writer function (`claim_next_ticket`, `run_claim_cycle`, `run_ticket.run`, `mr_raiser.raise_mr`, `purpose_metrics.run`, `ticket_pipeline.main`) rather than requiring a bespoke "find the real entry point" analysis per module — which is exactly where the last two attempts burned their time and still got it wrong twice.

**Token/time cost:** this is a genuinely large, mechanical sweep (84 ratchet files + ~11 plists + a handful of dashboard/IPC files). I'm spending tokens up front reading every file the task list below touches so the implementer doesn't have to re-derive guard placement a third time; the substitution itself (literal → `instance.*()`/`instance.owner()`/`instance.ticketsRepo()`) is mechanical and batched per logical cluster, not per file.

**Phone-OS / capability:** directly serves north star 2 — this is the thing that currently breaks a friend's clone (ADR 0071's own stated motivation: a second user's MR Review showed the owner's PRs). Fixing it is what makes MARVIN installable by someone who isn't Gil, a precondition for "OS of a phone," not just Gil's.

**More capable, not more passive:** this is pure infrastructure hardening (no UI the user has to learn, no judgment removed from Gil) — it fails loudly instead of silently when unconfigured, which is strictly safer, so north star 3 doesn't argue against it.

## Scoping call (stating plainly, not re-litigating)

The AC's "personal lines in prompts and skills (names, the phone number class of data)" bullet is **already satisfied** for the literal incident ADR 0071 describes (owner's phone number and clearance status in a skill template, 2026-10-25): `skills/resume-tailor/SKILL.md`/`README.md` already use placeholders (`[phone]`, `(000) 000-0000`, `[security_clearance]`), the real values live in the private `master.md`, and `lib/tests/test_push_guard.py` + `bin/pre-push-guard` (ADR 0071 step 1, already shipped) are the standing gate against that recurring. I will **not** sweep every "Gil"/"Giles" mention out of skill `.md` prose — most describe Gil's own voice/preferences in skills that are inherently about him (`writing-style`, `resume-tailor`), the ratchet test's own `CODE` glob deliberately excludes `.md` entirely, and scrubbing hundreds of legitimate prose mentions is a separate, much larger, unrequested project. The two *code* instances of personal-machine/person phrasing that **are** in the 84-file ratchet scope — `skills/paper-dive/scripts/paper_graph.py:177` (`"...run this on gils-mac-mini."`) and `skills/improve/scripts/cross_machine_merge.py`'s `MERGE_PROMPT_TEMPLATE`/module docstring ("Gil's registered machines") — are fixed as part of the normal 84-file sweep below.

## Tests written first

No "How we'll try to break it" section exists on this issue; the list below is built from the ACs, the two documented prior-attempt failures (both are now tests, not just fixed code), and the standard misuse categories.

1. **Unconfigured instance, every writer, asserted against the real collaborator's shape — not mocked away.** For each of `ticket_claim.claim_next_ticket`, `ticket_claim.run_claim_cycle`, `run_ticket.run`, `mr_raiser.raise_mr`, `purpose_metrics.run`, `ticket_pipeline.main`, and the three dashboard IPC handlers (`decisions:submit`, `mr:ticketContext`, `mr:sendBackForOptions`): monkeypatch/override to a *blank* instance (no origin, no `instance.json`) and assert the call raises `instance.NotConfiguredError` (Python) / throws a typed `NotConfiguredError` (JS) **before** any `gh`/`git` subprocess runs — assert on the injected fake/subprocess spy never being called, the same shape as `test_an_unknown_or_injected_probe_never_runs_anything`'s `pytest.fail` spy already does in `test_purpose_metrics.py`.
2. **The exact prior regression, named.** A new test proves `claim_next_ticket(machine_id, list_claimed=fake, ...)` called directly (bypassing `run_claim_cycle`), and `rt.run(20)` / `mrr.raise_mr(...)` called directly (bypassing `main()`), still pass under the suite's default (configured-fake) fixture with zero changes to any existing test's fixtures — this is the literal regression test for "tests pass on a configured Mac and raise on a clean checkout," proving the conftest fix, not a CLI-only guard.
3. **A fake instance (`acme/marvin`) never leaks the upstream owner.** Extend `test_instance.py`'s `at()` fixture pattern: configure `{"owner": "acme-eng"}` / origin `acme-eng/marvin`, call through `claim_next_ticket`'s and `purpose_metrics.run`'s injected fakes, assert no constructed `gh`/URL/ticket-ref string contains `"G-Eskayo"` anywhere in the call args.
4. **Bad/malformed instance.json never crashes a writer** — reuse `test_a_corrupt_or_wrong_shaped_config_reads_as_a_blank_instance`'s bad-JSON fixtures (`"{not json"`, `"[]"`, `'"a string"'`, …) through `is_configured()`/`require_configured()`; a corrupt file reads as unconfigured (fails loud), never as a crash or a silent pass.
5. **Huge/malformed origin URL never panics the regex.** A `remote.origin.url` with embedded control characters / 10 KB garbage / no `github.com` substring at all still resolves to "unconfigured" or the documented non-GitHub fallback, never an unhandled exception (extend `test_a_non_github_origin_is_not_parsed_into_a_fake_repo`).
6. **`git remote get-url` failing (no git installed, detached worktree, permission-denied `.git`) is treated as "no origin," not a crash** — `_origin_repo()`/`load()`'s existing try/except already covers `OSError`/`subprocess.SubprocessError`; add an explicit test forcing that path and asserting `is_configured()` still returns a clean boolean.
7. **Repeats / O(1) per process still holds** for `is_configured()`/`require_configured()` — extend `test_the_config_file_is_read_once_per_process`: calling `require_configured()` in a hot loop (the pipeline calls instance getters in loops per its own docstring) does not re-stat/re-exec git each time.
8. **Concurrency:** two processes (the mac-mini scan and a manual `run_ticket.py` invocation) reading the same `instance.json` mid-write by `instance:setFeature` never see a torn/partial read — reuses the existing `_config()`/`load()` try/except-on-parse-failure path (already covered by test 4's malformed-JSON case; add one test writing truncated JSON mid-read via a monkeypatched `read_text`).
9. **Wrong machine / wrong permissions:** `instance.json` unreadable (chmod 000) is treated identically to "missing," not a crash — extend `test_a_missing_instance_dir_is_a_blank_instance_not_a_crash`'s shape to an existing-but-unreadable file.
10. **A person's mistake — `instance.json` with `"engine_repo": 7` or `{"owner": {}}`** (wrong type, not just wrong JSON) reads as blank, per `_str()`'s `isinstance` guard — extend the corrupt-config parametrize list with these shapes.
11. **The ratchet itself, both directions:** `test_no_new_engine_file_hard_codes_an_owner_account_or_machine` passes with `GRANDFATHERED` emptied to `set()`; `test_the_grandfathered_list_only_shrinks` still passes (nothing *new* is added to the file). Both already exist; they are the acceptance gate for every file-level change below, not new tests to write, but must stay green throughout.
12. **Dashboard "not configured" banner, both states:** a `boot:data`/new `instance:get` read with `configured: false` renders the banner and the three guarded IPC handlers' thrown errors surface as a visible message, not a silent failure; a `configured: true` read renders nothing extra. New `dashboard/test/instance.test.js` cases plus one `decisions_submit.test.js`/`mr_review.test.js`-style case per guarded handler.
13. **Plist install is idempotent and non-destructive under repeats/stale state:** installing the same plist twice backs up the previous one (`$DEST.bak-<timestamp>`) rather than erroring or silently dropping it — the existing `install_code_sync.sh` behavior; the new shared `install_plist.sh` helper gets its own test/invocation proving this holds for a plist that was never templated before (first-run) and one that already was (re-run).
14. **A plist install given a template that still contains `/Users/gileskayo` (a person's mistake — forgot to re-template before calling the shared helper) fails the `plutil -lint` check loudly** rather than installing a broken or still-personal plist — assert the helper's `plutil -lint` gate actually rejects an untemplated file.
