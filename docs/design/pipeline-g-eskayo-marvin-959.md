## North-star fit

**Reuses before adding anything new:**
- `_safe()` in `lib/dispatch_concurrency.py:152` — already the "catch, return None, never block" pattern; it becomes the first `guard_reading()` call site instead of a parallel mechanism.
- `lib/machine_resources.py:157` (`read_samples`/`is_stale`) — a remote machine's disk is already sampled every 30s and synced via the existing `~/.claude` sync layer (no SSH). Wiring `dispatch_concurrency.can_start_another`'s remote-disk gap to this, instead of inventing an SSH disk probe, directly fixes the table's "Disk on a remote machine... | always pass" row with zero new infrastructure.
- `dispatch_concurrency.mark_plan_limited`/`plan_limited` (`lib/dispatch_concurrency.py:215-232`) — the "mark once, read back to gate a repeated action within a window" shape is reused for the 2-hour degraded-alert dedup, instead of a new state mechanism.
- `health_checks.default_checks()` / `guarded()` (`lib/health_checks.py:1634`, `:1796`) — the existing check-registration and timeout-wrapper pattern; one new tuple added, no new orchestration.
- `notify.notify()` (`lib/notify.py:82`) — the one alert path (#1123/ADR 0083); reused as-is for the degraded alert.
- `test_tool_requirements.py`/`test_outside_state.py`'s `ast.parse`-on-source pattern — reused for the "table covers every guard" static test, instead of inventing a runtime registry.
- `machine_resources`-style JSONL logging and `_result()`/severity vocabulary from `health_checks.py` — reused for the new Health row rather than a new severity scheme (the spec's "yellow, never green" is exactly CONTEXT.md's existing "degraded or stale-by-design" definition, no new state needed).

**Why this is the simplest sufficient approach:** one small module (`lib/guard_reading.py`) holds the log, the streak math, the fail-mode table and the alert dedup once; every call site becomes a one-line wrapper around a read it already performs. No new daemon, no new storage format (JSONL, same as every other MARVIN log Health already reads), no SSH added.

**Tokens:** spends a little upfront (a new module + ~10 call-site edits + cross-language JS edit), saves going forward — the exact outages in the ticket (#889, #891) ran for days burning dispatcher attention and owner trust; a yellow Health row at 30 minutes stops that class of silent multi-day failure before it compounds.

**Machine:** no machine affinity — pure library code plus one dashboard/webhook-server (Node) edit; runs wherever dispatch, the pipeline, or the merge gate already run today.

**More capable, not more passive:** this makes failures visible and, past 2 hours, proactively surfaced — it replaces "nothing tells you" with "Health shows it, then it pings you," which is squarely north star 2 (nothing breaks silently) without taking any decision away from Gil (it still alerts rather than auto-fixing).

**Correcting the ticket's own framing:** the ticket doesn't mention it, but the "disk" row also covers the **merge gate's own JS-side disk check** (`dashboard/webhook-server/merge.js:528`, `freeDiskBytes`/`rebaseAndRetest` — currently `.catch(() => null) // unreadable: carry on, as before this check`). This is a second, separate disk-floor implementation from `disk_triggers.preflight`, in a different language, and per the Decision it must also flip from open to closed. Flagging this now because it's cross-language and easy to miss (plausibly why earlier attempts failed review) — the plan below treats it as in-scope, no new Decision needed since it's a direct application of the already-answered Decision.

## Decisions

None outstanding. `guard-unreadable` was answered by Gil 2026-10-30 (per-guard: closed for disk and memory, open-but-loud for the rest) and is already machine-recorded on the issue. One consequence worth stating plainly rather than silently implementing: making the **remote**-disk guard closed (via the `machine_resources` samples, since no remote disk reading currently exists for dispatch at all) means a remote Mac whose resource sampler hasn't reported recently (asleep, sampler job down, or simply never having run) stops being eligible for parallel-dispatch tickets under the disk guard, where today it's silently always eligible. This is the correct reading of "closed for disk," not a bug — flagged so it isn't a surprise during review.

## Tests first (one per line in "How we'll try to break it", plus misuse it didn't name)

From the ticket's own list:
1. Guard input is a **missing file** → `guard_reading` logs unreadable, returns `None`; the disk/memory callers refuse, the rest carry on.
2. Guard input is **unreadable (permissions)** → same path as missing file (OSError family).
3. Guard input is **malformed JSON** → same path (ValueError family); one bad task-record file among several valid ones must not drop the valid ones (extends existing `test_read_task_records_globs_json_files_and_skips_malformed`).
4. A **probe that hangs** → the existing per-check `budget_s`/`guarded()` timeout in `health_checks.py` already bounds this for the Health row; a direct test calls `guard_reading` with a reader that sleeps past a timeout wrapper and confirms it logs unreadable rather than hanging the caller.
5. A **CLI not on PATH** (launchd PATH gotcha, e.g. `tailscale`) → `FileNotFoundError` from `subprocess.run` is caught and logged exactly like any other read failure.
6. **Flapping** (unreadable → readable → unreadable within the window) → one log test: readings alternate every poll; assert the streak/episode counter resets on each success rather than accumulating across gaps, and the alert-dedup state only re-arms after a real recovery (one episode, not many, matching `check_sync_stuck_from_text`'s existing streak logic it patterns off of).
7. **A guard added later without a table entry** → the AST-based static test scans `lib/**/*.py` and `dashboard/webhook-server/**/*.js` for `guard_reading(` / the JS recorder call with a literal first argument, and fails if that name is missing from `FAIL_MODE`.
8. **A remote Mac unreachable over SSH** → not applicable to the *new* remote-disk path (it no longer uses SSH — it reads the synced sample file), but it must be asserted directly: `read_samples()` returning `[]` or `is_stale() is True` for a device is treated as unreadable (closed), not as "0 GB" or "fine."

Misuse the ticket's list didn't name, added per the repo's north stars:
9. **Each dependency failing independently**: `gh` down (github budget), `tailscale` missing, `sysctl` missing (memory), `statvfs`/`statfs` raising (disk, both Python and the Node `merge.js` path) — one test per dependency, not one generic test, so a future regression in just one of them is caught.
10. **Concurrency**: two processes calling `guard_reading` for the same guard name at once while the log is being appended/trimmed — assert no exception and no corrupted line (reuses the existing append-and-trim pattern from `memory_guard.record()`, which already handles this for its own log).
11. **Repeats**: calling `guard_reading` hundreds of times in a tight loop (a busy dispatch scan) must not re-send the degraded alert every call once already alerted for the current episode (dedup test, explicit assertion of exactly one `notify.notify()` call).
12. **Wrong order**: a success recorded *before* any failure (cold start, log file doesn't exist yet) must read as "healthy," not as "unreadable since epoch."
13. **Stale state**: the alert-dedup state file pointing at a *previous* episode (old `streak_start`) when a *new* unreadable episode begins must re-alert, not stay silently suppressed forever (direct analogue to `dispatch_concurrency.plan_limited`'s window check).
14. **A person's mistakes**: hand-editing `config/dispatch.json`'s `guards` block or the FAIL_MODE table to reference a guard name that doesn't exist anywhere — must not crash the dispatcher (name absent from the table is a programming-time test failure per #7, not a runtime crash path).
15. **Regression on existing behavior that must NOT change**: `test_an_unreadable_guard_never_blocks_starting` (`lib/tests/test_dispatch_concurrency.py:114`) currently asserts `github_budget_pct` raising **and** `disk_free_gb` returning `None` both yield `(True, None)`. This must be split: the GitHub-budget half keeps asserting open (unchanged), and a **new** test asserts `disk_free_gb=lambda m: None` now refuses with a named reason (closed). Same for `test_an_unreadable_level_is_none_so_it_never_blocks` (`lib/tests/test_memory_guard.py:74`) — rewritten to assert refusal, not pass-through. Same for `disk_triggers.py`'s `test_an_unreadable_disk_pre-flight_...`-style case at `lib/tests/test_disk_triggers.py:66` (`free=lambda: None, reclaim=lambda: pytest.fail(...)`) — today it asserts `ok=True`; it must assert `ok=False` and that `reclaim` is still never called (nothing to reclaim toward when the reading itself is unknown).
16. **Real collaborator, not a mock**: the remote-disk test reads an actual `machine_resources`-shaped JSONL sample file on disk (not a mocked function returning a canned dict), since the bug class here is exactly "the reader returns something that *looks* fine" — same reasoning CONTEXT.md gives for testing `repo_state_script` against real git plumbing.
17. **Health card thresholds**: exactly 2 consecutive unreadable readings (no time elapsed) → yellow; 1 reading at 31 minutes old → yellow; 1 reading at 29 minutes with only 1 consecutive reading → no row at all (below both thresholds).
18. **Alert escalation boundary**: streak age at 1h59m → no alert; 2h00m01s → exactly one `notify.notify()` call with "degraded" in the message and the guard's name.
19. **Merge-gate JS path**: `rebaseAndRetest` with `freeBytes` resolving to `null` → now returns `{ ok: false, reason: ... }` (closed) instead of proceeding; a companion test asserts the existing low-but-readable-disk path (`free < MIN_GATE_FREE_BYTES`, a real number) is unchanged (first aid still runs, still refuses after).
