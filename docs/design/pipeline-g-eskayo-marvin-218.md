This ticket only needs to make `run_ticket.py` *produce* a hold + revisit line the existing machinery already consumes.
- `lib/run_ticket.py:140` `_park_stuck_ticket` and its existing `prior_streak`/`MAX_CONSECUTIVE_FAILURES` call site (`run_ticket.py:364-372`) — already a working 3-strike guard; this ticket swaps its *counter source* (GH comments → jsonl) and its *label* (`needs-info` → `hold`), not its shape.
- `lib/project_profile._validate`'s `setdefault` + `raise ValueError(f"{source}: ...")` validation style (`project_profile.py:113-148`) for the new `failure_threshold` field.
- `lib/health_checks.check_missing_profiles`'s `snapshot=None → ticket_agents.collect(repos, gh=gh)` injectable-snapshot pattern (`health_checks.py:612-640`) for the new Health check, rather than a fresh ad-hoc `subprocess.run` call — one less bespoke GH-calling shape in the file.
- `lib/tests/test_failure_breaker.py`'s `isolated_log` fixture + `_fail()` helper — reused as-is for every new `failure_breaker` test.

**Correcting the ticket's own stated shape:** the issue has no literal `## What to build` header, but `ticket_policy.triage_verdict` (`ticket_policy.py:244`, comment names `#218` explicitly) already accepts `## Solution` as satisfying that gate — the triage-bot's "missing a 'What to build' section" comment on this ticket is stale. Treating "Solution" + the "Tests:" bullet as the de-facto spec, per this ticket's own "make the most reasonable call" instruction.

**A real, already-merged trap this plan must close:** `lib/ticket_policy.STATE_LABELS` (`ticket_policy.py:14`) does not include `"hold"`. `triage_verdict` treats any ticket with no label in `STATE_LABELS` as untriaged. A ticket parked with only `hold` (exactly what this change produces) would get `ready-for-agent` silently re-added by the next hourly `triage` pass — reopening the retry storm this ticket exists to stop. Fixing this (add `"hold"` to `STATE_LABELS`) is in scope, not scope creep: it's the thing that makes AC2's hold actually stick. (JS `dashboard/electron/main/board.js:20` already has `hold` in its own `STATE_LABELS` — that one's for label *coloring*, already correct, no JS change needed.)

**Why the existing PR #400 is not a shortcut here:** it was built against an older `main` and now permanently conflicts (`DIRTY`/`CONFLICTING`, repeatedly rebased and sent back per the ticket's own comment history) because `main`'s `run_ticket.py` has since grown `_trailing_streaks`, `MAX_CONSECUTIVE_RETRIES`, load-aware retry backoff (P6, 2026-10-21) — machinery PR #400 doesn't know about. Its design doc and test list are still a good source (reused above and in the test list below), but its diff cannot be reapplied. Also found while reading it: its `ticket_streak()` indexes `r["ticket"]`/`r["project"]` without `.get()` — a `"clear"` record (`failure_breaker.py:82-83`, no `ticket`/`project` key at all) would `KeyError`-crash it; this plan reads defensively. **Lesson applied:** keep this attempt's touch to `run_ticket.py` as small as possible (one call site, not a rewrite of the surrounding failure-handling branches) — the repeated "same lines changed on both sides" conflicts were very plausibly self-inflicted by over-broad edits to a fast-moving file.

**Simplest sufficient approach:** net-new code is one streak/hold function pair in `failure_breaker.py`, one label/comment change in one existing call site, one profile field, one Health check, one `STATE_LABELS` entry, one CONTEXT.md addition. The `timed_out`- and `too_vague`-triggered `_park_stuck_ticket` call sites (`run_ticket.py:342-346`, `357-360`) are deliberately left untouched: their failures aren't written to `pipeline-failures.jsonl` at all (AC1 is specifically about that log), and touching them would re-widen the diff into exactly the territory that made PR #400 unmergeable.

**Tokens:** saves them going forward — once held, a ticket stops burning paid model time on every dispatch cycle (the stated motivation: retry storms were ~70% of output tokens). The plan/build/verify cost here is a small, contained diff, not a rewrite.

**User capability:** reliability plumbing (north star 2, "nothing may break silently"), not user-facing capability — but it leaves Gil more capable: a stuck ticket surfaces its cause and a date to look again instead of silently re-burning cycles while looking "blocked."

## Tests to write first

From the ticket's "Tests:" bullet, made concrete against the real jsonl log and real `ticket_policy` parser (no mocks where either's own rules could hide a bug) — reusing `lib/tests/test_failure_breaker.py`'s `isolated_log` fixture and `_fail()` helper throughout:

1. **N mixed failures** → `should_hold` returns `reason="n-failures"` at exactly N, with the N distinct signatures in order.
2. **2 identical signatures in a row** → held immediately even with N-1 total failures (e.g. N=3, only 2 failures, both same signature).
3. **A success in between resets the count** → N-1 failures, a recorded success, then N-1 more failures ⇒ not held (streak restarts from the success).
4. **Malformed/corrupt line** between real entries never crashes `ticket_streak`/`should_hold` and isn't counted (mirrors `_read()`'s existing per-line skip).
5. **A `"clear"` record** (no `ticket`/`project` key at all, the real shape `failure_breaker.clear()` writes) must not crash `ticket_streak` via `KeyError` — this is the concrete regression test for the bug found in PR #400's abandoned implementation; use `.get("ticket")`/`.get("project", MARVIN)`, never bare indexing, inside the ticket-scoped filter.
6. **Empty input** — no log file yet → `{"count": 0, "signatures": []}`, never held, never raises.
7. **Huge input** — thousands of lines across many unrelated tickets/projects (the real #28-shape, 1,644 entries) — one ticket's streak must only see its own lines and stay fast (bound the test's wall time, not just correctness).
8. **Dependency failing** — `gh issue edit --add-label hold` or `gh issue comment` failing (rate-limited/offline) inside `_park_stuck_ticket` must not crash `run()` or leave the ticket re-dispatchable; mirrors the existing `test_a_failing_gh_call_never_stops_the_rest_of_the_park` (`test_run_ticket.py:418`) — extend that same test (or add a sibling) to cover the new hold-label call.
9. **Repeats/idempotency** — crossing the hold threshold twice (revisited, re-dispatched, fails again) must not double-apply `hold` (`gh issue edit --add-label` is already idempotent) nor leave two conflicting `Revisit by:` comments `latest_revisit()` can't resolve — assert `latest_revisit` still cleanly picks the newest.
10. **Concurrency / per-machine isolation** — two machines each write their own `pipeline-failures.jsonl` (`LOG_PATH` is per-machine already); assert ticket A's streak on machine 1 is unaffected by ticket B's failures logged only on machine 2. Document explicitly that cross-machine streak counting is *not* implemented (matches `failure_breaker.py`'s own existing module docstring), rather than letting it look handled.
11. **Env-missing / model-unavailable / timed-out never count toward this streak and never hold** — these paths never call `failure_breaker.record_failure` with a ticket-attributable "real" failure the way the generic-failure branch does (timeouts/env-missing already skip it entirely; model-unavailable records a failure but that path doesn't read `should_hold`). Add a regression test: N repeats of a `TestTimedOut`/`env_missing` outcome never triggers `hold` via the new code path.
12. **Stale pre-change state** — old `FAILURE_MARKER` GitHub comments from before this ships must not instantly park a ticket on the first post-change run; the new counter starts from the jsonl log's own content, independent of comment history.
13. **A person's mistake (manual release)** — removing `hold` and re-adding `ready-for-agent` on an already-held ticket does **not** reset its jsonl streak (no implicit clear exists for a single ticket, only `failure_breaker.clear()` for the whole breaker); if it fails again, the streak keeps accumulating from the prior failures. Decided, not asked: matches the north-star "verified, not assumed" — a label edit isn't proof the cause was fixed. Add a regression test asserting this.
14. **Per-project isolation** — ticket `#7` failing in `G-Eskayo/marvin` and ticket `#7` failing in another profiled project count as two independent streaks (mirrors the existing cross-ticket-breaker test `test_ticket_streak_two_different_tickets_are_separate`-shaped case already proven for `tripped()`).
15. **Profile override, including malformed values** — `failure_threshold: 5` honored; no key / no profile file (marvin) falls back to the pipeline default (3); `failure_threshold: 0` or a negative int raises `ValueError` at `project_profile.load_profile()` time (fails loud, visible, not a silent runtime surprise); `should_hold()` itself stays defensive (never divides/indexes out of range, never holds) if ever called directly with a non-positive threshold.
16. **`STATE_LABELS` regression** — a ticket carrying only `hold` (no other state label) is *not* re-triaged back to `ready-for-agent` by `triage_verdict`, even with a fully-formed body. The latent bug this plan closes.
17. **Health check, all branches** — no repos/no snapshot → `[]`; a repo with no `hold` tickets → nothing reported for it; a `hold` ticket with streak count 0 (held for an unrelated reason, e.g. a person's manual hold) → excluded, not misreported as a retry-storm hold; a `hold` ticket with a real streak → included with its ticket/repo/count/last-signature; malformed/missing jsonl log doesn't crash `run_all()`.
18. **Revisit round-trip** — the generated `Revisit by:` line is byte-for-byte parseable by the existing `ticket_policy.parse_revisit_comment`/`latest_revisit` (a real round-trip call, not asserting on the generator's string shape in isolation) — the "verify fails when code changes without a test changing" guard for this exact integration seam.
19. **Existing seam tests keep passing unchanged** — the ~20 tests in `test_run_ticket.py` that monkeypatch `rt._consecutive_failure_streak`/`rt._park_stuck_ticket` as black-box seams (e.g. `test_run_parks_the_ticket_instead_of_releasing_at_the_failure_cap`) must need **no changes**, since the function's name and call signature don't change — only its body. Only the two tests that assert the *old* GH-comment-scanning internals (`test_consecutive_failure_streak_counts_trailing_failure_comments`, `test_consecutive_failure_streak_resets_on_a_human_comment`) and the two that assert the *old* `needs-info` label (`test_park_stuck_ticket_removes_ready_for_agent_label`, `test_parking_adds_needs_info_before_removing_ready_for_agent`) need deliberate rewrites — call this out explicitly so review can see it's an intended behavior change (AC4: a success resets it, *not* any human comment; AC2: `hold`, not `needs-info`), not an accidental regression.
