## North-star fit

**Reuses:** `lib/instance.py:feature_enabled()` and `dashboard/electron/main/instance.js:featureEnabled()` already exist, already default every unknown/missing feature to `False`, and the dashboard's `instance.json` cache/`reset()` pair already exists for invalidation. Nothing in this ticket needs a new config-reading abstraction — it's wiring real call sites to functions that already exist and are already tested (`lib/tests/test_instance.py`, `dashboard/test/instance.test.js`). The IPC shape I'll add (`window.api.instance.features/setFeature`) reuses the exact `contextBridge` → `ipcRenderer.invoke('ns:method')` → `ipcMain.handle('ns:method', …)` pattern already used for `health:*`/`profiles:setDispatch` (`dashboard/electron/preload/index.js:98-105,78-82`). A write-capable IPC method is already precedented there (`profiles.setDispatch`, `health.setMergeFromDashboard`, `dispatch.setConcurrency`) — the preload file's header comment claiming "no write methods" is already stale before this ticket, not a constraint I'm breaking. The Python-side sys.path convention for a skill script importing `lib/*` reuses `skills/paper-dive/scripts/*.py`'s `Path(__file__).resolve().parents[3] / "lib"` (relative to the file, not `~/.agents`, so it works inside this ticket's own worktree) rather than the `Path.home()/".agents"/"lib"` form other skills use.

**Why simplest sufficient:** Of the three add-ons, only Seal ingest has a real background job + launchd plist (`lib/seal_beta_ingest.py` + `config/launchd/com.marvin.seal-beta-ingest.plist`, confirmed hand-installed per its own header comment — no automated installer loads it, so a fresh/stranger instance has no running job to stop in the first place); Portfolio has only an on-demand dashboard tab (confirmed: `App.jsx` is the only place `PortfolioHub` is mounted, and it has ~15 `useEffect`s firing `window.api.portfolio.*` on mount); Resume Tailor has only a slash-command skill, no dashboard presence and no job. So the gate goes exactly where AC's own words point — the job's single entry point (`ingest()`), the skill's routing entry, and the tab's mount point — not inside Portfolio's ~50 individual IPC handlers, which AC doesn't name. No launchctl bootstrap/bootout machinery is built: there's no precedent for dynamic plist (un)loading anywhere in this repo, and building one now would be new infrastructure nobody asked for (Watts check) — "stops its jobs" is satisfied by the job refusing to do real work when off, which is sufficient because no default-build install today auto-loads that plist at all.

For the dashboard gate, I'm deliberately **not** reusing the rejected prior attempt's shape (an internal `useEffect`+`useState` fetch inside a new `PortfolioHubGate.jsx` wrapper per add-on). This repo's dashboard tests never mount effects (confirmed: `dashboard/test/vitest.config.js` has no jsdom; every existing component test either asserts pure-function output or SSR markup via `renderToStaticMarkup`, which never runs `useEffect`). A fetch-inside-the-gate design is therefore untestable for "zero IPC calls when off" in this codebase's own test style — the previous attempt's test for that case didn't actually test it. Instead: `App.jsx` fetches `features` once (mirrors the existing `reviewStatus`/`healthOverall` pattern already in `App.jsx:57-107`) and passes `enabled` down as a plain prop into a tiny new `AddonGate` component (`enabled === null → render nothing`, `false → <AddonNotSetUp/>`, `true → children`). Because JSX element creation (`<PortfolioHub/>`) doesn't invoke the component function — only actually rendering it into the tree does — passing `<PortfolioHub/>` as `children` and never taking that branch means `PortfolioHub`'s effects provably never run. This is a 6-line component, reusable as-is by Resume Tailor/Seal's future tabs with zero changes, and it's the unit that makes the "zero IPC calls when off" criterion checkable with a plain `renderToStaticMarkup` test (pass a spy component as `children`, assert it never renders), matching this repo's existing no-dependency SSR test convention (`dashboard/test/open_dev_site_button.test.jsx`, `check_progress_view.test.jsx`) instead of `@testing-library/react`/`user-event`, which aren't in `dashboard/package.json` — this is the exact bug that twice failed PR #663's CI (`test/addon_not_set_up.test.js`, JSX syntax in a `.js` file plus an uninstalled dependency; Rollup's "Expression expected" parse error). I'm fixing that root cause by not repeating the pattern, not just renaming a file.

**Tokens:** spends a small, fixed amount now (one shared `AddonNotSetUp` card, one tiny `AddonGate` wrapper, ~2 new IPC calls, one gate line in `ingest()`, one gate script for Resume Tailor) in exchange for every future add-on reusing the same two components and the same `instance:features` call — O(1) per tab switch, no polling added.

**More capable, not more passive:** this makes an implicit "is this running" state explicit and visible, protecting a stranger's first install from silently running Gil's personal/paid add-ons, and protecting Gil from a gate that silently turns off something he already relies on (the migration script exists for exactly that).

## Decisions
<!-- marvin:decisions -->
### tab_shape: Where does each add-on's "not set up" state live?
- [ ] A: One new shared "Add-ons" tab lists all three (Portfolio, Resume Tailor, Seal ingest) as cards with the shared not-set-up/enabled state; Portfolio's existing tab is also gated, so it shows the state in two places until Portfolio's own tab is the primary surface
- [ ] B: Each add-on gets its own tab — Portfolio's existing tab plus two new minimal tabs (Resume Tailor, Seal) — using the shared `AddonNotSetUp` component; when on, the two new tabs show only a thin status placeholder (no real feature UI exists for them yet)
- [ ] C: Only Portfolio's existing tab gets the gate now; Resume Tailor and Seal are gated at the job/skill level only (no new tabs), deferred until a later ticket gives them real on-state dashboard content

I'm shipping **C** by default (matches today's reality — Resume Tailor and Seal have no dashboard tab to gate at all right now, so A/B would mean building placeholder tabs nobody asked for yet) but leaving this open since adding tabs is a product call, not just an engineering one.

### setup_button: What does "start its setup" do today, before a first-run setup wizard exists?
- [ ] A: The button flips `features.<name>` straight to `true` in `instance.json` via a new write IPC (`instance:setFeature`) — simplest; a later wizard can replace what runs *before* the flip without reworking this gate
- [ ] B: The button only shows the manual `instance.json` edit instructions and writes nothing itself, until a real wizard ships

I'm shipping **A** by default — a write-capable IPC following this exact shape already exists in this file (`profiles.setDispatch`, `health.setMergeFromDashboard`) — but it's a real UX choice about whether a casual click should mutate config today.

## Tests (written first)

No "How we'll try to break it" or Attacks list exists on #647; treating the acceptance criteria as that section, plus standard misuse:

1. **Seal job, feature off:** `ingest(..., feature_enabled=lambda n: False)` with real report files present in a tmp attachments dir returns `{"ok": True, "skipped": "feature_off", ...}`; asserts nothing written to `reports.jsonl`/`summary.json`/`status.json` and the attachments dir is never listed (inject a `find_reports`-style spy or check the store dir has zero new files).
2. **Seal job, feature on (regression guard):** same call with `feature_enabled=lambda n: True` behaves exactly as today — unchanged existing-test results.
3. **Seal job, dependency failing while off:** feature off *and* a simulated Full-Disk-Access denial (`find_reports` would raise `IngestError("permission", …)`) still returns the clean `skipped` status — the off-gate short-circuits before any filesystem touch, never racing the permission check.
4. **Seal job, malformed instance.json:** `feature_enabled` backed by `lib/instance.py`'s existing corrupt-config fixtures still reads as off; `ingest()` still skips cleanly (reuses `lib/tests/test_instance.py`'s fixtures, doesn't re-derive them).
5. **Seal job, repeated/concurrent while off:** two concurrent `ingest()` calls with the feature off both return `skipped` without ever opening/creating the `.lock` file (proves the gate precedes `fcntl.flock`, no race possible).
6. **Seal job, production wiring:** `main()`'s `run` subcommand passes `feature_enabled=inst.feature_enabled` (not the default) — a test that patches `instance.feature_enabled` and calls `main(["run"])` proves the CLI path actually honors the real gate, not just that the function *can* accept one.
7. **Resume Tailor gate script — off/on/missing/corrupt instance:** new `skills/resume-tailor/scripts/tests/test_check_enabled.py` — exits 1 when off, missing, or corrupt; exits 0 only for a real `true`; never writes anything (assert no file created under a tmp `~/.claude/resume/`).
8. **Dashboard: `AddonGate` mounts nothing when off:** render `<AddonGate addon="portfolio" enabled={false} onEnable={fn}><Spy/></AddonGate>` with a local test-only `Spy` component that sets a flag if its function body ever runs; assert the flag stays `false` and the markup is `AddonNotSetUp`'s. This is the literal proof of "no tab data load runs while off," not a string match on `PortfolioHub`'s markup.
9. **Dashboard: `AddonGate` mounts children when on:** same harness with `enabled={true}` — `Spy` *does* render (flag `true`), proving the gate doesn't also suppress the on-state (regression guard pairing test 8).
10. **Dashboard: `AddonGate` loading state:** `enabled={null}`/`undefined` renders nothing (not the not-set-up card) — a still-loading `features` fetch must never flash "not set up" for a feature that's actually on.
11. **Dashboard: shared component, no per-add-on copy:** call the *same* imported `AddonNotSetUp` for all three addon ids and assert each renders its own name/description — proves one component serves all three literally, not a lookalike.
12. **Dashboard: unknown addon id:** `AddonNotSetUp` with an id outside the known three renders a clear "unknown add-on" message rather than crashing (malformed-input case).
13. **Dashboard: `instance:features` IPC, missing/corrupt/empty instance.json:** handler returns `{portfolio: false, resume_tailor: false, seal_ingest: false}` rather than throwing (mirrors `instance.test.js`'s corrupt-config cases through the IPC boundary).
14. **Dashboard: `setFeature` IPC, unknown addon name:** rejects/throws rather than silently writing an arbitrary key (misuse: a stale renderer sending a bad name).
15. **Dashboard: `setFeature` IPC, missing/corrupt existing file:** writes a valid, minimal `instance.json` rather than crashing or clobbering unrelated keys when the file is absent or unparsable.
16. **Dashboard: `setFeature` then `features()` sees the change without restart:** write `portfolio=true`, call `reset()` (as the handler does), then `features()` reflects it in the same process — proves "enables it without a reinstall" at the IPC layer.
17. **Migration, Gil's real shape:** `apply_legacy_grant({"features": {}})` (the literal current shape) returns all three known add-ons `True`.
18. **Migration, respects an explicit prior choice:** `apply_legacy_grant({"features": {"portfolio": False}})` leaves `portfolio: False`, still grants the other two.
19. **Migration, idempotent / malformed input:** running twice is a no-op the second time; non-dict `features` (`{"features": "yes"}`), missing `features` key, and unrelated top-level keys are all handled the same way `lib/instance.py` already treats a wrong-shaped config (read as blank, never crash, never drop unrelated keys).
20. **Ratchet:** `lib/tests/test_instance.py::test_no_new_engine_file_hard_codes_an_owner_account_or_machine` (or equivalent) run unchanged — `lib/addon_migrate.py` and `check_enabled.py` take their paths from `instance.instance_dir()` / relative-to-file lookups, never a literal home path or `G-Eskayo`.
21. **Verify-fails-without-a-matching-test:** each new gate point (ingest early-return, skill check-script exit code, `AddonGate`'s `enabled` branch, `setFeature`'s name validation, migration's idempotence) is the only thing standing between "off" input and "no work happens" in its own test above — confirmed by construction.
