## North-star fit

**Reuses:** `lib/instance.py:feature_enabled()` / `dashboard/electron/main/instance.js:featureEnabled()` — both already exist, already default every unknown/missing feature to `False` (`lib/tests/test_instance.py:107-113`, `dashboard/test/instance.test.js:70-73`), and already use `"portfolio"` / `"resume_tailor"` as example feature names. No new config-reading abstraction is needed — the gate this ticket builds is just *wiring real call sites to functions that already exist*. The IPC pattern this ticket adds (`window.api.instance.*`) reuses the exact `contextBridge` → `ipcRenderer.invoke('ns:method')` → `ipcMain.handle('ns:method', …)` shape already used for `health:*` (`dashboard/electron/preload/index.js:98-105`, `dashboard/electron/main/index.js:298-299`). The dependency-injection style for testability (pass dirs/exec in as params, as `portfolio.js:createPortfolio()` and `seal_beta_ingest.py:ingest()` already do) is reused rather than introducing mocking.

**Why simplest sufficient:** Of the three add-ons, only Seal ingest has a real background job + launchd plist (`lib/seal_beta_ingest.py`, `config/launchd/com.marvin.seal-beta-ingest.plist`); Portfolio has only an on-demand dashboard tab (`PortfolioHub.jsx` + `portfolio.js`, ~50 IPC handlers, no job); Resume Tailor has only a slash-command skill (`skills/resume-tailor/SKILL.md`), no dashboard presence and no job at all today. So the gate is added at exactly the three places that actually run something — the tab's initial mount (for Portfolio, where the criterion's own words "tab data load" live), the job's single pure entry point (`ingest()`, for Seal), and the skill's routing entry (for Resume Tailor) — not inside Portfolio's ~50 individual IPC handlers or the webhook-server's `/portfolio/*` endpoints, which aren't named by the acceptance criteria and would be unbounded extra surface for no criterion gain. No launchctl bootstrap/bootout orchestration is built: there is no existing automated installer that loads these plists today (Seal's plist is hand-installed by Gil, per its own header comment), so "stops its jobs" is satisfied by the job refusing to do real work when off, not by a new daemon-management subsystem — cheaper and avoids adding something nobody asked for (Watts check).

**Tokens:** spends a small, fixed amount now (one shared component, ~3 new IPC calls, one gate in `ingest()`, one gate in a SKILL.md phase) in exchange for never re-deriving "is this add-on on" logic per add-on later — every future add-on reuses the same `AddonGate`/`AddonCard` component and the same `instance:features` IPC call, O(1) per tab switch, no polling loop added.

**More capable, not more passive:** this doesn't automate a judgment call away from Gil — it makes the off/on choice explicit and visible instead of silent, which is exactly what protects a stranger's first install from accidentally running Gil's paid/personal add-ons, and protects Gil from the gate silently turning things off he already relies on (the migration piece below exists for that reason).

5. **Seal job, malformed instance.json:** `feature_enabled` backed by a corrupt `instance.json` (reuses `lib/tests/test_instance.py`'s bad-config fixtures) still reads as off, `ingest()` still skips cleanly.
6. **Seal job, repeated/concurrent runs while off:** two concurrent `ingest()` calls with the feature off both return `skipped` without taking the `fcntl.flock` lock or racing each other (assert the lock file is never created/opened).
7. **Resume Tailor gate script, off/on/missing-instance:** new `skills/resume-tailor/scripts/tests/test_check_enabled.py` — exits 1 when off or instance missing/corrupt, 0 when on; never writes anything, never touches `~/.claude/resume/`.
8. **Dashboard: tab data load gated (Portfolio):** `dashboard/test/*.test.js` — mount the gated tab wrapper with `instance.featureEnabled('portfolio') === false`; assert zero `portfolio:*` IPC calls fire (no `window.api.portfolio.*` invoked) and the shared not-set-up component renders instead of `PortfolioHub`.
9. **Dashboard: tab data load fires once enabled:** same harness with the feature on — the real tab's data-load calls do fire (regression guard, mirrors test 3 on the JS side).
10. **Dashboard: shared component, no per-add-on copy:** a test asserting the *same* component function (not a lookalike) is used for all three add-ons' off state (import identity check), covering "one shared component used by every add-on" literally, not just by eyeballing the diff.
11. **Dashboard: `instance:features` IPC, missing/corrupt/empty instance.json:** handler returns all-false for all three known add-ons rather than throwing (mirrors `lib/tests/test_instance.py`'s corrupt-config cases through the IPC boundary).
12. **Dashboard: setup button → IPC write, malformed existing file / concurrent write:** (shape depends on `setup_button` decision) if a write path is built: writing `features.<name>=true` into a corrupt or missing `instance.json` produces a valid, minimal JSON file rather than crashing or clobbering unrelated keys; two rapid clicks don't corrupt the file (last-write-wins is acceptable, a torn/partial write is not).

15. **Migration, idempotent / unrelated keys untouched:** running `apply_legacy_grant` twice is a no-op the second time; an unrelated top-level key (`owner`, `tickets_repo`) and non-dict garbage under `features` (e.g. `{"features": "yes"}`) are handled the same way `lib/instance.py` already treats a wrong-shaped config (read as blank, don't crash).
16. **Ratchet (`lib/tests/test_instance.py::test_no_new_engine_file_hard_codes_an_owner_account_or_machine`):** run unchanged — nothing added by this ticket should hard-code `/Users/gileskayo` or `G-Eskayo`; the new `lib/addon_migrate.py` CLI takes the instance path as an argument/`instance.instance_dir()` default, never a literal home path.
17. **Verify-fails-without-matching-test check:** each new gate point (ingest early-return, skill check-script, tab wrapper, IPC handler, migration function) has at least one test above that fails if the gate line is deleted — confirmed by construction since every gate is the only thing standing between "off" input and "no work happens" in its test.
