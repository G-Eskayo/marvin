## North-star fit

Reuses `qa_capture.store_entry()` (`skills/qa-agent/scripts/qa_capture.py:116-128`) — the exact id-lookup-then-add pattern (`col.get(ids=[...], include=[])` then `col.add` only what's missing) — scaled to a batch via the existing `BATCH = 500` chunking and `seen`-set dedup already present in `store_entries()` (`skills/qa-agent/scripts/qa_scan.py:610-639`). No new file, no new abstraction: it's a straight line-for-line rewrite of one function body, deleting the `existing`/`PAGE`/`offset` full-collection-scan loop (lines 616-624) and replacing the chunk-write loop's `col.add` with a filtered `found = set(col.get(ids=[...])["ids"])` check per chunk, mirroring `qa_capture.py`'s single-id version at N-id granularity. This is the simplest sufficient change — it is a drop-in replacement that keeps the same signature, same return value semantics, and same call sites (`main()`'s summary print at line 797 is untouched).

Token/resource saving is the entire point of the ticket (north star 1): the read cost moves from O(KB size) — a full-collection page-through that grows every scan/sweep/auto-fix pass across 15+ ingested repos — to O(scan size), i.e. `ceil(len(entries) / 500)` lookups bounded by `--max-files`. This is a backend fix with no user-facing behavior change, so "more capable vs. more passive" doesn't directly apply; it just removes wasted machine work so scans/sweeps finish faster and cheaper for whoever (human or agent) is waiting on them.

No design options are genuinely open here — the ticket fully specifies the mechanism and the existing sibling function is the reference implementation — so there is no Decisions section.

## Tests (write first)

All tests patch `qa_scan.CHROMA_PATH` to `tmp_path` (monkeypatch, following the ticket's explicit requirement) before calling `store_entries`, so none touch `~/.claude/chroma`. Entries are built as `{"id": ..., "document": ..., "metadata": {...}}` dicts matching what `scan()` produces.

1. **Double-store dedup**: call `store_entries(entries)` with N distinct-id entries → returns N; call again with the same entries → returns 0. (Acceptance criterion 2.)
2. **Mixed new/existing ids**: pre-store a set of entries, then call with a batch containing some of those ids plus brand-new ids → returns only the count of new ids actually added, and a subsequent query shows the pre-existing documents untouched. (Acceptance criterion 3, part 1.)
3. **Duplicate ids within one call**: a single `entries` list containing the same id twice (different or same document) → added once; return value counts it once. (Acceptance criterion 3, part 2 — exercises the existing `seen` logic still being applied before the new get/add path.)
4. **Chunk-boundary correctness**: construct >500 candidate entries (e.g., 1200) where some ids already exist in the collection and the pre-existing ids are deliberately placed so they fall in different 500-id chunks (e.g., indices 10, 510, 1010) → only the genuinely-new ids across all chunks are added, and the returned count matches exactly. (How we'll try to break it #1 — this is the test that would fail if `BATCH` chunking or the `found` set lookup is off-by-one or chunk-local instead of global.)
5. **Empty entries list**: `store_entries([])` → returns 0 and does not call `chromadb.PersistentClient(...)` / open a write at all (assert via monkeypatching `chromadb.PersistentClient` to raise, or spy, confirming it's never invoked). (How we'll try to break it #2.)
6. **`dry_run=True`**: `store_entries(entries, dry_run=True)` with a non-empty list → returns `len(entries)` and never touches Chroma (same no-call assertion as #5, with non-empty input this time to make sure the dry-run short-circuit precedes any chunking/get/add). (How we'll try to break it #3.)
7. **No `limit`/`offset` call**: a static/behavioral check that `store_entries` never calls `col.get` with `limit=` or `offset=` kwargs — implemented by wrapping/spying on a fake collection's `get` method and asserting none of the recorded calls include those kwargs. (Acceptance criterion 1 — this is the regression guard against reintroducing the full-scan loop.)
8. **Large single-chunk entries with no pre-existing ids** (misuse case the ticket's break-list didn't name: all-new large batch): 1000 brand-new entries, nothing pre-stored → returns 1000, and exactly `ceil(1000/500)=2` `col.get` calls happened (confirms the lookup still scales with scan size, not KB size, which is the actual perf claim being fixed).

Tests 1–4 and 7–8 need a real `chromadb.PersistentClient` against `tmp_path` per the ticket's explicit instruction (testing against the real collaborator, not a mock, so Chroma's actual id-filtering/dedup semantics are exercised) — this matches the existing untested-but-prescribed pattern and needs a `chromadb` import available in the dev venv (`~/.agents/venv`), which `qa_capture.py`/`qa_scan.py` already depend on at runtime. Tests 5–6 use a lightweight fake/spy collection (no real Chroma call should happen at all in those paths, so a spy is the correct tool there, not a mock hiding real rules — nothing real is being skipped since nothing should run).
