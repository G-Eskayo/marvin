## North-star fit

**Reuses:** `lib/session_start_report.py:51-52` (`_now() -> datetime: return datetime.now(timezone.utc)`) and `lib/session_start_report.py:396` (`_check_digest`'s `today = _now().astimezone().strftime("%Y-%m-%d")`). This exact "freeze `_now()`, then `.astimezone()`" seam is already the established, tested pattern for date-sensitive logic in this repo (`lib/tests/test_health_checks.py`, `lib/tests/test_code_stale_guard.py` both monkeypatch a module's `_now`). I'm reusing it in `daily_digest.py` instead of the ticket's literal suggested line (`TODAY = date.today().isoformat()`), for two reasons: (1) it makes `daily_digest.py`'s formula byte-for-byte identical to the reader it must agree with (`_check_digest`), removing any risk of two "equivalent but different" implementations drifting apart later; (2) `date.today()` is a module-level constant computed once at import, which is awkward to unit-test under a frozen clock without `importlib.reload` gymnastics — a `_now()`-based pure function (`_today_local()`) is directly callable from tests with `_now` monkeypatched, no reload needed. This is a one-line deviation from the ticket's suggested code, not from its intent (local date, matching the readers); verified `cross_machine_merge.py:68` and `research_digest.py` (lines 55/71/100) already use `date.today().isoformat()` correctly and need no change, confirming the ticket's "No other change needed" claim.

**Simplest sufficient approach:** 4 lines changed in one file (`daily_digest.py`), zero new files, zero new dependencies (no freezegun needed — `time.tzset()` + TZ env var, already how this codebase would test OS-local-time code, is sufficient and POSIX-only is fine since this runs on macOS/Linux only).

**Cost:** negligible — one extra function call at import time, no runtime/network/LLM cost. Test additions are plain pytest, no new fixtures beyond stdlib `os`/`time`.

**Phone-OS / north star 5 fit:** directly serves "every machine works" — this *is* the fix that makes the daily digest file findable on every machine regardless of its timezone.

**More capable vs. passive:** pure infrastructure-correctness fix, no user-facing behavior change — N/A to the capable/passive test.
