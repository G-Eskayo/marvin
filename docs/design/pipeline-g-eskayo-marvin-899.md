## North-star fit

**Reuses:** the entire staleness primitive already exists and is correct — `lib/health_checks.py:37` (`STATUS_TOLERANCE_S = 20*60`, the sweep's actual allowed gap: 15 min cadence + 5 min buffer) is already written into `health-status.json`'s envelope via `stamped.write(...)` (`lib/health_checks.py:1992`), and `dashboard/electron/main/stamped.js`'s `fromData()`/`readStamped()` (built for marvin#1223, PR #1247) already computes `ageS` and `stale = ageS > tolerance_s` from it, exposed today through `health:status`'s `copy: {host, ageS, stale, legacy, toleranceS}` (`health.js:44-57`, wired at `index.js:470`). `boot_data.js` already reads this via `readStamped` (`boot_data.js:39`) but only reads `ageS`, discarding `stale`, and recomputes its own freshness check by hand. `stamped.js` also already exports `ago()`, an age formatter in exactly the "4 min ago / 3 h ago" shape the ticket's own example text uses (`stamped.js:52-58`), used today by `describeCopy()`. So this ticket needs **no new staleness computation and no new backend work** — it's wiring three UI surfaces to a primitive that already exists, plus fixing two display bugs that let "stale"/"bad data" masquerade as healthy.

For the two new presentation-logic units, I reuse established repo patterns rather than inventing a new shape: `dashboard/src/lib/pr_fetch_status.js`'s `reviewDotStatus()` (pure function → `{dot, note}`, consumed by `App.jsx`'s tab-dot rendering) is the template for a new `healthDotStatus()`; `dashboard/src/lib/boot_view.js`'s `bannerTone()`/`subtitleText()` (pure derivation over a `verdict` object) is the template for the new Health-tab verdict logic. Every `src/*` consumer already keeps its own tiny local `ago()` (6 existing copies: `AgentsPanel.jsx`, `HealthDashboard.jsx`, `ReachRow.jsx`, `TicketAgentsPanel.jsx`, `ToolsView.jsx`, `pr_fetch_status.js`) because renderer code can't import `electron/main/*`; I follow that same convention rather than trying to share one. `boot_data.js`, however, *is* main-process code already importing from `./stamped.js`, so there I import `ago()` directly instead of writing a fourth copy.

**Simplest sufficient approach:** no new polling, no new tolerance constant, no new IPC channel. Pure plumbing (surface fields that are already computed) plus closing two latent "shows healthy when it shouldn't" bugs that the ticket's own break-it list exposes.

**Resources:** zero new runtime cost — no new timers, no new Claude calls, no new files on disk. Token/compute cost of this change is confined to a few small pure functions and their tests.

**Phone-OS direction:** this is exactly the "nothing broken silently" leg of Healthy (CONTEXT.md "Vitals") — the verdict becoming untrustworthy without saying so is the kind of silent failure that a phone-resident MARVIN can't afford, since there's no one glancing at a dashboard to notice via some other cue.

**User impact:** strictly more capable/informed — Gil currently has no way to tell "it's green because the sweep said so 3 hours ago" from "it's green right now," and `OverallBadge` can currently show "All checks healthy" on a `null`/garbled `overall` or on zero checks. Fixing this removes a trust gap rather than removing a task from him.

## Existing bugs this ticket's break-it list exposes (fix as part of this ticket, not separately)

1. `OverallBadge` (`HealthDashboard.jsx:127-147`) chooses its headline text by `overall === 'red' ? … : overall === 'yellow' ? … : 'All checks healthy'` — any other value (`null`, `undefined`, `'grey'`, a future typo) falls through to the **green, healthy** branch. `boot_data.js`'s own `level()` helper already documents the correct rule two files over: *"unknown severity is a warning, never green"* (`boot_data.js:17`). `OverallBadge` never got that guard.
2. `OverallBadge` trusts `status.overall` even when `status.checks.length === 0` (a sweep that "ran" but wrote an empty/garbled payload with a fresh timestamp — ticket's own "writes a partial snapshot" case). `boot_data.js`'s `verdictOf()` already guards this (`!health || !counts.total` → `tone: 'unknown'`, `boot_data.js:142`); `OverallBadge` has no equivalent, so the big "No health data yet" panel below it can be true while the badge above it still says "All checks healthy."

## Decisions
<!-- marvin:decisions -->
### future_clock: A snapshot timestamped in the future (system clock was set forward, matching the ticket's own "change the system clock forward and back" break-it case) currently reads as age 0 / not stale (`stamped.js` clamps `ageS` to 0 and sets a separate `future: true` flag nothing downstream reads). Should the verdict trust it as fresh, or refuse to call it fresh until the clock issue clears?
- [ ] A: Trust it as fresh (age 0) — simplest, matches today's `stamped.js` behavior, no new UI state
- [ ] B: Treat a future-dated snapshot as untrustworthy too (reuse the same amber "can't verify" treatment as a stale one, wired off the existing `future` flag), until a later snapshot is no longer in the future

### partial_wording: A sweep that runs but writes an incomplete snapshot (fresh timestamp, but `checks: []` or a garbled `overall`) is a different failure than a frozen sweep — the timestamp is honest, the payload isn't. Should the verdict line/tab dot/boot verdict show this with the same "verdict is N old · sweep hasn't run" wording as a stale snapshot, or its own distinct wording (e.g. "sweep ran but wrote nothing usable")?
- [ ] A: Same wording as stale (one amber state, simpler, one fewer string to keep in sync across three surfaces)
- [ ] B: Distinct wording (more honest — the sweep *did* run, saying it didn't would be false; costs one more string per surface)

## Tests (written first)

From "How we'll try to break it":
1. **Freeze the sweep job** — `health-status.json`'s `generated_at`/`tolerance_s` stop advancing while `now` keeps moving: `verdict_line.js`, `health_dot_status.js` and `boot_data.js`'s `verdictOf()` must each flip from whatever `overall` says to the amber/stale state once `ageS > toleranceS`, even though the last recorded `overall` is `'green'`.
2. **Change the system clock forward and back** — a snapshot with `generated_at` ahead of `now` (`future: true`, `ageS` clamped to 0): per the `future_clock` decision, assert the chosen behavior; either way, assert `ageS` is never rendered negative and nothing throws. Then clock moves back to normal: age tracks `now - generated_at` again with no leftover "future" state stuck on.
3. **The sweep runs but writes a partial snapshot** — fresh `generated_at`/within tolerance, but `checks: []`, or `overall` missing/`null`/a garbled string (`'purple'`): all three surfaces must not read as healthy. Per the `partial_wording` decision, assert either the shared stale wording or the distinct one.

Additional misuse the ticket's list didn't name, applying the ticket's own "try to break it" standard:
4. **Bad/empty/malformed input** — `health-status.json` missing entirely, truncated/corrupt JSON, or `tolerance_s` present but `0`/negative/non-integer (already guarded by `stamped.js`'s own tests at the primitive layer — add one consumer-level test per surface confirming "missing file" still renders as the existing "unknown"/"no data" state, not amber-with-an-age and not green).
5. **Each dependency failing** — `window.api.health.status()` rejects (IPC error) in `App.jsx` and `HealthDashboard.jsx`: the tab dot and verdict line must keep their last-known state (or a neutral "unknown"), never crash, never show green on a rejected promise. (Mirrors the existing `.catch(() => {})` pattern already in both files — add a regression test that the stale/age state introduced here doesn't quietly rely on a resolved promise shape it won't get on rejection.)
6. **Repeats / concurrency** — clicking "Refresh now" while the verdict is already showing the amber stale state, and the in-flight refresh resolves with a fresh snapshot: assert the badge transitions cleanly from amber-stale straight to its post-refresh state with no flash of the old amber text (covers AC3's "a fresh sweep clears the amber" at the UI layer; the sweep de-duplication itself is #837's, not re-tested here).
7. **Wrong permissions / a person's mistakes** — a hand-edited `health-status.json` that's valid JSON but has `host` set to a different, unregistered Mac name, or a `tolerance_s` someone hand-set absurdly low/high: assert age/stale still compute off the file's own `tolerance_s` (already `stamped.js`'s job) and the three surfaces don't misattribute it to "this Mac" when `host` disagrees — scoped to "doesn't crash and doesn't say something false," not full peer-identity resolution (that's #898).
8. **Stale state left over from a previous run** — a leftover `health-status.json` from hours ago on app relaunch (boot's own scenario): boot verdict must show the stale/amber state with age on the very first paint, not only after the first live poll (since `App.jsx`'s/`HealthDashboard.jsx`'s 60 s polling doesn't apply to the one-shot boot sequence).
9. **Regression on the un-stale, healthy path**: every existing green-path assertion in `boot_data.test.js` (`'ALL SYSTEMS NOMINAL'`, `'1 CRITICAL · OPEN HEALTH'`, etc.) gets updated to its new age-suffixed text, not deleted — proving the age addition didn't just overwrite correctness with a looser matcher.
10. **`OverallBadge`'s two bugs above**, each with its own test: an `overall` of `'grey'`/`null`/`'purple'` never renders "All checks healthy"; `checks.length === 0` with `overall: 'green'` never renders "All checks healthy" either.

Mocked vs real: `window.api.health.status()`/`.refresh()` are mocked at the test boundary (as `HealthDashboard`'s existing tests, if any, and `App.jsx`'s existing conventions do — there's no real Electron process in `vitest`), but the *shape* fed to the mock in every test is the real shape `readHealthStatusFresh`/`readStamped` actually produce (confirmed above, not invented) — so the mock can't hide a contract mismatch. `boot_data.test.js` already writes real JSON files to a temp tree and reads them through the real `readStamped`, so its new tests exercise the real staleness primitive end-to-end, not a stub of it.
