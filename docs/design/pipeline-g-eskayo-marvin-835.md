## North-star fit

**Reuses before adding anything new:**
- `lib/health_checks.py:1241-1242` `JOB_PLACEMENT` — already derives per-job machine placement from `job_catalog.JOBS`, proving the exact "catalog, not plist-glob" pattern `coverage()` needs. I copy this derivation style rather than inventing a second one.
- `lib/task_dispatch.py:148` `accepts(info, need)` + `GENERAL` constant — the existing, already-imported (`health_checks.py:33`) primitive for "does this registry entry take untagged/general work." This is the generic, non-hardcoded test for "is this machine calibrated for ordinary duty," so mac-mini-2012 isn't special-cased by name — any future specialised node (another box, a bench-only Mac) gets the same treatment automatically.
- `lib/health_checks.py:48-50` `_result()` (always sets `checked_at`) — the existing single source of a well-shaped result; the bug is that three producers (`mirror_health._row`, `output_contracts.evaluate`, `purpose_metrics.health_findings`) build dicts by hand and skip it. Fix: make each of those three set `checked_at` themselves (they're separate modules `health_checks.py` imports, not vice versa, so they can't call `_result()` directly without a new import edge).
- Dashboard's existing `unmonitored` severity (`HealthDashboard.jsx:28`, dashed grey card, already excluded from `overall_severity()` since that function only tests for literal `"red"`/`"yellow"`/`UNKNOWN`) — reused as mac-mini-2012's non-counting status, instead of inventing a new severity colour/behaviour.

**Simplest sufficient approach:** no new registry field, no new "calibrated" flag, no new UI grouping concept. Four small, surgical changes in `lib/health_checks.py` plus `checked_at` one-liners in the three producer modules plus one `job_catalog.py` field correction. Vitals' "system grouping" / "decision lane" language in `CONTEXT.md` is explicitly future work this ticket exists to prepare the ground for ("needed before any Vitals view, so it isn't born red") — building that grouping now would be scope creep the ticket's four ACs don't ask for.

**Where it spends/saves:** removes a whole check category (`cron:*`, ~1 per discovered job) and a background thread per sweep; adds one small `task_dispatch.accepts()` call and a cheap dict comprehension over `job_catalog.JOBS` (32 entries) in `coverage()`. Net: fewer tokens/cycles per 15-minute sweep, not more.

**Phone-OS direction:** neutral — pure backend correctness, no new surface.

**More capable or more passive:** more capable — Gil currently has to mentally discount red cards he's learned not to trust (coverage noise, a box that was never going to be "always on," two false sync cards). Removing the false signals makes the one remaining signal (genuinely red = genuinely broken) trustworthy again, which is the whole point of `docs/adr/0033` and this ticket.

## What I found already covers part of this, and what's genuinely missing

- `discover_launchd_jobs()` (`lib/health_checks.py:284-297`) globs every `com.*.plist` in `~/Library/LaunchAgents`, excluding only `com.apple.BKAgentService`. It has no Dropbox/Google-specific carve-out, so any third-party updater plist (Keystone, DropboxMacUpdate, etc.) is counted as a "discovered job," inflates `coverage()`'s denominator, and shows as an unmonitored card. This is a real, present bug, not historical.
- `cron:*` (`check_cron_job_log`, `_cron_job_logs`, lines 300-316, 1788-1793) is a thin wrapper over `cron_health.check_job()`'s offset-tracked log scan — exactly as the ticket describes, clearing "on time, not on a pass."
- `contract:*` (`lib/output_contracts.py:evaluate`, line ~161) and `purpose:missed` (`lib/purpose_metrics.py:health_findings`, line 1008) are both still `"red"` today, with no `checked_at` key in either producer — confirmed by reading both functions directly. `lib/mirror_health.py:_row()` (line 244) also omits `checked_at`.
- `machine:mac-mini-2012`: the registry (`~/.claude/marvin-network.json`) already correctly marks it `"os": "linux"`, so `remote_macs()` already excludes it from repo-sync/machine-state checks. But `check_machine_reachability()` iterates `remote_devices()` (every registered device, Mac or not) and, for `kind: "desktop"` with no `grace_hours`, `classify_unreachable()` returns unconditional `"red"` whenever it's unreachable — there's no carve-out for a device that `accepts` only `["security","quarantine","test","bench","box-build"]` (never `"general"`). Ticket `#623` (calibration) is closed but its own comments show the claim was released with no completed calibration run; the box's registry entry still has no `"general"` tag today, which is the generic, already-existing signal this ticket should key off instead of a name check.
- `job_catalog.JOBS["cron-health"]["consumer"]` is literally the string `"Health cron:*"` — once `cron:*` is deleted this becomes a dangling reference inside the catalog that `job_catalog.waste()` would silently trust; it needs correcting to its real consumer (the session-start report, per `cron_health.py`'s own docstring and ADR 0033).
- `config/loops.json`'s `research-action` loop watches `contract:research-digest` with `broken_when: "red"` — the one loop entry that could be affected by downgrading `contract:*`'s red case to amber. In practice this contract (1-day `within_days`, read daily) essentially never reaches the 30-day-cut red case, so this is low risk, but it's a real downstream consumer I'm flagging rather than silently affecting.

## Decisions

<!-- marvin:decisions -->
### contract-blocking: `contract:*`/`purpose:missed` are supposed to stay red "only when they also block something else" — nothing in the codebase today detects cross-check blocking. Ship v1 unconditionally amber, or build a minimal blocking detector now?
- [ ] A: Ship v1 with `contract:*`/`purpose:missed` always amber (yellow); no blocking-detection exists yet, and building one is real new scope beyond this ticket's four ACs. A future ticket can add real "also blocks X" escalation once a concrete blocked-by case shows up.
- [ ] B: Block this ticket on first building a minimal "does this finding also block a red check" detector (e.g., cross-reference `config/loops.json`'s `watches`/`broken_when` wiring) before shipping the severity change.

### uncalibrated-box-row: mac-mini-2012's reachability row folds `mirror:sync@mac-mini-2012` in and is excluded from `overall_severity()`'s inputs regardless of its real mirror state (even a genuine, currently-failing mirror sync). Is that intended, or should a real mirror failure still count once it's severe enough?
- [ ] A: Fully excluded, always — matches the ticket's literal wording ("doesn't count toward the verdict"); the box's own `errors.jsonl` entries still surface in "Recent errors" regardless, so a real mirror outage isn't silent, just not in the pass/fail verdict.
- [ ] B: Excluded from the *overall* verdict but the folded row can still show real red/yellow for a genuine mirror failure (just never escalates `overall_severity()` — i.e. carve it out of `overall_severity()`'s input list specifically, not by giving it a non-red/yellow severity string). More faithful to #910's original intent (mirror failures must be visible), slightly more code (one exclusion list instead of one severity string).

## Tests I will write first

Covering the ticket's "How we'll try to break it," then the misuse cases it didn't list:

1. **A job that fails then passes: red until the pass, green after.** `evaluate_machine_state`'s `jobs:exit` row already derives this from the live `job_exits` snapshot with no time-based clearing — write a regression test proving it stays red across two sweeps 10 days apart with no intervening pass, and turns green the sweep after a passing run, to lock in the "reds stay red until something passes" decision now that `cron:*` (which cleared on time) is gone.
2. **The 2012 box calibrated mid-run.** Two calls to the new reachability logic with the same device whose `accepts` list differs (without `"general"`, then with it) must switch from the folded/`unmonitored` row to an ordinary counting row — nothing cached/sticky.
3. **A catalogued job with no plist on this Mac.** `coverage()` sourced from `job_catalog.JOBS` must still count a job meant for `"mini"` while running on `"laptop"` (no local plist) as covered — coverage answers "does it have a check," not "is it loaded here" (that's `jobs:exit`/`JOB_PLACEMENT`'s job).
4. **An empty job catalog.** `coverage({})` → `total == 0`, `fraction == 1.0`, `unmonitored_jobs == []` (vacuously full, matching today's empty-`discover_launchd_jobs()` behaviour).
5. **Malformed/missing `reporter` field** (a person's mistake adding a new catalog entry) — `coverage()` must use `.get("reporter")`, not `["reporter"]`, and flag the job as uncovered rather than raising.
6. **Third-party plist noise** — a `com.google.keystone.agent.plist`/`com.dropbox.DropboxMacUpdate.plist` on disk must not appear anywhere in `coverage()`'s totals or `unmonitored_jobs` once `coverage()` no longer calls `discover_launchd_jobs()`.
7. **Each dependency failing**: GitHub unreachable while building `contract:*`/`purpose:missed` (existing `except` branches) must still produce a result with `checked_at` set — covers the two except-paths that currently build dicts by hand.
8. **Malformed `accepts`** (not a list) on a registry entry — must be treated as "not general" (fails closed, per `task_dispatch.accepts()`'s own documented behaviour), landing it in the folded/non-counting row rather than crashing or silently counting as general.
9. **An entry with no `accepts` key at all** (predates the field) — must be treated as general (existing Macs' behaviour must not regress).
10. **Severity regression tests**: `output_contracts.evaluate()`'s 30-day-cut case and `purpose_metrics.health_findings()`'s missed-purpose case both change from `"red"` to `"yellow"` — update `lib/tests/test_output_contracts.py:48-52` and `lib/tests/test_purpose_metrics.py:84-87` (currently asserting red) to assert yellow/amber, and add a new case where the "also blocks something else" escalation path is exercised according to whichever Decision option is chosen above.
11. **Stale cached severity** — a `machine:mac-mini-2012` row from a sweep taken before this change (literally cached old red severity in `health-status.json`) must not wedge `overall_severity()` red forever; since nothing persists severities across sweeps except the on-disk snapshot the next sweep overwrites wholesale, this is a one-line test that `run_all()` always recomputes fresh (no accumulation).
