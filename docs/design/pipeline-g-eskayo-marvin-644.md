The one genuine (if currently latent) defect is a **starvation bug**: `_score_one` always retries the single globally-oldest unscored PR (`pick_unscored`, `min(..., key=number)`); if that PR's mutation check ever crashes or times out, the exception is swallowed (`lib/auto_merge_shadow.py:224-225`) and `scored` is never updated, so the *exact same* PR is picked again next hour, forever — blocking every newer PR's score silently. ## Tests (write first)

Ticket's embedded attack list (AC #3) plus the generic misuse categories, scoped to `lib/auto_merge_shadow.py` (the layer that's actually under-tested — `mutation_check.py` itself already has thorough timeout/huge-PR/malformed coverage, confirmed by reading `lib/tests/test_mutation_check.py`, so not duplicated here):

1. **Reproduce the real bug**: observe a PR with no score yet (`ask: pending`), then observe it again later once a real score arrives (`auto`); `report()`'s `would_merge` and `line` must reflect the *live* state, not the frozen first-seen one. (Direct regression for the root cause, built from the real production shapes I found in the state file.)
2. **Disagreement across a verdict change**: a PR whose *early* verdict was "ask: pending" but whose *later* (pre-close) verdict was "auto" and which Gil then closed/reverted must be flagged as a disagreement — today this is structurally impossible to detect, defeating the shadow report's whole purpose.
3. **No regression**: the existing `test_shadow_starts_on_the_first_run_and_records_each_pr_once_with_its_first_verdict` keeps passing unchanged — `first_seen`/the raw frozen fields stay as they are (the dashboard already correctly reads `.current`; only `report()`'s field choice changes).
4. **Crashing mutant run**: `_score_one` hits an exception (e.g. `git worktree add` raises) — the failure is recorded (not silently dropped), and a second consecutive failure on the same PR@sha causes the *next* call to skip it in favor of the next-oldest unscored PR (no starvation).
5. **Timeout**: same as #4 but via a `subprocess.TimeoutExpired`-shaped failure — logged, retried-with-deprioritization, never silent.
6. **Stated reason after repeated failure**: once a PR has failed scoring `MAX_CONSECUTIVE_FAILURES` (3, matching `run_ticket.py`'s existing convention) times at the same commit, the PR body gets a "Score: unknown (scoring failed repeatedly: …)" section via the existing `render_section`/`merge_bodies` path — satisfies AC #1 ("stated reason it can't").
7. **PR closed mid-scoring**: the PR disappears/closes between being picked and the `gh pr edit` write-back — the pipeline step must not crash and must not retry against a PR no longer in the open list (it naturally drops out of the next `gh pr list --state open`).
8. **No wasted repeats**: two consecutive `_score_one`/`run()` calls against an unchanged, already-successfully-scored PR score it exactly once, not twice (ties to AC #4's cost claim).
9. **Concurrency**: two interleaved `_Locked` writers touching the new per-PR failure-count field round-trip safely (same lock already protects `scored`).
10. **Missing checker ≠ failure**: `import mutation_check` failing (not installed) stays the existing silent no-op — must not be miscounted as a "failure" and must not get a body edit (distinguish "no checker" from "checker crashed").
11. **Cost is a checked number, not a claim**: a test asserts the reported/logged duration for a scan is bounded by the existing `wall_clock_budget_sec` constant, so "the space and time cost per scan is stated" is backed by code, not prose.

No mocking of `mutation_check`'s own scoring logic (that's the already-tested real collaborator); only the GitHub/git subprocess boundary is faked for the crash/timeout/closed-PR cases, since those are genuinely about *our* code's reaction to an external failure, not about GitHub's real behavior.
