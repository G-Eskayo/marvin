## North-star fit

**What's actually wrong with the last attempt, in one sentence:** every must-fix bug the review found was logic that got hand-written *inline*, in the file least able to be unit-tested (`index.js`'s `checkRepoHead` closure) or as a second ad hoc code path next to an existing correct one (`docs_search.js`'s `mergeAndWrite` inventing `generated_at`; `docs_service.js`'s cache-hit branch skipping the hook the cache-miss branch calls). The stub test (`docs_repo_head_check.test.js`, six `expect(true).toBe(true)`) is a symptom of the same cause: there was nothing pure to test, so nothing real got written. This revision's one real change in shape is to stop adding new ad hoc logic and instead **reuse the one piece of this codebase that already gets this exact comparison right and already has real tests for it**, then make every other fix a small, named, single-purpose operation instead of a flag or an early return.

**Reuses, verified against the actual current code in this worktree (not the aspirational description from the last design doc):**
- `createChangeDetector`'s inner loop (`webhook-server/gh_watch.js:24-39`, tested in `dashboard/test/gh_watch.test.js:13-56`) — `const previous = etags.get(repo); etags.set(repo, res.etag); if (previous !== undefined && previous !== res.etag) onChange(repo)`. This is the exact rule `checkRepoHead` needed and got backwards (`index.js:427-430` sets the etag *before* checking `has()`, so the check is always true). Rather than hand-fix that one line again, I extract the rule itself as a new sibling primitive in the same file, `createRepoOpenChecker`, built from this exact logic (capture-before-write, skip on non-200/no-etag, fire `onChange` only when a *previous* value existed and differs). I can't reuse `createChangeDetector` as-is, though: its `tick(repos)` forgets any key not present in that call's list (`gh_watch.js:25-27`), which is correct for a periodic full-registry sweep but wrong for an on-demand single-repo check fired by whichever project happens to be opened — calling `tick([oneRepo])` on every open would delete every other repo's remembered etag. So the new primitive keeps `createChangeDetector`'s comparison rule, drops its "forget" housekeeping, and checks one repo per call instead of a list. Both now live in `gh_watch.js` and both get real unit tests in `gh_watch.test.js`, the same way `createRepoHeadProbe` and `createChangeDetector` already do — this also directly replaces the stub test file.
- `docsForRepo` (`docs_search.js:15-17`, already exported and tested) — reused in `docs_service.js`'s `tree()` to decide cache-hit vs. cache-miss (`docsForRepo(idx, id).length > 0`), replacing the last attempt's `treeFromDocs(...).length > 1` heuristic, which misses the common case of a repo with only a cached `CONTEXT.md` (`docs_service.js:99` today — confirmed live: that repo's tree renders `[CARD, {CONTEXT.md}]`, length 1, so it refetches from GitHub on every single open even though it's fully cached. That's the exact bug the ticket exists to kill, still present).
- `treeFromDocs` → `groupDocSections`/`isDocMarkdown` (`doc_paths.js`) — already correctly wired in the current code (`docs_service.js:14-46`); kept unchanged, this part of the last attempt was right.
- The per-repo single-flight `Map` already in `docs_service.js:82` (`treeInflight`) — the shape is reused, not reinvented, for a second, smaller gap: `content()` has no such guard, so two concurrent opens of the same never-fetched file double-fetch. Same `Map`-of-inflight-promises shape, new key (`${id}:${filePath}`).
- The lazy-getter DI convention (`getCatalog`, now `getIndexer`) — unchanged, still the right way to break the `docsService` ↔ `docsIndexer` circular construction.

**What's new, and why it's the smallest sufficient addition, not a new flag:**
- `createIndexer` currently has exactly one write path, `applyRepoDocs(repoId, docs, fetchedAt)`, which *replaces* a repo's entire doc set. That's correct for "a whole repo was just refreshed" (tree cache-miss, HEAD-change refresh) but wrong for "one file was just fetched" — `content()`'s miss path calls it with a single-element array, which silently deletes every other cached file for that repo (confirmed live at `docs_service.js:152-158`: `mergeAndWrite` does `docs.filter(d => d.repo !== repoId)` then appends only the new array, whole-repo, every time). The fix is not a `{merge}` boolean on the same function (that's the pattern already rejected once) — it's a second, differently-named operation for a genuinely different operation: `upsertDoc(doc)`, which merges by `(repo, path)` and never touches `repos[repoId].fetchedAt` (a single file arriving is not "the repo was refreshed"). Both operations share one tiny private `commit(next)` helper so the persist-safety fix from the last attempt (`current = next` before `persist`, swallowed sync/async failure) isn't duplicated.
- `raw` text on doc entries. `content()` must return the exact bytes the renderer asked for (`DocsExplorer.jsx:135` does its own `notebookToMarkdown` client-side on whatever `content()` returns), but the index only ever stored `searchableText(...)` — already markdown-converted for `.ipynb`. Confirmed live: cache-hit returns `cached.content` (converted), cache-miss returns the original `text` (raw) — a notebook renders differently depending on whether it happened to be cached yet. Storing a second field is the direct fix, but to respect "minimise resources": `searchableText` returns the *same reference* for every non-notebook path (`docs.js:105`, identity return), so `content !== text` is already a free, correct test for "this file actually needed conversion." `raw` is only ever written when that's true — i.e. only for notebooks, the one case that needs it. No duplicated storage for the other ~95% of docs.
- `persistIndex(index, indexPath)`, extracted from `buildDocsIndex`'s existing two-line tail (`mkdirSync` + `writeFileSync`) and passed as `persist` when `index.js` constructs the real `createIndexer`. Today `docsIndexer = createIndexer({ build, getLocal })` (`index.js:521-524`) has no `persist` at all, so every `applyRepoDocs`/`upsertDoc` this ticket adds is memory-only and is gone on app restart — the entire point of the ticket (stop re-fetching) silently resets every launch. This was filed as a "note" rather than a must-fix, but it's load-bearing for the ticket's own acceptance criteria, costs two lines to wire, and the write logic already exists and is already tested (`buildDocsIndex` tests) — just not reused.

**Token/compute cost:** unchanged from the previous estimate — a few dozen lines removes 2-4 `gh api` calls per click down to 0 after first fill, plus one conditional request per project open. The `raw`-only-for-notebooks choice keeps the on-disk/in-memory index at the same order of magnitude it was before this ticket, not double.

**Accepted, not fixed:** `createRepoHeadProbe` uses raw `fetch` + `process.env.GH_TOKEN` rather than the `gh` CLI gate. This is not a new deviation — it is the exact same pattern `createGithubProbe` already uses one function above it in the same file, for the already-shipped issue-watch loop. Consistent with the existing precedent; changing it is out of scope for this ticket and would be a different ticket against both probes at once.

**User capability:** unchanged from the ticket's own framing — Docs tab stays instant for every project regardless of whether it's cloned locally, with its age always visible so a stale copy is never mistaken for live. More capable, not more passive.

**CONTEXT.md:** the existing entry (`CONTEXT.md:574`, added by the last attempt) already describes the mechanism but describes the *buggy* version ("fires when a live GitHub tree is served" — true today only on cache-miss, which is exactly finding #2). It needs correcting to describe the actual fixed behavior: one conditional request per GitHub-sourced project open regardless of cache state, via `createRepoOpenChecker` in `gh_watch.js`.
