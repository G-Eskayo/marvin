## Why the previous attempt failed (grounded in the actual current file, line-by-line)

1. **`lib/tests/test_portfolio_research.py:522-553` (`test_plan_mode_makes_no_writes`).** `main()` always resolves the template via `project_catalog.portfolio_repo_path()` (line 402 of `portfolio_research.py`) regardless of how `source_repo` was passed in. The test writes a `template.json` at `tmpdir/"template.json"` and never points anything at it — no `MARVIN_PORTFOLIO_PATH` override, no template at the path `main()` actually computes (`<portfolio_repo_path()>/templates/content/app-product.json`). On a machine without the real portfolio repo checked out, `main()` hits `sys.exit(1)` (template not found) and the test fails outright; on a machine that happens to have it, the test is silently exercising the real repo's real templates, not the fixture. Nothing in the test checks that `--plan` actually printed anything, either.
2. **`lib/tests/test_portfolio_research.py:467-484` (`test_double_escape_regression_query_string_url`).** The assertion is `assert 'href="...&amp;other=data"' in html or 'href="https://example.com/docs' in html`. The second disjunct is satisfied by a truncated or still-double-escaped href (`&amp;amp;other=data` still contains the substring `href="https://example.com/docs`), so this test cannot fail even if the escaping bug came back.
3. **`lib/tests/test_portfolio_research.py:106-113` (`test_an_entry_missing_a_required_bullet_is_skipped_not_crashed`) and `parse_log`'s docstring (`portfolio_research.py:47`).** Both claim malformed entries "are skipped." Neither is true: `parse_log` returns the entry with `None` fields (test itself asserts `len(entries) == 2`, not 1), and `render_entry` will publish a `Yes`/`Careful` entry missing `What we took`/`Drives` as a Source-only callout — a half-empty box on the live public page. This is a real product-quality bug (not just a naming mismatch): a portfolio page showing a lone "Source: [link]" with nothing else looks broken, which the ticket's copy-quality framing (`feedback-portfolio-copy-sell-it`: never look sloppy) implicitly rules out. I'm resolving this as an engineering/robustness call, not an owner Decision — the "fail closed, don't render garbage" default in the north stars (and `feedback-no-unapproved-ui-changes`, which cuts against *adding* a visible-but-broken element) settles it without a product trade-off to offer.
