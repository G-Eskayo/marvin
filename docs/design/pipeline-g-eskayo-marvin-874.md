## North-star fit

**Reuses**: `lib/loops.py` (ADR 0083, marvin#1123) already *is* most of what #874 asks for. Its `fix` field — `{level, kind, arg}` — is literally captioned in ADR 0083 line 31 as **"the #874 shape."** `LEVELS = ("auto", "one_tap", "decision")` already exists. `fix_plan()`/`run_fix()` already execute an allowlisted, validated set of `FIX_KINDS` (`rerun`, `relogin`, `install_job`, `rollback`, `ticket`, `decision`) with argument patterns (`ARG_RE`) checked on every registry load (`validate()`). The Loops panel (`dashboard/src/components/LoopsPanel.jsx`, `dashboard/electron/main/loops.js`, `dashboard/src/lib/loops_view.js`) already renders every loop's fix as a button and already calls an IPC (`window.api.loops.fix(id)` → `loops.py fix <id>`) that runs it. `job_events.job_run()` + `loops.read_runs()`/`loops.failed_in_a_row()` already give "N consecutive failures" for free from a job's own run log. `graphify_freshness.refresh()`, `cleanup_sweep.py` (already wired as loop `disk`, kind `rerun`, arg `cleanup-sweep`), and `project_catalog.refresh()` are the three concrete "safe actions" already sitting in the tree. **What's missing is one thing: nothing ever runs a fix automatically.** Every fix today — even ones the registry calls `"auto"` in spirit — waits for a human or the dashboard to press a button. #874 is that missing auto-run step, plus the 2-strikes demotion, plus closing three gaps in the registry (`code-graph`'s fix is currently a placeholder `ticket`, not a real rerun; no loop yet watches `catalog:fresh`; nothing distinguishes "safe to run with no one watching" at validation time).

**Correcting the ticket against the code**: the ticket's "What to build" says *"Extend the #836 fix field to `{level, action, undo?}`."* #836 ("every check carries its reason, fix, confidence, age and machine") is **still open** — `lib/health_checks.py`'s `RESULT_TEMPLATE` (line 41) has no `fix`/`reason`/`confidence`/`tolerance_s` fields at all today. There is nothing to "extend" there. The shape the ticket wants already exists, just living in `loops.py`/`config/loops.json`, not in `health_checks.py`'s per-check results — and ADR 0083 already claims it for #874. This plan builds on `loops.py`'s existing shape (adding the optional `undo` field it's missing) rather than retrofitting #836's broader, unrelated schema onto every health check — that's #836's own scope, and blocking #874 on it would be exactly the kind of mis-scoped rework that likely produced the prior "mixed" verdict.

**Simplest sufficient approach**: no new module, no new log format, no new IPC. Extend `loops.py`'s validated vocabulary with two new `FIX_KINDS` (`rebuild_graph`, `refresh_catalog`) for the two starter actions that have no backing launchd job to kick-start; promote the already-present `disk` loop's `rerun`/`cleanup-sweep` fix and the `code-graph` loop's fix from placeholder to `auto`; add one new `catalog` loop; wire the one missing step — an auto-run call, triggered off the health-check job's own already-scheduled sweep (no new poller, no new timer) — into `health_checks.py`'s `_cli()`, next to the two reactions already shaped exactly this way (`react_to_low_disk`, `react_to_accounts`).

**Resources**: spends nothing new at steady state — the auto-fix runner piggybacks on the health-check job that already runs every 15 minutes; every action it's allowed to take is already a tiny, already-existing, already-scheduled local operation. It *saves* a human click for the common case (Gil currently has to notice a red Loops row and press "Re-run" by hand).

**Phone-OS fit**: reachable, proactive, no new surface — fixes what's broken before Gil ever opens the dashboard.

**More capable or more passive?** This is explicitly the kind of mechanical, no-judgment-required repair (rebuild a derived cache, retry a transient job failure) the north stars say *should* be automated — it's Gil's own stated design (CONTEXT.md "Fix level"), not something that removes his judgment from anything that needs it. Real choices stay at `decision` level, untouched.

## Decisions

Four real forks came out of this research that change scope/blast-radius materially. I'm not guessing on these:

```markdown
<!-- marvin:decisions -->
### disk_dup: "The cleanup sweep" starter action already has an ad hoc fixer (`health_checks.react_to_low_disk`, hourly-throttled, pre-#874). Promoting loop `disk`'s fix to `auto` gives disk:space *two* live fixers. What should happen to the old one?
- [ ] A: Remove `react_to_low_disk` and its direct call in `_cli()`; the loops-driven auto-fix runner becomes the only path that clears a low-disk check. Rewrite its existing tests against the new path instead of deleting coverage.
- [ ] B: Leave `react_to_low_disk` exactly as is; have the new auto-fix runner skip any loop whose underlying check id starts with `disk:space@` so the two never compete.
- [ ] C: Don't promote the `disk` loop to `auto` in this PR at all — satisfy "the cleanup sweep" starter action with the allowlisted `rerun`/`cleanup-sweep` fix kind existing and reachable (manually, as today), and leave the auto-trigger decision for a follow-up once disk behavior under both paths has been observed.

### fourth_action: "Retry a failed job" (the 4th starter action) has many candidate loops already using `kind: rerun` at `one_tap` (health-sweep, daily-digest, research-digest, architecture-review, ...). Several of those call out to paid APIs, which an auto fix must never touch (AC 3). Which loop should be promoted to `auto` as the concrete "retry a failed job" example?
- [ ] A: `health-sweep` (reruns `health-check` itself — no budget, no other repo, but mildly self-referential: the sweep retrying its own job).
- [ ] B: `daily-digest` (reruns `daily-digest` — need to confirm it spends no paid API budget before promoting; if it does, this option is withdrawn).
- [ ] C: None — ship only the two unambiguous starter actions (code-graph rebuild, cleanup sweep) plus the new `catalog` cache-refresh loop as the generalized "retry a failed job" example (its action job `project-catalog` is itself a retry-on-red of a job), and leave promoting any other `rerun` loop to a later ticket once each candidate's budget/repo touch has been individually audited.

### undo_depth: CONTEXT.md's "Reversible" requires every auto fix to leave "a record of what it changed and an undo." For these four starter actions nothing is destroyed (a derived cache gets rebuilt, a job gets restarted) — there's no real rollback target. How much "undo" should this PR actually build?
- [ ] A: A one-line free-text `undo` field in the registry (e.g. "disposable tier, ADR 0065 — nothing it clears is irreplaceable") recorded on the `loopfix-<id>` job_events run detail. No restore mechanism, since nothing needs restoring.
- [ ] B: Same, plus the Loops panel UI surfaces that `undo` line to Gil when a fix has run.
- [ ] C: Require an actual restore path per action (e.g. snapshot `graph.json` before `rebuild_graph` runs, and add a real `undo` subcommand) — more faithful to the letter of "Reversible," materially more work, and arguably unnecessary for cache-rebuild/job-restart actions where there's nothing to restore *to*.

### scope_836: Confirmed above: #836 (per-check `reason`/`fix`/`confidence`/`tolerance_s`/`machine` on every `health_checks.py` result) is still open and unrelated to `loops.py`'s already-existing `{level, kind, arg}` shape. This PR does not touch #836's schema.
- [x] Proceed on `loops.py`'s existing shape only; #836 stays a separate, unblocked ticket.
```

## Tests to write first

Mirrors `lib/tests/test_loops.py`'s existing style (`_loop()`/`_world()`/`_r()` fixtures, pure functions over `tmp_path` registries/health files/job dirs — no real subprocess, no real filesystem outside `tmp_path`). Against **the real collaborator** where a mock would hide its rules: the actual `config/loops.json` registry (not a fixture copy) must validate under the new schema, and the real `validate()` must be the thing rejecting unsafe entries, not a test-only stand-in.

**From "How we'll try to break it":**
1. `test_two_macs_auto_fix_the_same_shared_thing_at_once` — two `run_fix` calls for the same loop id, same tmp jobs dir, with a `runner` that blocks until released: the second call's `job_events` write must not corrupt the first's (reuses `job_events`'s own `fcntl.flock`-protected `_mutate`); assert both run records land intact and `failed_in_a_row` reads a sane history either way (no half-written JSON, no lost run).
2. `test_a_fix_that_passes_but_the_check_stays_red_does_not_loop_forever` — `run_fix` returns `ok: True` (e.g. `graphify_freshness.refresh` exits 0) but the re-check of `graphify:fresh` is still red (rebuild succeeded, something else is now wrong). Assert this counts as a **fix failure** for demotion purposes (judged by the re-check, not the subprocess exit code) and increments toward the 2-strike cap — otherwise a "successful" no-op fix could retry forever without ever demoting.
3. `test_a_hanging_fix_counts_as_a_failure_not_a_hang` — `run_fix`'s runner raises `subprocess.TimeoutExpired`; assert the attempt is recorded as `failed` (not left `running` forever) and counts toward the 2-strike cap. (`test_loops.py:192` already covers this for manual `run_fix`; add the same assertion through the new auto-trigger path.)

**Misuse the section didn't name, required by the north stars' adversarial-testing mandate:**
4. `test_validate_rejects_an_auto_level_rerun_fix_whose_job_is_not_in_the_safe_allowlist` — a hostile/malformed `config/loops.json` entry with `fix: {level: auto, kind: rerun, arg: "ticket-pipeline"}` (a job outside `AUTO_SAFE_JOBS`) must raise `LoopError` on load, never silently pass through to the runner. **This is AC 3's real enforcement point.**
5. `test_validate_rejects_auto_level_for_kinds_that_are_never_safe` — `fix: {level: auto, kind: "relogin"|"rollback"|"ticket"|"decision", ...}` must raise `LoopError` (auto is restricted to `AUTO_SAFE_KINDS` only).
6. `test_auto_fix_runner_never_touches_a_loop_whose_action_or_fix_names_another_repo_or_a_url` — construct a loop entry with `arg` containing a path traversal (`../../other-repo`) or a URL; assert `ARG_RE`/the fixed dispatch table reject it (same spirit as `test_loops.py`'s existing "a fix arg that tries to inject a command" case, extended to the new kinds).
7. `test_two_consecutive_auto_failures_demote_to_one_tap_with_both_reasons` — two failed `loopfix-<id>` runs with distinct `error` text; `status()`'s derived `fix.level` reads `one_tap` and both reasons are present (not just the latest) — AC 2, exact wording.
8. `test_a_third_failure_does_not_add_a_third_reason_or_re_attempt_automatically` — once demoted, the runner must stop auto-attempting (only the one-tap button, pressed by a person, runs it again) — bounds the failure-reason list at 2 and never auto-retries a demoted loop.
9. `test_a_fix_that_clears_resets_the_failure_count` — one failure, then a run that passes and re-checks green: the next red episode starts the 2-strike counter fresh, not accumulated across unrelated episodes.
10. `test_run_auto_fixes_skips_a_loop_whose_fix_attempt_is_still_running` — a `loopfix-<id>` run with `status: "running"` and a recent `started_at`: the runner must not fire a second concurrent attempt for the same loop this sweep (covers the two-Macs/concurrency case structurally, and plain same-machine double-invocation).
11. `test_run_auto_fixes_only_fires_on_loops_whose_fix_level_is_auto` — a `one_tap`/`decision` broken loop is left alone; nothing runs without Gil's press.
12. `test_rebuild_graph_and_refresh_catalog_kinds_take_no_arg` — malformed registry entries giving these new kinds a non-null `arg` are rejected by `validate()` (they're fixed-target actions, not parameterized).
13. `test_bad_empty_huge_malformed_registry_or_health_file` — reuses/extends existing `load()` coverage: an unreadable/truncated `config/loops.json`, a `health.json` with a check entry missing `id`, and a huge `checks` list (1000+ entries) all degrade to a `problems` entry or are silently skipped, never a crash in `run_auto_fixes`.
14. `test_a_dependency_failing_graphify_binary_missing_cleanup_sweep_import_error` — each of the four action callables raising (e.g. `graphify` binary not on `PATH`, `cleanup_sweep` import failing) is caught and recorded as a failed run, never propagates and never breaks the health-check sweep that's hosting it (`_cli()` must finish and still write `health-status.json`).
15. **Dashboard/UI** (`dashboard/test/loops_panel.test.jsx` style): `test_loops_panel_shows_both_failure_reasons_once_a_loop_is_demoted_to_one_tap` and `test_loops_panel_still_shows_a_manual_fix_button_for_an_auto_level_loop` (Gil can always force it early, per existing `fixFor` behavior) — against real component rendering, not a snapshot mock.
16. `test_health_check_sweep_still_writes_a_full_status_file_when_the_auto_fix_runner_itself_throws` — the new call site in `_cli()` wrapped the same way `react_to_low_disk`/`react_to_accounts` already are (`except Exception` inside the reaction, never inside `_cli()` itself) — a person's mistake (bad registry edit mid-sweep) must not take down the whole health-check job.

**Verify-fails-when-code-changes-without-a-test-changing**: every new branch in `validate()`, `fix_plan()`, `run_fix()`, and the new `run_auto_fixes()` is covered by at least one test above that would fail if that branch's behavior changed; the three promoted/added `config/loops.json` entries are exercised by loading the **real** file (not a fixture copy) in at least one test, so a future hand-edit to the registry that breaks the new allowlist rule fails CI immediately.
