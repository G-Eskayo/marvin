## North-star fit

**Reuses:** this ticket is almost entirely an extension of the loop kernel already built for #1123 (ADR 0083), not a new subsystem. `lib/loops.py` already declares `LEVELS = ("auto", "one_tap", "decision")` and a `fix: {level, kind, arg}` per loop (`lib/loops.py:36-37,96-109`), but nothing ever *acts* on `level == "auto"` today — `fix_plan`/`run_fix` only run when a human presses the Loops panel's button (`dashboard/electron/main/loops.js:29-47`, `dashboard/src/components/LoopsPanel.jsx:85-97`), and `dashboard/src/lib/loops_view.js:fixFor()` shows a button for every level alike. `config/loops.json` already has a `"code-graph"` loop watching `check:graphify:fresh` (currently `fix.kind: "ticket"` — it only files a ticket, it doesn't call the rebuild) and a `"disk"` loop watching `check:disk:headroom` with `fix.kind: "rerun"` arg `"cleanup-sweep"`. #874 is: make `"auto"` actually run, immediately, from the existing sweep, instead of sitting inert. The trigger-without-polling pattern is already proven in `lib/health_checks.py`'s `react_to_low_disk()` (`health_checks.py:2005-2044`, comment: "this check already runs on its own schedule; reacting to its result adds no loop of its own") and `react_to_accounts()`, both called from `_cli()` right after `write_status()` (`health_checks.py:2088-2109`) — I hook the new auto-fix pass in there, the same way. The real graph-rebuild mechanism already exists (`graphify_freshness.refresh()`, used today by the Electron "Rebuild graph now" button, `dashboard/electron/main/health.js:21-31`); I call the same function, not a new one. Reporting reuses `job_events.step(...)`, exactly how `react_to_low_disk`/`react_to_accounts` already report. The one-tap IPC round-trip ("One-tap fixes expose an IPC the Vitals tab calls") already exists end-to-end: `loops:fix` → `loops.js createLoops().fix()` → `lib/loops.py run_fix()`. Nothing new is needed there except making the *level* correctly flip to `one_tap` after two failures.

**Simplest sufficient approach:** extend `lib/loops.py` (new `FIX_KINDS`, an explicit auto-safety allowlist enforced in `validate()`, a small per-machine attempt/failure state file, and a `run_due_auto_fixes()` function) and `config/loops.json` (promote specific, already-declared loops to `level: "auto"`), rather than building a parallel "fix registry" next to the health-check framework. A brand-new module would duplicate `loops.py`'s existing id validation, job-rerun mechanics, ticket-filing fallback and IPC surface for no benefit.

**Resource cost:** near zero extra steady-state cost — the auto-fix pass only does real work on a sweep where something it can act on is actually broken; most 15-minute sweeps add one cheap evaluate-and-skip pass. The one case that reruns the full sweep (to verify a fix actually cleared the check, not just "exited 0") only happens on sweeps where an auto-fix fired.

**Phone-OS direction:** reduces reds Gil would otherwise have to tap through manually — a step toward MARVIN handling its own low-risk upkeep unsupervised, consistent with north star 2 and the existing "Fix level" design (CONTEXT.md "Vitals" section, 2026-10-29/30).

**More capable, not more passive:** this is explicitly the category of work the Vitals spec designed MARVIN to take off Gil's plate (graph staleness, a stuck local job) — it's bookkeeping, not judgment, so automating it doesn't erode anything Gil would rather be doing himself.

**Note on the ticket's "#836 `fix` field" reference:** #836 (the per-check `reason`/`fix`/`confidence`/`tolerance_s`/`machine` schema) is **not built** — `lib/health_checks.py`'s `RESULT_TEMPLATE` (`health_checks.py:41`) still only has `{id, label, severity, detail, checked_at, value}`; existing checks bury their fix text in free-form `detail` strings (e.g. `check_intent_routing_collection`'s `"Fix: python3 ..."`). The field that actually already has the shape the ticket wants to extend is `loops.py`'s own `fix: {level, kind, arg}` — not a health-check-result field at all. I'm treating the ticket's "extend the #836 fix field to `{level, action, undo?}`" as describing this `loops.py` field (reading `action` as the existing `kind`/`arg` pair, since renaming `kind`→`action` would break the registry, the IPC contract and the UI for no gain), adding only the missing `undo`. I'm not pulling #836's broader schema work into this PR — it has its own acceptance criteria (a schema test over *every* check, UI age/Mac display) that #874 doesn't need to satisfy AC1–AC3.

## Tests first

From "How we'll try to break it" plus misuse the section didn't name:

1. **Two Macs auto-fixing the same shared thing at once** — same-machine overlap: a second `run_due_auto_fixes()` call while one is already mid-run for the same loop is skipped (busy-lock file, same shape as `task_dispatch`'s existing `{busy, started_at, task}` idiom used by `check_dispatch_lock`), not double-counted as a second failure. Cross-machine: each Mac's attempt/failure state lives in its own local `~/.claude/logs/*.json` (never synced), so two Macs never share — and therefore never race on — the same counter; assert the state path is machine-local and that running the same scenario against two independent state files never cross-contaminates counts.
2. **A fix that passes but the check stays red** — mock `run_fix` returning `ok: True`, but the re-check after it still reports red; assert this counts as a **failure** for the two-strikes counter (the runner trusts the re-measured check, never the action's own exit code).
3. **A fix that hangs** — mock the runner raising `subprocess.TimeoutExpired`; assert it's recorded as a failure, not left "running" forever, and that `rebuild_graph`/`refresh_catalog` get their own longer timeouts (graph rebuild is slow) rather than inheriting `run_fix`'s 120 s default.
4. **A red code-graph check is fixed automatically and reported** (AC1) — a red `graphify:fresh` result + `code-graph` loop at `level: "auto"` causes `graphify_freshness.refresh` to run without any button press, the check is re-measured, and a `job_events.step("Auto-fix", ...)` entry records the outcome.
5. **A fix that fails twice shows as one tap with both reasons** (AC2) — inject two consecutive failures for one loop; assert `loops.status()` now reports that loop's `fix.level` as `"one_tap"` and surfaces both stored failure strings (not just the latest), and that a third sweep does **not** attempt the fix again automatically.
6. **No auto action can touch another repo, a budget or a public site** (AC3) — (a) `validate()` rejects any loop entry with `level: "auto"` whose `kind`/`arg` falls outside the explicit allowlist (e.g. `level: auto, kind: rerun, arg: ticket-pipeline` or `kind: decision`/`ticket`/`relogin`/`rollback` at `auto` level) as a registry problem, never silently accepted; (b) a test walks the **real** `config/loops.json` and asserts every currently-`auto` entry is in the allowlist, so a future hand-edit that promotes something unsafe fails CI, not just this PR's own fixtures.
7. **Bad / malformed / huge input**: a `fix` dict missing `level`/`kind`, an unknown key, a 10 KB `arg`, a non-string `undo`, a loop `id` with path-traversal-looking characters — all rejected by `validate()` as problems (same pattern as existing `test_loops.py` "a fix arg that tries to inject a command").
8. **Every dependency failing**: `graphify_freshness.refresh` raising, `project_catalog.real_refresh` raising, the launchd `kickstart` subprocess returning non-zero, the health-status read failing mid-sweep — each is a failure, never an unhandled exception that kills the sweep (mirrors `first_aid_here`'s existing "never raises" contract).
9. **Repeats / wrong order**: running the auto-fix pass when nothing is broken is a no-op; running it immediately after a fix already cleared the check doesn't re-attempt; running it on a loop that's `wired: false` or `not_wired` never fires.
10. **Stale state**: an attempt-state file with a `started_at` far in the past (crashed mid-run) is treated as stale and the lock is reclaimed, not stuck "busy" forever (same remedy `check_dispatch_lock` already measures for the dispatch lock).
11. **A person's mistakes**: Gil manually edits `config/loops.json` and sets `level: "auto"` with a typo'd `kind` — rejected at `validate()`, not silently ignored or crashing `loops.status()` for every other loop (one bad entry → one `problems` row, same as today).
12. **Recovery**: once an auto-fixed (or downgraded) loop's watched check goes green again, its failure/downgrade state resets, so it's eligible for automatic fixing again next time it breaks (not permanently stuck at one-tap from one old incident).
13. **Real collaborator, not a mock**: a test that actually runs `cleanup_sweep.clear_rebuildable` / the real `project_catalog.real_refresh` / a real (test-fixture) `~/.agents`-shaped repo through `graphify_freshness.refresh`, at least once each, rather than mocking every one of these the whole way down — so a change to their real signatures breaks this suite, not just a mock's expectations.
14. **UI**: `fixFor()` returns no button for a loop at `level: "auto"` that isn't downgraded (nothing to tap), and returns the normal button once downgraded to `one_tap`, with both failure reasons visible in the row's text (extends `dashboard/test/loops_panel.test.jsx`, same render-to-string style already used there).
