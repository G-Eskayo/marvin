## North-star fit

- **Reuses:** `lib/pr_images.py`'s existing `verdict()`/`image_urls()`/`link_problem()`/`pinned_shas()`/`parse_pr_call()` (already the implementation `bin/gh`'s `ui_evidence_refusal` in `bin/gh:267-302` imports in-process), and the exact dual-language bridging pattern ADR 0080's I2 already uses for the same kind of problem: `lib/decisions_check.py` is a thin Python wrapper that shells out to `dashboard/webhook-server/decisions_cli.js` because the *canonical* parser (`decisions.js`) is JS. This ticket is the mirror case — the canonical rule (`pr_images.py`) is Python, so the dashboard (JS) gets a thin CLI wrapper instead of a second implementation. No new bridging mechanism invented.
- **Simplest sufficient approach:** one new CLI subcommand on an existing module, a rename of two existing problem codes for cross-language consistency, and a port of logic that already exists and is already tested (`dashboard/webhook-server/ui_evidence.js`'s cross-repo staleness check, added by #734/#773) into the one place that should hold it. No new services, no new storage, no new protocol beyond stdin/stdout JSON (mirrors `decisions_cli.js`'s own contract).
- **Token/compute cost:** spends a little (one `python3` subprocess per Approve click, replacing the Node-side GitHub calls it already made) to save a lot going forward — this collapses the *second* independent re-implementation of I1 (the first already being fixed by #734 inside `ui_evidence.js` itself) and fixes a latent bug that exists in **both** current implementations today (see below), so the fix compounds across `bin/gh` and the dashboard instead of just one of them.
- **Phone-OS direction:** indirect — it makes the "owner always sees current evidence" rule reliable from any surface (chat, pipeline, dashboard), which is a precondition for trusting MARVIN's approvals when the owner isn't watching a specific screen.
- **Human experience:** yes — it closes the gap where the dashboard's Approve could pass on a broken/stale image that `bin/gh` would have refused, and vice versa. Fixing it directly protects what the owner sees before approving.
- **Machine:** no machine-placement decision here; this is pure library/gate code, runs wherever `bin/gh` or the merge server already run (both Macs).

### A correction to the ticket's own framing

The ticket's "What to build" says *"PR #734 (#733) has merged since this ticket was written; if it left an image check of its own in the merge gate, that copy also moves onto the CLI."* It did: PR #734 consolidated what used to be a separate merge-gate copy into `ui_evidence.js` itself, and both `merge.js` (gate) and `dashboard/electron/main/mr_review.js` (card) already call that one JS module — so today there are **two** implementations of I1 (`lib/pr_images.py` for `bin/gh`; `ui_evidence.js` for the dashboard), not three. I1 isn't fully live yet either: `ui_evidence.js`'s own pin-format check (`imagePins`) currently treats a `github.com/.../blob/<sha>/...?raw=true` link as *pinned* (no refusal), while `pr_images.py` already refuses it as a 404 risk for private repos (`test_a_blob_raw_true_link_is_refused_because_it_404s_for_private_repos`). That's exactly the "An image linked as `blob/...?raw=true`... refused on both roads with the same message" case in "How we'll try to break it" — it's not refused on the dashboard road today. This plan fixes that as part of consolidating onto one implementation, not as a separate bug.

### A second latent bug this consolidation also fixes

`ui_evidence.js`'s cross-repo staleness check (added by #773, for images pinned in MARVIN's private instance repo per ADR 0071) has no Python equivalent. `bin/gh`'s `changed_since` callback in `bin/gh:291-295` only compares within the PR's own repo; an instance-repo-pinned SHA passed to it 404s, `changed_since` returns `None`, and `pr_images.verdict()` returns `[]` (no staleness judged) for **every** pinned image on that PR, not just the cross-repo one. So a MARVIN PR opened from a chat with instance-repo-pinned screenshots already slips past `bin/gh`'s staleness check today. Porting #773's algorithm into `pr_images.py` (once) fixes this for `bin/gh` as a side effect of fixing it for the dashboard — compounding leverage, not scope creep.

## Design

1. **`lib/pr_images.py`** gains:
   - `image_pins(urls) -> list[tuple[str|None, str]]`: `(repo, sha)` for each raw-host full-SHA pin (repo parsed from the URL) and `(None, sha)`-less entries for GitHub-upload pins (no commit info, matches today's "staleness can't be judged" pass-through).
   - `verdict()`'s staleness branch is restructured to take a richer callback — `changed_since(repo, sha) -> list[str] | None`, where `repo` is `None` for same-repo (today's shape, unchanged) and the pin's own `owner/repo` string for a cross-repo pin — instead of today's single-repo-only `changed_since(sha)`. The *caller* (not `verdict()`) decides whether to resolve a cross-repo pin via a direct compare (same repo) or via the commit-timestamp-against-the-PR's-own-commit-history approach `ui_evidence.js:136-170` already implements; `verdict()` itself stays pure and unit-testable exactly as today.
   - Problem codes renamed for one vocabulary across both languages: `BAD_IMAGE_LINK` → `IMAGES_UNPINNED`, `STALE_UI_EVIDENCE` → `IMAGES_STALE` (matching `ui_evidence.js`'s existing names, which the card and merge-failure payloads already surface to the owner). `NO_UI_EVIDENCE` is unchanged. A new `UI_EVIDENCE_UNCHECKED` code is added for "couldn't gather the facts" (bin/gh already represents this today by returning `None`, i.e. failing open — it doesn't need the new code; only the CLI, which must fail *closed*, emits it).
   - A new `facts(pr_url, ask)` function that does the GitHub fact lookup — ported from `bin/gh:267-298`'s inline logic plus the cross-repo commit-date/PR-commit-list lookups `ui_evidence.js:136-170` does today — returning `(files, body, head_ref, repo)` plus a ready-to-use `changed_since(repo, sha)` closure. `bin/gh`'s `ui_evidence_refusal` is rewritten to call this instead of repeating the fact-gathering inline, so the two Python-side behaviors (today inline in `bin/gh`, soon shared) can't drift either.
   - A CLI entrypoint: `python3 lib/pr_images.py check <pr-url> [--extra-patterns-json '[...]']`, which builds its own `ask()` via `subprocess` calls to `gh` (same shape as `bin/gh`'s `_gh_json`), calls `facts()` then `verdict()`, and prints `{"problems": [[code, message], ...]}` to stdout. Any internal exception is caught and printed as `{"problems": [["UI_EVIDENCE_UNCHECKED", "<reason>"]]}` so the common case (GitHub unreachable, bad token, repo renamed) is still clean JSON — belt-and-suspenders, the JS caller treats a non-zero exit, timeout, or unparseable stdout as `UI_EVIDENCE_UNCHECKED` too, so a genuine crash can't be mistaken for "no problems."

2. **`dashboard/webhook-server/ui_evidence.js`**:
   - `assertUiEvidence(prUrl, exec, extraPatterns)` stops doing its own `gh pr view`/`gh api compare` calls and its own pin/staleness logic (`imagePins`, the cross-repo block, `link_problem`-equivalent). It instead spawns `python3 lib/pr_images.py check <prUrl> --extra-patterns-json ...` (via the existing injectable `exec`, so tests keep mocking a function rather than a real subprocess), parses the JSON, and raises the existing `MergeFailure(refusal(code, 'request', message, hint))` shapes it raises today — keeping its current wording/hints (`NO_UI_EVIDENCE`, `IMAGES_UNPINNED`, `IMAGES_STALE`, `UI_EVIDENCE_UNCHECKED`), now sourced from the CLI's `code` instead of locally-computed booleans.
   - `DEFAULT_UI_PATTERNS`, `globToRegExp`, `uiFiles`, `touchesUi`, `hasImage`, `imageUrls`, `unpinnedImages`, `imageShas`, `imagePins` stay as exported pure, synchronous, no-network functions — they're the only part of the rule `dashboard/electron/main/mr_review.js`'s `needsImages()` can use without adding a subprocess spawn to a tight per-PR-row loop that already runs with zero network/subprocess cost (see Decision 1). They are kept byte-for-byte in sync with `pr_images.py`'s equivalents (`image_urls`, `link_problem`, `pinned_shas`) via a new shared JSON fixture (`lib/tests/fixtures/pr_image_links.json`) consumed by both `lib/tests/test_pr_images.py` and `dashboard/test/ui_evidence.test.js`, so the two can never silently diverge again even though they're two files.
   - `ui_paths_for`'s JS/Python drift (`DEFAULT_UI_PATTERNS` already differs between `lib/evidence_capture.py` and `ui_evidence.js` today, pre-dating this ticket) is **not** touched — out of this ticket's acceptance criteria, and not safe to fold in without its own test pass.

3. **`dashboard/webhook-server/merge.js`**: no change to its call site (`uiEvidence(prUrl, exec, ...)` at `merge.js:881`, before any gate work) — it already gets the new behavior for free once `assertUiEvidence` changes underneath it.

4. **`dashboard/electron/main/mr_review.js`**'s `needsImages()` keeps using the synchronous `uiFiles`/`hasImage`/`unpinnedImages` (per Decision 1) — unchanged interface, now fixture-verified against the Python rule instead of hand-maintained in parallel with no check.

5. **The PR's required statement ("should `merge.js` also route through `bin/gh`?"):** **No.** `bin/gh` is the system-wide rate-limit/priority gate for every `gh` call on a Mac (`bin/gh:1-18`); routing the merge server's calls through it would entangle a server process with a gate designed around interactive/pipeline *priority* semantics, and — more concretely — would move the image check to just before the final `gh pr merge` call instead of its current place "before any gate work: refusing is cheap" (`merge.js:880`), undoing that optimization and losing the structured `MergeFailure`/stage-recording shape the dashboard needs (bin/gh's refusal is a stderr line and a non-zero exit). `merge.js` keeps calling `lib/pr_images.py check` directly, exactly as it calls `gh` directly today.

## Decisions

A genuine architecture fork with real cost/completeness tradeoffs — not guessed silently:

<!-- marvin:decisions -->
### card_parity: The "Needs images" card currently skips the staleness check (only the merge gate does it — see `mr_review.js:290`, "Staleness needs GitHub calls, so only the gate checks it"), because `needsImages()` runs synchronously over every open PR on every dashboard poll with zero network/subprocess cost today. Making the card's verdict fully match the merge gate's (including staleness) means adding a `pr_images.py check` subprocess call — with its own fresh `gh` calls — per open PR per poll.
- [ ] A: Keep the card limited to what it can judge without network calls (no image / unpinned link format) — same scope as today, now just fixture-verified against `pr_images.py` instead of hand-duplicated. The card and the merge gate can still disagree only in the direction "card says fine, gate later finds it stale" — never the reverse, since the card's checks are a strict subset run in the same order. *(Recommended: avoids a per-poll subprocess-and-GitHub-API-call fan-out over every open PR, which the merge gate itself avoids too by running once per Approve click, not per poll.)*
- [ ] B: Give the card the full verdict, including staleness, by having it call `pr_images.py check` per open PR per poll. Costs one Python subprocess + its `gh api` calls per open PR every poll cycle; needs `needsImages()`'s caller (`listPipelinePrs`, already `async`) changed from a sync `.map()` to an awaited one.

5. **A PR with no UI files passes on both roads with no image** — existing cases in both suites, kept passing.
6. **Cross-repo pinned images (MARVIN's instance repo, #773)** — port all of `dashboard/test/ui_evidence.test.js`'s "images kept in another repo" describe block (lines 200-262) into `lib/tests/test_pr_images.py` against the new `facts()`/`changed_since(repo, sha)` shape, including: never asking the PR's own repo about an instance-repo commit; current when taken after the last commit; stale when a look-changing commit follows; only-logic-changed stays current; an uncomparable instance-repo commit fails closed naming that repo; same-repo pins still use the direct compare. 12. **`dashboard/test/ui_evidence.test.js`'s existing describe blocks** (gate order, non-UI PR, project patterns) re-pointed at the CLI-backed `assertUiEvidence` via a mocked `exec`, kept green — verify fails if any of these pass without a corresponding mock/expectation change.
