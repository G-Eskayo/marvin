## North-star fit

**Reuses:** `lib/pr_images.py`'s existing `verdict()`, `link_problem()`, `ui_files()` (via `evidence_capture.py`), `ui_paths_for()`, and `parse_pr_call()` — already the one Python implementation `bin/gh` calls (`bin/gh:267-302`, `ui_evidence_refusal`). Reuses the dashboard's existing "shell out to a venv Python script" pattern already used for every other gate check in `merge.js` (`exec(VENV_PYTHON, [PROFILE_SCRIPT, ...])`, `merge.js:635,658,1137,1163`) — `assertUiEvidence` already receives that same `exec` as its 2nd argument, so no new plumbing is needed to call a CLI, only a new script to call. Reuses the existing dependency-injection shape of `mr_review.js` (`uiPathsFor`, `sentBackTickets`, etc.) to thread an `exec` into `needsImages`.

**Simplest sufficient approach:** one new pure/orchestration surface in `pr_images.py` (a `check_pr(...)` function plus a `check` CLI subcommand around it) that both `bin/gh` and the dashboard call, instead of three places (`bin/gh`, `ui_evidence.js`, the card) each deciding image validity on their own.

**Where it spends tokens/compute:** the dashboard's per-PR "Needs images" card goes from zero extra calls to one `python3 pr_images.py check <url>` (plus its internal `gh api` calls) per open UI-touching PR per list refresh. That's a real, shared-GitHub-allowance cost (`bin/gh`'s own docstring: "Both Macs, the pipeline, its agents, the dashboard and every job share ONE GitHub account allowance"). I mitigate it with an in-memory cache keyed by `(prUrl, headSha)` in `mr_review.js`, so an unchanged PR is never re-checked between polls — this is the one place I'm spending calls to buy correctness, and I'm flagging the trade-off explicitly below rather than deciding it silently.

**Human experience:** closes a real blind spot — the owner currently can approve a dashboard merge whose images are broken or stale, because the merge server's own copy of the rule (`ui_evidence.js`) doesn't check `blob/...?raw=true` links at all (only `bin/gh`'s Python does), and the "Needs images" card doesn't check staleness or bad links at all. After this, what he's shown and what the merge gate enforces are provably the same thing.

## Current-state corrections to the ticket

- **#734/#733 already merged** (2026-10-27, PR #734) and put a *third* copy of the rule straight into `ui_evidence.js` (pinning + staleness + cross-repo-pin resolution for images in another repo, e.g. MARVIN's own instance repo, ADR 0071/marvin#773) rather than into `pr_images.py`. So the "what to build" bullet about #734 is already true: its rework is this ticket.
- **Two real rule conflicts exist between the Python and JS copies today**, which this ticket must resolve, not just relocate:
  1. Python's `link_problem()` refuses **any** `github.com/.../blob/...` link, even one pinned to a full commit SHA (`test_a_blob_raw_true_link_is_refused_because_it_404s_for_private_repos`). JS's `unpinnedImages()` treats a blob link pinned to a full SHA as *pinned* (`ui_evidence.test.js:132-137`). The ticket's own break-it list ("An image linked as `blob/...?raw=true`... refused on both roads") settles this in Python's favor: blob links are always refused, regardless of SHA. The JS test asserting otherwise is wrong and gets corrected.
  2. Python's `verdict()` stops checking pinned images as soon as it finds *one* that is current ("the newest one decides" — `test_with_several_pinned_commits_the_newest_one_decides`), so a PR with one fresh and one stale pinned image passes. JS refuses if *any* pinned image is stale (`ui_evidence.test.js:184-189`, "one stale set among several is enough to refuse"). JS's behavior is the one ADR 0080/north-star-3 actually wants; Python's is a latent bug in the very function `bin/gh` already calls. Fixed for both callers at once.
- **`ui_evidence.js`'s own fail-open/fail-closed split already matches `bin/gh`'s documented design** (`bin/gh:253`: "Fails OPEN when GitHub can't be asked... the dashboard's Approve still fails closed"). I keep that split: `verdict()`/`check_pr()` get a `fail_closed` flag — `False` for `bin/gh` (unchanged), `True` for the new CLI (used by the dashboard).
- **The existing JS refusal codes stay** (`NO_UI_EVIDENCE`, `IMAGES_UNPINNED`, `IMAGES_STALE`, `UI_EVIDENCE_UNCHECKED`): they're load-bearing elsewhere (`merge_order.js:113-114` merge-queue priority, `prState.js:12,182` live-refusal mirroring and retry copy, `mr_history.js:20`, `site/.../merge-gate.mdx`). The ticket's own text says `ui_evidence.js` "keeps its exported interface... **and messages**" — so the CLI's verdict codes (`NO_UI_EVIDENCE`, `BAD_IMAGE_LINK`, `STALE_UI_EVIDENCE`, `UI_EVIDENCE_UNCHECKED`) get mapped 1:1 onto those existing JS codes inside `assertUiEvidence`, not the reverse.

## Design

**`lib/pr_images.py`** (existing pure helpers unchanged except as noted):
- `image_pins(urls) -> list[tuple[str, str]]`: `(owner/repo, sha)` for every `raw.githubusercontent.com` link with a full 40-hex SHA, replacing the repo-blind `pinned_shas()` for staleness purposes (`pinned_shas()` stays, now implemented in terms of `image_pins()`, so its existing test keeps passing).
- `verdict(files, body, extra_patterns=(), changed_since=None, head=None, fail_closed=False)`: same shape, two behavior fixes — (a) iterates **every** `image_pins()` entry, refusing on the first stale one found rather than returning early on the first current one; (b) when `changed_since(repo, sha)` returns `None` for a pin, `fail_closed=True` turns that into an `UI_EVIDENCE_UNCHECKED` problem immediately, `fail_closed=False` (bin/gh's existing default) skips that pin and keeps checking the rest. `changed_since` becomes 2-arg `(repo, sha)`; `head` lets a pin equal to the PR's head skip the compare call entirely (ports the JS "no comparison needed" optimization and its test).
- `make_changed_since(pr_repo, pr_number, head, files, ask) -> callable`: the "open-PR facts lookup" the ticket asks for — same-repo pins go through `gh api repos/{pr_repo}/compare/{sha}...{head}`; a pin in another repo (MARVIN's instance repo, ADR 0071/marvin#773) is resolved by commit time against the PR's own commit list (ports `ui_evidence.js:136-168`'s `assertUiEvidence` logic verbatim, including "older than every PR commit ⇒ every file counts as changed" and "own repo can't find the commit ⇒ uncheckable, naming that repo"). `pr_number=None` (the `pr create` case, before a PR/number exists) makes any cross-repo pin uncheckable, same as today.
- `check_pr(pr_repo, pr_number, head, files, body, extra_patterns, ask, fail_closed=False) -> list[tuple[str, str]]`: wires the two together — the single orchestration point both callers use.
- `parse_pr_url(url) -> tuple[str, str, int] | None`: new, pure, used by the CLI.
- CLI: `pr_images.py check <pr-url> [--extra-ui-path PATTERN]...` — fetches `gh pr view <url> --json files,body,headRefOid` via a thin `ask()` that shells out to `"gh"` on `PATH` (deliberately *not* hardcoding the real binary, so if `~/.agents/bin` is first on `PATH` it still goes through the rate-limit gate; if not, same fallback as today — no change to how the dashboard reaches GitHub), then calls `check_pr(..., fail_closed=True)` and prints `{"problems": [[code, message], ...]}`. Any failure to get PR facts, or any uncaught exception, means no valid JSON on stdout and a non-zero exit — the only contract callers rely on.

**`bin/gh`** (`ui_evidence_refusal`): becomes a thin shim over `pi.check_pr(...)` built from its existing `ask` closure, instead of hand-rolling the same-repo-only `changed_since`. This is a pure win for chat/pipeline PRs: they gain correct cross-repo-pin staleness checking and the any-pin-stale fix, while keeping the exact same fail-open behavior on any lookup failure (unchanged: `bin/gh:379-383`).

**`dashboard/webhook-server/ui_evidence.js`**: keeps `uiFiles`, `hasImage`, `imageUrls`, `unpinnedImages` (still used elsewhere — `mr_history.js`, `prState.js` do *not* need these, but nothing else is asked to drop them, and `uiFiles`/`hasImage` are cheap/pure and still useful for other call sites — confirmed none of the ticket's acceptance criteria ask for their removal, only for `ui_evidence.js` to have "no image or UI-path **rule**", i.e. no verdict logic). `assertUiEvidence(prUrl, exec, extraPatterns)` keeps its signature; internally it now does `exec(VENV_PYTHON, [PR_IMAGES_SCRIPT, 'check', prUrl, ...extraPatterns.flatMap(p => ['--extra-ui-path', p])])`, parses `{problems}`, and maps the first problem's code (`NO_UI_EVIDENCE`→`NO_UI_EVIDENCE`, `BAD_IMAGE_LINK`→`IMAGES_UNPINNED`, `STALE_UI_EVIDENCE`→`IMAGES_STALE`, `UI_EVIDENCE_UNCHECKED`→`UI_EVIDENCE_UNCHECKED`) onto the same `MergeFailure`/`refusal()` calls it already throws, using the Python message as the factual body of the message and keeping its own remediation/retry wording per code. A rejected/timed-out/non-JSON `exec` call throws the existing `UI_EVIDENCE_UNCHECKED` refusal, unchanged in wording.

**`dashboard/electron/main/mr_review.js`**: `needsImages(pr, uiPathsFor)` becomes `async`, calling the same CLI through a shared helper exported from `ui_evidence.js` (the non-throwing counterpart `assertUiEvidence` wraps), cached in a module-level `Map` keyed by `` `${pr.url}@${pr.headSha}` `` so unchanged PRs aren't re-checked on every poll. `ownBlocker`, `markBlocked`, `prsForOrderCheck`, and the one call site inside `listPipelinePrs` become `async`/`await` accordingly — all three are already called from `async` contexts today (`listPipelinePrs` itself, and `index.js:1211`'s `prsForOrderCheck` call), so this is a non-breaking extension of the existing shape, not a new concurrency model. `exec` is threaded in as a new optional dependency (default `execFileAsync`), matching how every other optional collaborator in this file is injected.

**`merge.js`**: no signature changes; `uiEvidence = assertUiEvidence` (`merge.js:858`) keeps working unchanged, since `assertUiEvidence`'s external contract (`prUrl, exec, extraPatterns`) doesn't change.

**Should `merge.js` route through `bin/gh` too?** No. `bin/gh` is a gate for callers that *don't* already enforce I1/I2 themselves (interactive chats, pipeline agents) — it adds rate-limit coordination, job-priority budgeting, and the I2 decisions check on top of the plain `gh` call. `merge.js` already enforces I1 (via `pr_images.py` directly, as of this ticket) and I2 (via `decisions_gate.js`/`assertDecisions`) before ever touching GitHub for the merge itself. Routing merge.js's own `gh pr merge` call through `bin/gh` as well would nest one gate inside another, depend on `~/.agents/bin` being first on the dashboard's launchd `PATH` (the exact gap that caused this bug for PR creation), and risk `bin/gh`'s background-job budget/priority logic mistakenly deferring a person-triggered dashboard merge. The fix that matters — one shared rule implementation — is what this ticket already does; it doesn't need `merge.js` to also become a `bin/gh` caller.

## Tests to write first

From the ticket's "How we'll try to break it":
1. An image linked as `blob/...?raw=true` or a repo-relative path: refused on both `bin/gh` and `merge.js`/the card, same code (`IMAGES_UNPINNED`) and same message text, sourced from `pr_images.link_problem`.
2. An image pinned to a commit older than the last look-change commit: `IMAGES_STALE`/`STALE_UI_EVIDENCE` on both roads, naming the stale file.
3. The CLI crashes (non-zero exit), times out, or prints non-JSON: `merge.js` refuses (`UI_EVIDENCE_UNCHECKED`), never passes. (`bin/gh`'s own direct-call path can't "crash" this way since it calls `check_pr` in-process — covered instead by an exception inside `ask()`, still fail-open per its existing contract.)
4. A project profile's `evidence.ui_paths` is honoured identically by `bin/gh` and `merge.js`/the card for the same file list.
5. A PR with no UI files: passes on both roads with no image, no gh calls beyond the initial `pr view`.

Misuse the ticket's list doesn't name, added per north-star "tests try to break it":
6. Several pinned images, one stale and one current: refused (`IMAGES_STALE`) — covers the "newest one decides" bug fix, same case on both `bin/gh` and the CLI.
7. A blob link pinned to a full SHA: still refused (not treated as pinned) — covers the Python/JS conflict resolution; updates/removes the now-wrong JS test at `ui_evidence.test.js:132-137`.
8. An image pinned to a commit in another repo (MARVIN's instance repo, ADR 0071): current when taken after the last PR commit; stale when a look-changing PR commit lands after it; uncheckable (that repo's own commit lookup fails) fails closed on the CLI path and fails open on the `bin/gh` path, naming the right repo in the message either way.
9. `pr create` (no PR number yet) with a cross-repo pin: treated as uncheckable (can't look up PR commits without a number), not a crash.
10. Repeats/concurrency: calling the card's check twice for the same `(prUrl, headSha)` hits the cache, not the CLI, a second time; a new commit (new head SHA) busts it.
11. Malformed/huge input: a PR body with hundreds of image tags, or a `gh pr view` payload missing `headRefOid`/`files`/`body` keys — doesn't crash `check_pr`, degrades to "can't check" rather than a Python exception reaching the CLI's stdout as a traceback mixed with JSON.
12. Wrong permissions / stale state: the `check` subcommand invoked for a PR number that's since been merged or deleted (`gh pr view` 404s) — fails closed on the dashboard path, fails open on the `bin/gh` path, each with its existing message shape.
13. `test_work_loop_e2e.py`'s new I1 section: a chat PR (through `bin/gh`, `pr merge`) and a dashboard merge (through `merge.js`, mocking only `exec`/the fake `gh` on `PATH`, not `pr_images.py` itself) are both refused for the same stale-image fixture, verifying it's genuinely one code path and not two that happen to agree today.
