## North-star fit

**Reuses before adding anything new:** the whole sandbox/subprocess-E2E harness already exists and is extended in place, not duplicated:
- `lib/tests/test_work_loop_e2e.py` — the `github` fixture (a fake `gh` binary that records every call's argv + body-file to `$HOME/github-calls.jsonl`) and the `_gh()`/`_reached()`/`_gate_log()` helpers. Its own docstring says "Each rule adds its own section" — I1 and I3 are new sections in this same file, not a new file.
- `lib/real_home_guard.py` + the repo-wide `conftest.py` — already give every pytest process (this file included) a temp-mirrored `HOME` and a write-guard that fails any test touching the real `~/.claude`. `lib/tests/test_test_harness.py` already proves that guard works. Acceptance criterion "never touches the real HOME or GitHub" is satisfied by this existing, already-tested mechanism plus the `_gh`-style helper always pinning `HOME`/`PATH` to the sandbox — no new code needed for it.
- The real choke points themselves, exercised through their real entry points: `bin/gh` → `lib/pr_images.py` (I1), `lib/owner_decisions.py`'s CLI (`sync`/`status`) (I3) — never mocked.
- `lib/main_health.py:101` already runs `pytest lib/tests -q` for the full suite, and `lib/tests/*.py` is pytest's normal discovery root — so "runs in the merge gate's test suite" needs no new wiring; it's a consequence of editing a file that's already in that directory.

**Simplest sufficient approach:** the only genuinely new piece is a small, generic extension to the fake `gh` script: an optional `FAKE_GH_RESPONSES` JSON file, keyed by a short call marker (`api` path for REST-shaped calls, a query-text sniff for GraphQL), so a test can hand back canned PR/comment data instead of the default `{}`. Everything else (issue list/create, label create) already works fine against the default `{}` response, as the existing I2 tests show — so this extension is the one lever needed for both I1 (stale/missing images) and I3 (overdue decisions), kept backward-compatible with every existing test in the file.

**Resource cost:** no new runtime code, no new dependency; a few more pytest cases (sub-second each, subprocess-based) added to a file the gate already runs. Spends a little test time to stop a recurring "each part works alone, the loop doesn't" failure class, per ADR 0080.

**Phone-OS / capability:** this makes "the loop works" a falsifiable, machine-checked claim instead of something only verified by the owner noticing a dropped PR days later (#724's actual history) — strictly more capable, not more passive; the owner stops being the detector of last resort.

**Which machine:** no machine-specific behavior; it's a pytest file, runs wherever the gate runs its Python suite.

**Scope boundary (checked against the code, not assumed):**
- I1's *other* stated choke point — the dashboard's merge server calling `lib/pr_images.py` directly instead of its own `ui_evidence.js` copy — is **not yet built**: `grep` shows `dashboard/webhook-server/merge.js` still imports `assertUiEvidence` from its own `ui_evidence.js`, and this drift is tracked as its own open ticket, **#743** ("I1: the dashboard's merge server uses the one screenshot rule"), separate from #859. `docs/life-of-a-ticket.md`'s own order table lists "dashboard merges skip `bin/gh`" as a still-open "new" row. So the I1 test here exercises the choke point that *does* exist today — `bin/gh` → `lib/pr_images.py` — exactly as #859's own ordering note says ("3. The loop test, first for I1–I3"), and does not block on #743.
- "a push after a gate refusal (#678)" is categorized under **I5** in `docs/life-of-a-ticket.md`'s own table ("#678 | I5 | The liveness checker..."), and I5 (`next_step()`-based liveness) isn't built yet (that's ADR 0080's I4/I5, ticket **#860** and beyond). The ticket's own "Start with I1–I3" line scopes this out explicitly; I'm not silently dropping it.
- "The fake GitHub refusing (rate limit, 5xx) mid-loop... never dropped" is also I5's "visible as stuck" in full, but today's code already has a *visible, not-silent* behavior at each I1/I3 choke point I can test now: `bin/gh`'s image check fails **open with a logged note** (`bin/gh` lines 381–390: "couldn't check this PR's images... letting it through"), and `owner_decisions.sync()` fails **closed with `ok: false` and a note**, filing nothing, rather than acting blind (`lib/owner_decisions.py` `fetch()`/`sync()`). I test those two concrete, already-shipped behaviors rather than inventing a liveness checker.

No Decisions section: ADR 0080 and `docs/life-of-a-ticket.md` already settled scope, choke points, and ordering; the only items that don't fit I1–I3 (#678/I5, the dashboard's I1 copy/#743) are already tracked as separate open tickets, not a choice for the owner to make here.

## Tests first

All new tests live in `lib/tests/test_work_loop_e2e.py`, as new `# ── I1 ──` and `# ── I3 ──` sections (matching the file's existing I2 section), reusing `github`/`_gh`/`_reached`/`_gate_log`. One new fixture helper, `_route(tmp_path, responses)`, writes the canned-response JSON file the extended fake `gh` script reads via `FAKE_GH_RESPONSES`; a new `_od()` helper mirrors `_gh()` but invokes `lib/owner_decisions.py` as a subprocess with the same sandboxed `HOME`/`PATH`.

**I1 — current evidence (`lib/pr_images.py` via `bin/gh`)**
1. `test_i1_missing_ui_evidence_refused_before_reaching_github` — `pr create` touching a `.jsx` file (via a routed `compare` response), body with no images → rc 1, `NO_UI_EVIDENCE` + the `pr-shots` fix text in stderr, nothing reaches GitHub, gate log records the refusal. *(Fails if the `ui_evidence_refusal` call is ever removed from `bin/gh`'s `main()`.)*
2. `test_i1_stale_pinned_images_refused` — body has one raw-host image pinned to a full SHA; first `compare` call shows a `.jsx` UI file; second `compare` call (the staleness check, keyed by the pinned SHA) shows a *newer*, non-image UI file → rc 1, `STALE_UI_EVIDENCE`.
3. `test_i1_current_pinned_images_reach_github` — same as #2 but the staleness `compare` shows no newer non-image UI files → rc 0, the `pr create` call is recorded as reaching GitHub.
4. `test_i1_override_lets_one_call_through_and_is_logged` — `MARVIN_UI_EVIDENCE_OK="<reason>"` on the bad-body call from #1 → rc 0, logged with `ui_evidence_override`; a repeat of the same call without the override is refused again (one-call-only, parity with the existing I2 override test).
5. `test_i1_github_unreachable_fails_open_with_a_visible_note` — the `compare` call is routed to return a non-zero exit (simulated GitHub failure) → rc 0 (fails open, by design) **but** stderr contains the "couldn't check this PR's images... letting it through" note — proves the mid-loop failure is visible, not silent.

**I3 — answers are acted on (`lib/owner_decisions.py`)**
6. `test_i3_overdue_decisions_file_a_followup_that_reaches_github` — the routed GraphQL `fetch` response is one PR whose latest owner-authored Decisions comment is older than the grace period, with no reply and no commit since → run `owner_decisions.py sync` → rc 0 **and** `_reached()` shows an `issue create` call (label `owner-decisions`, body containing the `marvin:decisions-addressed` instruction) actually landing at the fake GitHub. Asserting the outbound call, not just the process's own "ok" return, is the direct regression guard for the #724 shape (a job reporting success while silently filing nothing).
7. `test_i3_a_bare_commit_with_no_reply_is_not_addressed` — same PR, but with a commit timestamped after the decisions and still no `marvin:decisions-addressed` reply → `owner_decisions.py status --repo --pr` → JSON shows `has_decisions: true`, `built: false`, despite the commit. This is the data the merge gate (`owner_decisions_gate.js`) reads to refuse "approve before decisions answered," and it's the explicit marvin#733 rule ("a commit alone no longer counts").
8. `test_i3_a_reply_carrying_the_addressed_marker_is_built` — same PR, with an owner-authored reply comment containing `<!-- marvin:decisions-addressed -->` after the decisions → `status` shows `built: true`, `addressed_by: "reply"`.
9. `test_i3_github_unreachable_never_files_blind` — the routed GraphQL call is made to fail (non-zero exit) → `sync` → JSON `ok: false` with a note, **and** `_reached()` has no `issue create` call at all — never acts on a partial read.

**Deliberately not added here (named, not silently skipped):** a "push after gate refusal" case (#678) and a full liveness/"visible as stuck" check — both are I5, not built yet (tracked at #678 and inside ADR 0080's I5 row); and a test of the dashboard merge server's own I1 path — tracked separately at #743.
