What's still broken, and is the real reason this keeps failing, found by reading `merge_trend.py` against the *actual* signature of its collaborator rather than trusting the mocks in its own tests:

**Root cause #1 (production-fatal, currently invisible to any test): `lib/merge_trend.py:59` calls `amp.area(repo, files)`** — passing a repo-name string where `auto_merge_policy.area()` expects a single file path, and a `list[str]` of changed files where it expects the `rules: dict`. `rules.get("core", [])` on a list raises `AttributeError`. That exception is caught by `record_merge_event`'s outer `except Exception: return None` (`lib/merge_trend.py:81-82`), so **every real merge event in production silently writes nothing** — the entire "mutation scores over time" and "PRs merged below 80%" feature never gets data, in production, right now. `lib/tests/test_merge_trend.py` never catches this because all five of its scenario tests `patch('merge_trend.amp.area', return_value=...)` — mocking the exact boundary that's broken. This is the textbook case the north stars call out: "test against the real collaborator wherever a mock could hide its rules."

**Root cause #2 (silent no-op, also test-invisible): field-name mismatches between consumers and real producers.** `check_mutation_score_trend` (`lib/health_checks.py:1433`) filters recent entries by key `"at"`; the real producer `merge_trend.py:69` writes `"recorded_at"`. `"at" in e` on a dict checks key membership exactly, so this condition is always `False` against real data and the date window silently falls back to "last 7 entries by list order," not "last 7 days." Worse: `check_test_skips_trend` (`lib/health_checks.py:1479`) reads a `"count"` field that **the real producer never writes at all** — `commit_check.py:43` logs `{"at": time.time(), "kind", "repo", "files", "reason"}`, one row per skipped commit, no pre-aggregated `"count"`. In production this check will *always* return yellow "no skip counts recorded yet," forever. `lib/tests/test_health_checks_mutations.py`'s own fixtures use a schema (`"count"`, and inconsistently `"at"` vs `"recorded_at"`) that matches neither real producer — the tests and the code are mutually consistent with each other and both wrong against reality.

**Gap #3 (unmet acceptance criterion, not a prior focus): "both Macs."** AC #1 literally says "The four trends visible, both Macs," and the break-it list literally says "one Mac unreachable" — but `check_mutation_score_trend`, `check_test_skips_trend`, and `check_repo_growth` are all pure-local reads with no SSH, unlike every other true-cross-machine check in this file. Since `JOB_PLACEMENT["health-check"] = "mini"` (`lib/health_checks.py:1027`), health-check only *runs* on the mini — so "both Macs" visibility is structurally impossible without the same reach-out-over-SSH pattern `check_repo_sync_everywhere`/`check_deploy_steps` already use. No prior attempt's doc mentions this; it's new context from code-reading, not re-derivation of settled ground.

This spends tokens on rereading six files closely instead of trusting a stale summary, and it saves far more than iteration 7 of re-shipping the same crash fix: these three bugs are why the feature does nothing in production even when every test is green. It leaves Gil more capable — a real signal on core-area-merged-without-tests and skip bursts, not a dashboard card that is permanently and silently inert. **No Decisions section**: every fix follows directly from reading the real collaborator's actual signature/schema and the codebase's own established cross-machine pattern — nothing here is a judgment call for Gil.
