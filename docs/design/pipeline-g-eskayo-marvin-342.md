## Root cause of each must-fix finding, and the concrete fix

I re-read the current (uncommitted) `lib/health_checks.py`, `lib/tests/test_health_checks.py`, `lib/commit_check.py`, `lib/auto_merge_shadow.py`, `lib/auto_merge_policy.py`, `lib/project_catalog.py`, `lib/metrics_registry.py`, and `dashboard/electron/main/metrics.js` directly — not just the review comments — to confirm every finding against real line numbers.

1. **`check_test_skip_trend` (`lib/health_checks.py:1519-1567`) crashes on real data.** Confirmed: `commit_check._log()` (`lib/commit_check.py:43`) writes `"at": time.time()` — an epoch float. The check does `ts_str = entry.get("at"); ts = datetime.fromisoformat(ts_str.replace("Z", "+00:00"))` — `.replace` on a float raises `AttributeError`, not caught by `(ValueError, KeyError, json.JSONDecodeError)` (line 1550). A non-dict JSON line (e.g. `"[]"`) hits `entry.get("kind")` and also raises `AttributeError`. Future-dated entries aren't skipped (only `ts < cutoff: continue` exists, no upper bound).
   **Fix:** parse `at` as `datetime.fromtimestamp(float(at), tz=timezone.utc)`; guard `isinstance(entry, dict)` before any `.get`; widen the except tuple to also catch `TypeError`/`OverflowError`/`OSError` (bad/out-of-range `at`); add `if ts > now: continue`. **Also remove the `previous_value` parameter and its branch (lines 1519-1520, 1562-1565) entirely** — it's dead in production (`run_all()` never passes it, confirmed at line 1760), it's the second "did this get worse" mechanism the original design doc already decided to delete in favor of `mr.compare()`/`record_anomaly_metrics()` (which `run_all()` already calls generically, line 1781), and it's what caused this function to need two different "yellow" reasons. Deleting it removes a whole class of future bugs, it doesn't just patch this one.

2. **`scan_merged_prs` (`lib/health_checks.py:1403-1435`) can crash `run_all()`.** Confirmed: `rules = auto_merge_policy.load_rules()` and the `for pr in prs:` loop (lines 1421-1434) sit **outside** the `try/except` that wraps only the subprocess call and `json.loads` (lines 1408-1419). A `pr` entry that isn't a dict, or a `files` entry that isn't a dict, raises `AttributeError` on `.get`, uncaught. (`pr.get("body", "")` returning `None` on explicit JSON `null` is actually already safe — `mutation_score()` does `body or ""` internally, confirmed at `auto_merge_shadow.py:42` — so that specific sub-claim in the review is slightly imprecise, but the structural problem it's pointing at, an unguarded loop outside the try, is real and is what I'm fixing.)
   **Fix:** move the scoring loop inside a `try`, with `isinstance(pr, dict)` / `isinstance(f, dict)` guards that `continue` (not raise) on a malformed entry, so one bad PR or file entry degrades that one entry, not the whole scan. Also add a `rules: dict | None = None` parameter (default `None` → `auto_merge_policy.load_rules()`) so tests can inject rules instead of depending on the real `config/auto_merge.json` (this is also what fixes the review's note about `test_scan_merged_prs_scores_and_detects_core` reading live config). And pass `env=project_catalog.run_env()` on the `gh` call — `project_catalog.run_env()` already exists precisely to put the GitHub gate ahead of Homebrew's `gh` in `PATH` under launchd's bare environment (confirmed `lib/project_catalog.py:404-419`); without it this new call bypasses the gate (cooldown/budget floor) exactly as the review's note flagged, and reuses an existing primitive rather than adding a new one.

3. **`check_repo_growth`/`_top_level_dirs`/`new_top_level_this_week` (`lib/health_checks.py:1572-1699`) only catch `TimeoutExpired`, and `check_repo_growth` has no injectable `run`.** Confirmed: `_top_level_dirs` (line 1572) and `new_top_level_this_week` (line 1585) each take `run=subprocess.run` but only `except subprocess.TimeoutExpired`. `check_repo_growth` itself (line 1611) has **no `run` parameter at all** — its three file/folder/size blocks call module-level `subprocess.run(...)` directly (lines 1622, 1639, 1660), so a test can't inject a missing-`git` failure, and a real missing/unreadable `git` (`FileNotFoundError`/`OSError`/`PermissionError`) propagates straight out of `run_all()`. Also confirmed: `repo_path = repo_path or Path.cwd()` (line 1615) defaults to the wrong tree under launchd (though `run_all()` already passes `HOME / ".agents"` explicitly at line 1764, so today only a bare call is affected); files and folders are counted via two separate `git ls-tree -r --name-only HEAD` calls instead of one shared call; neither call passes `-c core.quotePath=false`, so non-ASCII filenames come back quoted and would be undercounted in the folder-prefix split.
   **Fix:** add `run=subprocess.run` to `check_repo_growth`'s signature and thread it through all three blocks; widen every except to `(subprocess.TimeoutExpired, FileNotFoundError, OSError)`; default `repo_path` to `HOME / ".agents"` instead of `Path.cwd()`; share one `git -c core.quotePath=false ls-tree -r --name-only HEAD` call for both files and folders; add `-c core.quotePath=false` to the size call too; guard the `rules.get("new_top_level_per_week")` path (already present at line 1689, keep it) against `rules` itself being malformed (non-dict) by treating that the same as "limit unavailable."

4. **`verify_health_checks.py` is a committed stray script that pollutes production state.** Confirmed: it's untracked (git status shows `?? verify_health_checks.py`) and every run calls `hc.run_all()` (line 17), which calls `mr.record("health-monitor", ...)` (a real, permanent append to `~/.agents/bench/metrics/health-monitor.<machine>.json`) and does a live `gh pr list` through `scan_merged_prs`.
   **Fix:** delete it. No replacement committed file — manual sanity-checking during implementation uses `health_checks.py`'s own existing `--json` CLI entry point (`_cli()`, line 1806) against a scratch `HOME`/`MARVIN_METRICS_DIR`, never the real ones.

5. **`test_repo_growth_yellow_on_exceed_new_top_level_limit` (`lib/tests/test_health_checks.py:1510-1539`) doesn't test what it claims.** Confirmed by reading it: both commits it creates are made seconds apart, so `new_top_level_this_week` always returns `None` ("not enough history"), and the test's own assertion is an `if green: pass else: assert yellow/red` — it passes either way, so the over-limit branch (lines 1688-1697 in the source) is never actually exercised.
   **Fix:** rewrite it to make the "old" commit real history: create the initial commit with `GIT_AUTHOR_DATE`/`GIT_COMMITTER_DATE` env vars set to 8 days before `now`, then add the new top-level dirs in a second, present-day commit, call `new_top_level_this_week(tmp_path, now=now)` to confirm it returns a real diffed set, then assert `check_repo_growth(..., rules={"new_top_level_per_week": 2}, now=now)`'s `repo-growth:new-top-level-weekly` result is unconditionally `"yellow"` or `"red"` (not the current either-or that can't fail).

**Notes-level fixes folded in because they're cheap and I'm already touching every line they're on** (not scope creep — each is inside a function this ticket is rewriting anyway): `HIGHER_IS_BETTER` derives its id via `f"mutation-score:{project_catalog.slug('G-Eskayo/marvin')}"` instead of the hardcoded literal; the new functions switch from tab indentation back to the file's existing 4-space convention; the fixed `/tmp/...` paths in `test_test_skip_trend_yellow_on_burst`, `test_new_top_level_this_week_handles_no_old_commit` move onto `tmp_path`.

**Explicitly not touched:** `check_ticket_failure_streaks`'s pre-existing bare `gh` call (line 151) has the same gate-bypass issue the review flagged for `scan_merged_prs`, but that function predates this ticket and isn't part of what #342 asks for — fixing it here would be scope creep on a function this ticket doesn't own. Worth a follow-up ticket, not this one.
