Simplest sufficient approach: a two-line text edit, no code, no new abstraction — the bug is that a *relative* link breaks depending on which path (symlink vs real file) it's read through, and an absolute path removes that path-dependence entirely. Spends no extra tokens/compute; it's a doc fix. Leaves the user (an agent running `/research`) more capable: it gets the epistemic-tier framework on the first read instead of a silent 404, which is the whole point of north star 1 (resources spent get the job done, not wasted on a failed lookup).

## Tests (written first)

The ticket's "How we'll try to break it" section describes two checks:

1. **Read the skill through the symlink path and through the repo path: the link resolves both times.** An absolute `~/...` path resolves identically no matter which path the file was opened through, so this is satisfied by construction once the link is absolute rather than relative — there's no code path where "symlink vs repo" changes resolution. I'll still encode it as a concrete regression assertion (test A below) so a future revert back to a relative link is caught mechanically, not just by inspection.
2. **A skill whose folder got renamed: the check above names the broken link.** This is a known, accepted limitation, not a new mechanism to build: an absolute path bakes in the skill's current folder name, so a rename would silently break it, and nothing in this repo re-derives these paths automatically. The ticket's own acceptance criterion 3 (the `rg` sweep) only matches *bare relative* links by design — it won't catch a stale absolute path either. Building a path-existence linter for this is out of scope for a P1 doc fix (no existing precedent in the repo — there is no SKILL.md-content test anywhere, only per-skill `scripts/tests/` for script code) and would be scope creep beyond what the ticket asks for. I'm flagging this rather than silently building extra machinery.

There is no dependency to fail, no concurrency, no permissions issue, and no "stale state" risk here — this is a static two-line markdown edit with no runtime behavior, so most of the standard adversarial-input categories (empty/huge/malformed input, repeats, wrong permissions) don't apply to the artifact itself. The only thing worth protecting against is **regression** (someone reverting the fix, or copy-pasting the old relative-link pattern back in), which test A covers.

Pure string/content check on a repo file — no HOME, no filesystem mocking, no `real_home_guard` interaction needed, so it runs identically in CI as it does here.
- No test is added for criterion 3's broader sweep as a standing lint — see Decisions-equivalent note above; I verified it by hand this run and it's reported in the PR description instead of as new permanent test infrastructure, consistent with "don't add abstractions beyond what the task requires."
