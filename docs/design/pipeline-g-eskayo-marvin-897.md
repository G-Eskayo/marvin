**Simplest sufficient:** no new daemon, cron, or health-check sweep. Job liveness already lands in `~/.claude/logs/jobs/<job>.json` via `job_events`/`job_report`; this ticket adds one declared number per catalogued job (`quiet_s`) and a one-shot client-side timer per producer, armed from data already flowing through the existing `work.json` poll — not a new scanning loop. This is the same reasoning Gil gave for Peer watch (triggers, not timers).

**Resources:** spends nothing new server-side; the only new backend cost is a few extra dict entries per `work_view.py` read, already O(catalogued jobs). Client-side it's one `setTimeout` per producer (handful of jobs), replacing nothing.

**Phone-OS:** the new `producers` array in `work.json` is the same JSON Mobile will eventually read — no rework needed there later.

**Capability, not passivity:** this closes a real blind spot Gil named ("a quiet system and a deaf one never look the same") — it makes a silently-dead background job visible instead of indistinguishable from "nothing to do right now," directly serving north star 3 ("nothing broken silently") and north star 5. It leaves Gil more informed, not more automated-around.

**Machine:** client-side code (the map/wallpaper) already runs on both Macs identically; the Python data side (`work_view.py`, `job_catalog.py`) already runs per-Mac locally against that Mac's own job logs — no new placement decision.

**Scope boundary (checked against the ticket):** AC1 ties the declaration explicitly to "the job catalog" (`lib/job_catalog.py`), so this plan is scoped to catalogued **scheduled** jobs (run-log producers). Continuously-running services with no discrete runs — `desktoplive`, `dashboard-webhook`, `dashboard-launch` — already have their own aliveness checks (`health_checks.py`: "desktoplive:running", "port 7878 answers") and get no `quiet_s`; they're excluded from this mechanism rather than falsely forced into a run-log model that will never populate for them. Mac-to-Mac "peer watch" is ticket #898, not this one: since job logs are per-machine and never synced (`job_events.py`'s own docstring), the producers list here is built entirely from this machine's own clock and own files — which is *why* clock skew between Macs structurally cannot reach it, and why a sleeping laptop cannot greys the Mini's parts (no cross-machine read exists in this path at all).

No Decisions block: every fork below (grey colour, banner wording, never-run-is-grey, timer vs. poll-tick) is already settled by a recorded precedent (CONTEXT's Staleness gradient, the existing offline-grey colour, the ticket's own quoted wording), so there's nothing left that needs Gil picking between options.

## Tests to write first

From "How we'll try to break it," plus misuse the section didn't name:

1. **Kill the activity writer** — a catalogued producer's job log shows a crashed run (started long ago, never finished) and no further runs; past `quiet_s` it reads `grey`, and with it the only applicable producer, the map's overall mark is "not hearing from anything," never healthy.
2. **Legitimately-quiet weekly job** (`sbir-monitor`) — at +40 min, +6 h, +2 days since its last Wednesday run, still reads `hearing` (its declared `quiet_s` covers the weekly gap).
3. **Explicit "sleeping" report** — a fallback job (`daily-digest-fallback`) whose runs are all `job_report` skip-on-purpose passes ("skipped: Mini built today's digest") keeps reading `hearing` as long as those passes keep landing inside `quiet_s`; it never degrades just because it did no real work.
4. **Clock skew, producer's timestamp in the future** — a run's `finished_at` ahead of the reader's clock clamps to "just now"/`hearing`, never `grey`, never throws (mirrors `stamped.py`'s future-guard idiom).
5. **No cross-machine read exists** — a job catalogued `"machine": "laptop"` is never included in the Mini's producers list (and vice versa), proving there is no path by which another Mac's clock or log could grey a part here.
6. **Sleeping the laptop must not grey the Mini's parts** — feeding a peer/Mac-asleep signal into the page changes no producer's listening state.
7. **Excluded producers** — jobs with no declared `quiet_s` (`desktoplive`, `dashboard-webhook`, `dashboard-launch`) never appear in the producers list at all: not `hearing`, not `grey`.
8. **Bad/empty/malformed input** — `producers` missing, `[]`, not an array, an entry missing `id`/`quiet_s`/`last_heard`, duplicate ids, a 50-producer burst in one tick: no throw, no double timers, malformed entries skipped the same way `applyWork`'s existing `typeof` guards do.
9. **Out-of-order / repeated events** — an older timestamp arriving after a newer one never rearms the deadline backwards; the latest-heard time always wins (reuse the "use the fresher" idiom from `stamped.newer`).
10. **Dependency failure: unreadable/corrupt job log** — a `.json` that exists but fails to parse reads as "never heard" (`grey`), not a crash (matches `_read_json`'s existing `OSError`/`ValueError` → `None`).
11. **A person's mistake: uncatalogued-but-running job** — a job removed from `job_catalog.py` while still loaded never gets a `quiet_s`, so it's excluded here (it's already separately flagged by `job_catalog.waste()`, not duplicated).
12. **Timer hygiene / concurrency** — two producers crossing their deadline in the same tick both go grey correctly; a producer removed from a later `work.json` read leaves no orphaned timer; the global "not hearing anything" mark clears the instant any one producer reports again, without waiting for the next poll.
13. **Parity** — the same fixture rendered once as `?wallpaper=1` and once as the dashboard view (both load the identical generated page) yields identical grey state for every producer at the same clock time.
