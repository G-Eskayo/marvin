## North-star fit

**Reuses:** the hardened `webPreferences` shape already established at `dashboard/electron/main/mockup_window.js:93-103` (`createMockupWindows`) and `dashboard/electron/main/show_web.js:98-107` (`createWebPane`) — both already ship `sandbox: true, contextIsolation: true, nodeIntegration: false, nodeIntegrationInSubFrames: false, webSecurity: true, webviewTag: false, navigateOnDragDrop: false`. `show_window.js:255-266` already has every one of those flags except `sandbox` itself. The only two call sites still on `sandbox: false` are the main window (`index.js:374-390`) and the show window (`show_window.js:246-267`) — this ticket brings both up to the baseline the codebase already settled on elsewhere, rather than inventing a new security posture. It also reuses the DI pattern those two files established (`BrowserWindow` passed in, not imported) so the change is unit-testable the same way the rest of the window-creation code already is.

**Simplest sufficient approach:** the preload (`electron/preload/index.js`) imports nothing but `contextBridge`/`ipcRenderer` from `electron` — no `fs`, `path`, `child_process`, no other Node builtin — and `show_window.js` already shares that exact preload. A sandboxed preload only loses access to arbitrary Node APIs; this preload never used any, so `sandbox: true` is a config flip with no preload rewrite needed. `nodeIntegration` was already `false` and `contextIsolation` already `true` on both windows, so the renderer's own isolation is unchanged — this closes the one remaining gap (the preload's own process reaching Node) rather than redesigning IPC.

**Where it spends tokens:** one small new file (`electron/main/main_window.js`, a pure options function + a thin DI factory) so the hardened `webPreferences` is asserted by a real unit test instead of only reachable by booting the real app — `index.js` can't be imported under vitest at all (`instrumentIpc(ipcMain)` and a dozen other module-load side effects run on real Electron singletons; `test/entry_files_load.test.js` only does a syntax `--check` on it, confirmed by reading it), which is almost certainly why the prior two automated attempts (see issue comments) failed code review with no way to prove the central claim. This is the same reason `mockup_window.js`/`show_window.js` exist as separate DI'd files already — reusing that precedent, not adding a new one.

**Leaves the user more capable / not more passive:** this is pure risk reduction with no behavior change Gil would ever see day-to-day (same tabs, same Approve/Decisions flow) — it removes a real attack surface (45 published advisories on Electron 30, a renderer that can render arbitrary GitHub text with `sandbox: false`) without costing him anything in workflow.

**Machine:** the laptop (where this worktree already is, claimed `macbook-pro`) for the implementation and `npm test`; the acceptance criteria explicitly also require `rebuild-and-install` and the sandboxed-tab walkthrough on **both** Macs before this can be called done, since code signing and the Mini's separate install are real, divergent runtime environments that no CI run can stand in for.

No north star argues against this work.

**Decisions:** none needed — the ticket is concrete (latest *supported* major, sandbox on both remaining windows, osv-scanner clean) and every other call is an engineering determination (electron-builder compatibility, exact breaking-change fixes), not a product choice for Gil to pick between.
