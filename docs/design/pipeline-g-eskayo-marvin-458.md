## North-star fit

**Reuses before adding anything new:** `lib/scanner_role.py:23-46` (`is_primary()`, `should_scan()`) is the exact already-built primary/standby primitive for this ticket's shape — "the primary (mac-mini) always scans/builds, the standby only when the primary's gone quiet." The plan adds one new module, `lib/brief_fallback.py`, that mirrors `should_scan()`'s call pattern (`Decision(should_build, reason)`) but checks a dated output file instead of a liveness heartbeat. It composes with, not duplicates, existing primitives: `machine_profile.registry_id()`/`remote_macs()` for identity and host lookup, `task_dispatch.SSH_OPTS` for the SSH flags, and `cross_machine_merge.py`'s `ssh_run()`/`cat <path>` shape for the live remote read (`read_remote()`). The idempotent-write guard already in `daily_digest.py:main()` (`if OUT_FILE.exists(): return`) and `research_digest.py:generate()` is kept, just swapped from a bare `.exists()` to the new `produced()` (same place, same shape, smarter check). Health's new check follows the existing `check_catalog_fresh()`/`_result()` pattern; the new `cron_health.JOBS` entry follows its own established tuple shape.

**A validated design already exists, not being re-derived:** this exact design was built, code-reviewed (verdict: no must-fix issues, 67% mutation score) and opened as PR #600, preserved at git ref `refs/rescue/pipeline/g-eskayo/marvin#458/20261022T110641735890Z` (commit `40411cef`). One prior review flagged real, still-unfixed quality gaps (below); I'm folding those in rather than restoring the WIP byte-for-byte.

**Root cause of the recurring merge conflict, found by reading current `main`, not assumed:** every retry's Task List step 3 says `Write skills/improve/scripts/tests/test_daily_digest.py` as a **new file**. It is not new — `skills/improve/scripts/tests/test_daily_digest.py` already exists on `main` today (340 lines of unrelated `bench_summary`/`reviewer_health_summary` tests, confirmed by reading it). Treating it as a fresh "new file" write is exactly an add/add conflict shape every time the branch rebases onto a `main` that already has this file — matching the repeated "same lines changed on both sides" failures in the comment history. **Simplest sufficient approach:** one new ~170-line module plus small, surgical edits to six existing files and three new fallback-schedule plists — no new scheduling framework, no change to `cross_machine_merge.py`'s item-sync (qa-knowledge/paper-knowledge/research-feed stay symmetric and unaffected; they already guard "no local cache yet" gracefully).

**Where it saves/spends tokens:** this is ADR 0067's "halve the model calls" ticket (research colony + daily digest currently both-Macs). Once installed, each of the three jobs runs once a day instead of twice on a normal morning, and `~/.claude` sync stops seeing the duplicate same-day quarantine entries ADR 0067's Context names (2026-10-10, 2026-10-15 incidents).

**More capable or more passive:** more capable — Health gains a real, truthful "which machine built today's brief" answer (AC4) instead of silence, and Gil's `~/.claude` sync stops colliding on duplicate output nobody asked for twice.

**ADR/CONTEXT check:** matches ADR 0067's decision and Consequences ("fan-out-and-merge becomes unnecessary for these jobs") without silently deleting `cross_machine_merge.py`'s merge step — that removal is a genuinely open Decision below, not assumed.

**Known, flagged, not fixed:** `scanner_role.is_primary()`'s `startswith("mac-mini")` would also match a future `mac-mini-2012` (Kali) entry if that node ever registered under a similar name. ## Decisions

<!-- marvin:decisions -->
### quarantine-counts-as-produced: Does a quarantined (but not failed) digest count as "the Mini produced it"?
- [ ] A: Quarantined counts as produced — the Mini did its job; a held-back item is a safety-check outcome, not an outage. The laptop never rebuilds just because content got quarantined.
- [ ] B: Quarantined counts as not produced — if the brief chain got nothing usable, the laptop should still try, in case its own run clears the safety check.

### retire-cross-machine-merge: Remove `cross_machine_merge.py`'s LLM digest/research-digest merge step now, or leave it in place?
- [ ] A: Remove `run_merge_authority` and its daily-digest/research-digest loop now — ADR 0067 says this step "becomes unnecessary for these jobs," and leaving it risks a stray LLM merge call plus a third `{day}-merged.md` write-back on the rare day the fallback actually fires alongside a late primary.
- [ ] B: Leave it in place for now (it already runs zero LLM calls on a normal day, since one side's file won't exist) and remove it in a separate follow-up ticket.

### brief-schedule-margin: Morning brief at 09:15 leaves only 15 min after the 09:00 research colony starts (colony's `call_claude()` alone has taken 90-120s+, plus fetch/correlate) (optional)
- [ ] A: Keep 09:15. `write()`'s idempotency means a brief built before the research digest lands never gets the "one idea from research" line that morning — acceptable, matches ADR 0067's "the brief still arrives on time" philosophy (`gather()` already tolerates a missing source).
- [ ] B: Push the Mini's morning-brief schedule later (e.g. 09:25) for a safer margin, at the cost of the brief landing slightly later each day.
