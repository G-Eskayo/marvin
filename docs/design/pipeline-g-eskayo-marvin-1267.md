## North-star fit

**Reuses:** `evidence_capture.run_timed`/`capture_test_results` (`lib/evidence_capture.py:133-223`, marvin#1113's test-slot-wait exclusion) — built for exactly this problem (a test run's wall-clock timeout silently eaten by waiting for `test_slot.py`'s "one test run at a time, merges first" lock) but never wired into `conflict_repair.default_tests` (`lib/conflict_repair.py:112-138`), which still does a bare `subprocess.run([... "pytest" ...], timeout=TEST_TIMEOUT_S)`. Also reuses `health_checks.check_dispatch_lock`'s age-threshold pattern (`lib/health_checks.py:119-150`) and `check_pipeline_breaker`'s cross-machine SSH-read pattern (`lib/health_checks.py:363-397`) for the new amber card, and `job_events`'s existing per-step timestamps (`lib/job_events.py:79-86`) for instrumentation — no new logging mechanism needed.

**Simplest sufficient approach:** the 50-minute stall has one root cause and it needs one fix regardless of which structural option is chosen (see Decision below): `conflict_repair.default_tests` runs its pytest/verify subprocess with a flat, slot-wait-unaware timeout, so when a scan's repair attempt lands behind a live merge (the `merges first` rule in `test_slot.py`), the wait itself burns the full `TEST_TIMEOUT_S` (25 min) per attempt, and `MAX_PER_SCAN=2` attempts stack to ~50 min — exactly the incident. No new mechanism is needed to fix this, just wiring the existing #1113 pattern through with a short, scan-appropriate wait cap (unlike a ticket build's generous 7200s cap, this step runs inside an hourly scan and should give up fast and defer to the next hour).

**Where it saves/spends:** saves wall-clock and dispatch latency (the actual bug); spends a small, fixed amount of extra code (reusing, not inventing). No added token cost beyond the design/build itself — the model-assisted repair path (`_resolve_hunks_with_model`) is unchanged.

**More capable, not more passive:** this is pure reliability plumbing — it makes MARVIN's own pipeline keep working unattended, consistent with north star 5 (every machine works) and the "nothing breaks silently" precondition. No user-facing behavior change for Gil beyond a scan that no longer silently stalls dispatch for an hour, and a new amber signal when it's slow instead of a mystery gap.

**Which machine:** no machine-specific concern — this is pure pipeline-logic/health-check code, runs wherever `ticket_pipeline.py`/`health_checks.py` already run (both Macs).

## Root cause (found, not guessed)

The ticket's own hypothesis is correct and now pinned to code: `_requeue_conflicted_prs` (`lib/ticket_pipeline.py:321-411`) calls `_try_conflict_repair` → `conflict_repair.attempt` → `conflict_repair.repair` → `run_tests=default_tests` (`lib/conflict_repair.py:112-138`), which runs `subprocess.run([VENV_PYTHON, "-m", "pytest", ...], timeout=TEST_TIMEOUT_S)` directly. That spawned pytest's own root `conftest.py:pytest_configure` (lines 87-104) takes this machine's real `test_slot` lock for any "heavy" (whole-suite) run — and merges always go first (`test_slot.slot()`, `lib/test_slot.py:101-154`). Because `default_tests` never routes through `evidence_capture.run_timed` (the thing that excludes slot-wait time from a timeout, per marvin#1113), each repair attempt's wait behind the live merge counts fully against its own 25-minute timeout. `conflict_repair.Budget`/`MAX_PER_SCAN=2` already caps this at 2 full attempts per scan — 2 × ~25 min ≈ 50 min, matching the incident (16:21→17:11) exactly. The whole `_scan()` — including this step — runs inside `with _scan_lock()` (`lib/ticket_pipeline.py:879-884`), so the lock (whose actual purpose is only "don't let two scans claim the same ticket," per its own docstring) is held hostage the whole time, and the 16:13/16:22/17:02 scans correctly saw it busy and skipped.

## Decisions
<!-- marvin:decisions -->
### scan-structure: How should "dispatch never waits behind Conflicted PRs" be achieved?
- [ ] A: Dispatch runs first — reorder `_scan()` so ticket claiming/dispatch happens before "Conflicted PRs"/"Owner decisions"/"Parked choices". Smallest change, but the scan lock is still held for the step's full duration afterward, so a *second* scan still can't start until it finishes — only this scan's own ready tickets get dispatched promptly.
- [ ] B: Move the step out of the scan — run `_requeue_conflicted_prs`/`_requeue_all` from a new standalone scheduled job (its own `job_events.job_run`, its own launchd plist, e.g. every 15–20 min), outside `SCAN_LOCK_PATH` entirely. Matches what the lock is actually for (ticket claims, not PR housekeeping); the hourly scan's lock is then held only for board discovery + dispatch (fast). Needs a new plist per machine and an update to the step-order test.
- [ ] C: Give it a time budget — keep it inside `_scan()`, but cap total wall time the step may spend (and cap each repair's test-slot wait specifically); whatever it hasn't reached when the budget runs out is left for next scan's fresh listing (already idempotent — no state is lost between scans). Lowest blast radius, no new job, but the lock is still held for up to the budget's length every scan, even when nothing is actually wrong.

Recommendation: **B**. It's the only option that removes the scan lock from the critical path on every run, not just a slow one, and it correctly separates "claim a ticket" (what the lock protects) from "repair a PR" (what this step does) — `_requeue_conflicted_prs` is already idempotent and uses its own re-read-before-act guard (`_still_needs_sending_back`) and its own per-commit memory (`conflict-repair.json`), so it needs no lock of its own. The slot-wait fix below (next section) is needed either way.
