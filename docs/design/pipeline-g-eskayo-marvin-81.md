**More capable, not more passive.** Pure visibility; nothing is paused, queued, or decided automatically. Unchanged from both prior rounds' framing, and still correct.

## Root cause read (what actually broke this time)

Reading the live diff, not the metrics summary in isolation, these are the concrete defects, each independently confirmed by reading the code on disk:

1. **`dashboard/src/lib/usage_view.js:143-154` (`weekList`)** mixes a UTC-constructed `Date` with local-timezone accessors (`getFullYear()`) and a local-timezone constructor (`new Date(year, 0, 1)`). It also numbers weeks from each row's *own calendar year's* Jan 1, so a window spanning a year boundary (e.g. late Dec into early Jan) produces week indices from two different epochs that never collide — prior-year weeks always show zero. Both are real, user-visible bugs: the first depends on which machine runs it, the second depends on the calendar date.
2. **`lib/session_usage.py:134-153` (`by_job`)** parses `at` with `datetime.fromisoformat(...).replace("Z","+00:00")` directly: a timestamp with no `Z`/offset (malformed or an older log format) parses successfully to a *naive* datetime, then `at < cutoff` raises `TypeError` comparing naive-to-aware, uncaught — crashing `by_job()` and therefore all of `aggregate()`. The same function also does `by_key[key]["output_tokens"] += out` with no type check, so a non-numeric `output_tokens`/`cost_usd` value crashes the same way. **Same defect exists in `_parse_ts()` (line 48-52)**, used by every transcript-based aggregation path — `_parse_ts` doesn't coerce a naive result to aware either, so a malformed/old-format transcript line hits the identical `TypeError` in `aggregate()`'s main loop. This was not caught by the reviewer but is the same bug in the sibling function; fixing it once in `_parse_ts` and having `by_job()` call that instead of re-parsing inline removes the duplication and the bug in one place.
3. **`lib/tests/test_session_usage.py:111-125`** calls `tu.aggregate([], now=NOW, window_days=30)` with no `launches_path`, so it (and seven other pre-existing `aggregate()` calls in this file) silently reads the real `~/.claude/logs/launches.jsonl`. In this specific test the result is immediately thrown away (`r["by_job"] = tu.by_job(...)` overwrites it), so the call is pure waste as well as non-determinism — it doesn't need to exist at all.
4. **`lib/tests/test_health_checks.py:1444-1455`** calls `hc.run_all(usage_path=...)` for real, stubbing only `mr`. Every other check inside `run_all()` runs unstubbed: `gh api graphql` (GitHub budget), `gh issue list` (ticket streaks), SSH to remote machines (reachability/sync/breaker), ChromaDB, and reads of a dozen real files under `~/.claude/logs`. This is exactly the shape of flakiness that produced the original PR #359 denial (`json.decoder.JSONDecodeError: Extra data` from a real file read deep in the call graph) — the test cannot be deterministic while it does this.
5. **New finding, not in the review:** `skills/improve/scripts/auto_fix.py:209` launches `"background-analyst"` with no `ticket=`. The existing parametrized test `test_each_caller_declares_its_launch_kind` (`lib/tests/test_marvin_launcher.py:181-195`) already groups this call alongside the five sibling digest/review scripts that *did* get tagged in this diff (`daily_digest.py`, `research_digest.py`, `background_review.py`, `background_architecture_review.py`, `ticket_promotion.py`) — `auto_fix.py` is the one left out, so its spend falls into the generic `("background-analyst","background-analyst")` bucket instead of being named, which is exactly the visibility gap "Top autonomous spenders" is supposed to close. I checked every other `marvin_launcher.launch(` call site in the repo (`purpose_metrics.py`, `denial_diagnosis.py` already pass `ticket=`; `ticket_pipeline.py`, `disk_forecast_notify.py`, `mr_notification.py`, `fit_check.py`, `generate_handoff_from_transcript.py`, `safety-monitor/verify.py` are `utility-call`/`judge` pings outside the digest/review family this ticket's diff is tagging) — only `auto_fix.py` is a same-family miss.
6. **Confirmed still missing, both rounds:** `dashboard/src/components/UsageView.jsx` has not been touched in either attempt (absent from `git diff --stat`). `autonomousSeries`, `weeklySeries`, `jobTable` are exported and tested in isolation but never rendered. Three of the ticket's four acceptance criteria ("autonomous vs interactive per day and per week", "share line with 30/40/50% references", "top autonomous spenders listed") are not met without this.
